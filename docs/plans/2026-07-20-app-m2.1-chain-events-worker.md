## 1. Origin & problem statement

Master plan §2: *"chain-events worker: vault/contract event ingestion →
`transactions`, `redemption_requests`; idempotent upserts keyed (txhash, event
index); replay proof: re-run from height 0 converges to byte-identical derived
state."* The `Transaction` and `RedemptionRequest` Prisma models already exist
([`transactions.prisma`](../../services/indexer/prisma/transactions.prisma),
[`redemption_requests.prisma`](../../services/indexer/prisma/redemption_requests.prisma));
this PR writes the worker that fills them and proves replay convergence.

The pinning fact that shapes the whole design (from the fixtures manifest): the
relevant events **do not all live in tx-search**. Swap-in, swap-out-request, and
expedite arrive via LCD tx-search; **payout, refund, and the
`EventSetNetAssetValue` NAV marker are EndBlocker events**, present only in RPC
`block_results.finalize_block_events`. The worker must ingest from both, behind
one checkpoint, in one causal order.

## 2. Mechanism

Files under `services/indexer/src/workers/chain-events/`:

- `index.ts` — registers the `chain-events` worker (via M2.0 `registerWorker()`),
  wires the loop from `runtime/worker.ts`.
- `sources.ts` — the **dual-source window reader**: for a window `[from, to]`,
  fetch (i) tx-search filtered to vault module events + `wasm._contract_address
  = contractAddress`, and (ii) `block_results` for each height in the window
  (EndBlocker payout/refund/NAV). Merge into **one height-ordered event stream**
  so reducers see a single causal order.
- `decode.ts` — raw events → typed domain events (`SwapIn`,
  `SwapOutRequested`, `PendingSwapOutExpedited`, `SwapOutCompleted`,
  `SwapOutRefunded`, `SetNetAssetValue`) via M2.0 `decode/attributes.ts`.
- `nav.ts` — tracks the running NAV from `EventSetNetAssetValue.price` so each
  `Transaction.navAtHeight` is the NAV current at the ingestion height (per the
  model comment).
- `transactions.ts` — reducer → `Transaction` rows (kind mapping: `swap_in`,
  `swap_out_request`, `redemption_payout`, `redemption_refund`; `transfer_in/out`
  where applicable).
- `redemptions.ts` — the lifecycle assembler (§3).

All writes for a window plus the cursor advance happen inside one M2.0
`runWindow` transaction.

### Idempotency keys

- `Transaction`: upsert on `(txhash, msgIndex)` — the model `@@id`. For
  **txless EndBlocker rows** (payout/refund emitted in `finalize_block_events`),
  the txhash slot uses a **deterministic synthetic id**
  (`blk:{height}:{request_id}:{payout|refund}`) so replay re-derives the
  identical PK. *This is the one design decision reviewers must explicitly
  bless* — it is what makes byte-identical replay hold for rows with no tx.
- `RedemptionRequest`: upsert on `requestId` (natural key).

Because every write is an upsert keyed on chain-derived identity and reducers
are pure functions of the ordered event stream, re-running from height 0
converges to identical rows.

## 3. Redemption lifecycle assembly

Keyed by `request_id`; a fixed **status lattice** advances the row monotonically
so out-of-order replay (a payout observed before its request in a re-point) still
converges:

| Event | Source | Effect (only if not already terminal) |
| --- | --- | --- |
| `EventSwapOutRequested` | tx-search | upsert `enqueued`; set `enqueuedAt`, `shares`, `owner` |
| `EventPendingSwapOutExpedited` | crank tx | set `expeditedAt`, status `expedited` |
| `EventSwapOutCompleted` | block_results | set `maturedAt`, status `matured` (terminal) |
| `EventSwapOutRefunded` | block_results | set `refundedAt`, status `refunded` (terminal) |

Terminal states never regress; `lastHeight`/`lastTxhash` track the newest event.
The `estimates` JSON series (§9.5.3 time-to-payout source) is appended from
sampled projected-payout reads where available — amounts as decimal strings,
never JS numbers (model comment, amount discipline).

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **Idempotent replay of untrusted chain input** (SECURITY.md "chain is the
   source of truth"). *Gate:* `test/property/chain-events-replay.test.ts`
   (Vitest + fast-check) — random sequences of swap/expedite/payout/refund over
   arbitrary `request_id`s and heights; assert full-replay and
   random-restart-height replay both **deep-equal** the derived `Transaction` +
   `RedemptionRequest` state and produce identical PK sets. DB modeled as an
   in-memory upsert map → Postgres-free, joins `pnpm -r run test`.
2. **Decode matches the captured corpus.** *Gate:*
   `test/fixture/chain-events-decode.test.ts` against every relevant fixture
   (`msgs/swap-in`, `msgs/swap-out`, `run-epoch/expedite`,
   `block-events/swap-out-completed`, `block-events/swap-out-refunded`) — a
   contract event-shape change breaks this test, not production.
3. **No PII.** Only public bech32 `address`/`owner`, heights, txhashes, amounts —
   all already on the schema allowlist; logging stays within `SAFE_FIELDS`. No
   new columns.

## 1. Origin & problem statement

Master plan §2: *"Validators public page (§8.6 public view): set table/cards,
set-health aggregates, Console verify links."* Depends on 4.1 (merged) and
"3.1 contracts". The consumer framing is §8.6's: "who is staking your HASH
and are they reliable," never the console's operational table. The operator
view (`/validators/mine`) is NOT this PR; it is M6-adjacent (§14.6 flows) and
needs sessions.

Following the 4.2 precedent (Carlton, 2026-07-22): the `/validators` endpoint
contract, deferred from 4.2's tranche, is frozen here, inside this PR, as an
honest empty scaffold that PR 3.1 implements for real. PR #9 (M2.2-2.5,
`validator_registry`/`validator_epochs`) is still in review; the shape below
must stay derivable from that schema but this PR must not depend on #9
merging.

What already exists for the live plane, all fixture-mocked:

- `NvhashContractClient.validators()` → `ValidatorStatus[]` (`valoper`,
  `operator`, `enrolledAtSeconds`, `uptimeBps` nullable before first capture,
  `jailed`, `tombstoned`, `inArrears`, `eligible`, plus operator economics
  this public page deliberately does not render).
- `NvhashContractClient.config()` → `performanceThresholdBps` (the uptime
  threshold the page compares against) and `jailReports()` if needed.
- `StakingClient.validators()` → monikers (`StakingValidator.moniker`) and
  `StakingClient.delegations(delegator)` → per-validator program delegation,
  where the delegator is the vault principal (`VaultState.principal.address`
  from `VaultClient.getVault`).
- `epochSnapshot()` → current `eligibleCount`.

From 4.2 (PR #11): `app/api/api.server.ts` (bounded transport, envelope
schemas), `app/learn/amounts.ts` (`formatHashCompact`, `bpsToPercent`),
`app/learn/duration.ts` (tenure display), the MSW endpoint pattern, and the
`VerifyLink` `validators` target (already in the closed map since 4.1).

## 2. Mechanism

### Tranche 1: the `/validators` 3.1 contract (frozen, honestly empty)

- `packages/api-types` (`src/rows.ts`): `ValidatorSetEpochRow
  { epoch_index: number; ended_at: string; eligible_count: number;
  enrolled_count: number; joined: number; departed: number }`, one row per
  settled epoch (newest first): exactly the §8.6 set-health inputs (eligible
  trend + churn), derivable from PR #9's `validator_epochs`/
  `validator_registry` (per-epoch eligibility flags; registry enrollment and
  departure marks).
- `services/api`: `GET /api/v1/validators` (enveloped, paginated by the
  existing `paginationSchema`, empty scaffold with null heights) registered
  in the route table; the registry-driven contract harness covers it
  automatically, plus a shape assertion like 4.2's.
- `apps/web/app/mocks/handlers.ts`: the matching MSW handler via
  `envelope()`.

### Tranche 2: data assembly (server)

- `apps/web/app/api/api.server.ts`: add `validatorSetEpochRowSchema` and
  `validatorsEnvelopeSchema` (`z.array(...).max(200)`), pinned with
  `satisfies z.ZodType<ValidatorSetEpochRow>`.
- `apps/web/app/validators/types.ts` (client-safe, the chrome/learn split):

  ```ts
  interface ValidatorRow {
    valoper: string;
    moniker: string | null;        // x/staking read failed or not found
    eligible: boolean;
    jailed: boolean;
    tombstoned: boolean;
    uptimePercent: string | null;  // null before first capture: "n/a"
    thresholdPercent: string;      // from config performanceThresholdBps
    programDelegation: string | null; // compact HASH; null if read failed
    tenure: string;                // coarse duration since enrolledAtSeconds
  }
  interface ValidatorsData {
    rows: ValidatorRow[] | null;   // null = contract validators read failed
    eligibleCount: number | null;
    setHistory: Envelope<ValidatorSetEpochRow[]> | null;
  }
  ```

- `apps/web/app/validators/validators.server.ts`: `loadValidatorsData(config)`
  with the 4.2 discipline (each read parses or degrades to null, never
  throws): contract `validators()` + `config()`, staking validators +
  principal delegations (join by `valoper`; a missing moniker or delegation
  degrades that FIELD, not the row), `epochSnapshot()`, and
  `/api/v1/validators` over `API_URL`. All BigInt display math through the
  4.2 amount helpers, server-side, so loader data stays serializable.
  Operator economics (`commission*`, `tipEpoch`, `headroom`, `inArrears`)
  are deliberately NOT projected into `ValidatorRow`: the public page never
  renders them (§8.6 splits them to the operator view), so they must not
  cross to the client at all.

### Tranche 3: the page

`routes/validators.tsx` becomes the real page (loader + sections), replacing
the 4.1 stub. Components under `apps/web/app/components/validators/`:

- `set-health.tsx`: the aggregates strip: eligible validators now (live),
  plus the indexed trend/churn summary from `setHistory` (latest row's
  joined/departed and an eligible-count sparkline reusing the 4.2 step-chart
  approach: `--viz-cat-1`, table view offered, distinct cold states for
  "unavailable" vs "no settlements indexed yet"). `<VerifyLink
  target="validators" />` on the strip.
- `set-table.tsx`: the §8.6 consumer table (cards on narrow viewports via
  responsive stacking): moniker (valoper truncated, monospace, as the
  fallback when moniker is null), reliability status as icon + label on the
  console-§11.2 family (eligible → `--status-good`; ineligible or jailed →
  `--status-serious`; tombstoned → `--status-critical`; color never alone),
  uptime vs threshold ("99.21% / 95% required", "n/a" before first capture),
  program delegation (compact HASH), tenure. One plain-language framing
  sentence above the table (§11: explanation is first-class).
- Copy through the `en` catalog, monthly-settlement vocabulary per the 4.2
  register decision ("epoch" only where it names the mechanism, which this
  page does not need).

## 3. Security & invariants (enforced mechanisms with gating tests)

1. **Never lie about state** (SECURITY.md, §12.1). *Gate:*
   `apps/web/test/validators-data.test.ts` (MSW): pristine fixtures → rows
   populated with fixture golden values; contract `validators()` failure →
   `rows: null` and the page renders the unavailable state (e2e); a failed
   staking read degrades only moniker/delegation fields; `uptimeBps: null`
   renders "n/a", never a number; API failure or off-shape/over-cap payload
   → `setHistory: null`, distinct from the empty-history cold state.
2. **No operator economics on the public surface** (§8.6 split). *Gate:*
   same suite asserts the serialized `ValidatorRow` keys are exactly the
   closed public set (no `commission*`, `tipEpoch`, `headroom`, `inArrears`
   key ever crosses to the client).
3. **Input bounding at the boundary** (SECURITY.md): the new endpoint bounded
   by `paginationSchema` (services/api contract tests); web-side responses
   through the zod row schema (`satisfies`-pinned); LCD responses through
   chain-client parsers; amounts BigInt-only via the 4.2 helpers (already
   golden-gated).
4. **Verify links environment-locked** (§12.2): only the existing closed-map
   `validators` target; standing `test/verify-link.test.ts` plus an e2e
   assertion on the page's verify hrefs.
5. **Standing gates:** axe (route already listed, both themes; the table
   needs proper `<th>` semantics and the sparkline a table alternative),
   i18n coverage for all new copy, palette/brand-token validation for the
   status usages.
6. **No PII:** validator monikers/addresses are public chain data; nothing
   address-keyed is stored or counted.

## 6. Open questions

1. **`ValidatorSetEpochRow` field set:** `joined`/`departed` per epoch assume
   PR #9's registry keeps enrollment and departure marks queryable per epoch
   boundary. If the 3.1 implementer finds departures are only
   forward-deterministic marks (not per-epoch counts), the churn fields
   become nullable in a spec-noted amendment. Frozen nullable-free here on
   the strength of #9's design notes; confirm against its merged schema.
2. **Program delegation source:** proposal reads the vault principal's
   delegations live (one LCD call, fixture-covered). Alternative (indexed
   per-epoch delegation from `validator_epochs`) is richer but belongs to
   3.1; the live read is honest and current, which the proof framing wants.
3. **Sparkline vs full chart for the eligible-count trend:** proposal ships
   the small step-chart variant with a table toggle (dataviz method
   compliance) rather than a full §8.5-style chart; 4.4 owns the big history
   views. Reviewer confirms the smaller form is enough for §8.6.
4. **Jail reports on the public page:** `jailReports()` exists, but §8.6
   public copy names eligibility/uptime/delegation/tenure only, and jailed
   state already shows as status. Proposal: no separate jail-report list
   here (the incident feed on Learn carries `jail_report` incidents once
   3.1 lands); reviewer confirms.

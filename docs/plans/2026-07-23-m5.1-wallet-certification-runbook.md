# M5.1 — §14.1 wallet certification runbook (Figure + Arculus, devnet)

**Status:** RUNBOOK (PR 5.1 acceptance gate; plan
[`app-m5-wallet-flows`](2026-07-23-app-m5-wallet-flows.md) §3/§7 Q2).
Results recorded per vendor below are transcribed into
[`app-spec.md`](../specs/app-spec.md) §14.1 in the same change that merges
Tranche A.
**Who runs it:** a human with the real wallets (Figure mobile app, Figure
browser extension, Arculus card + app) against the devnet stack. The
automatable parts already run in CI (noted per item); this runbook covers
what only a real vendor wallet can prove.

## Scope and staging

§14.1 items (a)–(e) run against **both v1 vendors**. Tranche A lands as one
GitHub PR (plan §5), so the gate reads:

- **(a)–(c)** — pairing, Provenance chain support, arbitrary-nonce signing —
  certifiable at the **5.1 commit** (the session flow is the test surface).
- **(d)–(e)** — §10.2 message signing with intact decoded preview, §10.3
  flow rules over a drill cycle — certifiable only after the **5.2 commit**
  (the lifecycle machinery is the test surface). The merged PR carries all
  five; either vendor failing any item blocks the merge and reopens §14.1
  (mechanism (iii)).

Vendor-transport matrix (App surface): Figure = WC v2 mobile **and**
injected extension; Arculus = WC v2 mobile only. A vendor certifies on every
transport it supports — five checklist columns total: figure-wc, figure-ext,
arculus-wc for (a)–(c), plus (d)–(e) on each once 5.2 lands.

## Setup

1. Full devnet stack: `infra/devnet/stack.sh up` (app profile). The web tier
   needs, additionally to its stack defaults:
   - `WALLETCONNECT_PROJECT_ID` — a real WC cloud project id (client-safe;
     §7). Without it the WC transport renders "not configured" and only
     figure-ext items can run.
   - `DATABASE_URL` — the `app_writer` URL (stack Postgres, port 5433);
     apply the app migration first:
     `./dev pnpm --filter @nvhash/web run migrate:deploy`.
   - The phone running Figure/Arculus must reach the web tier's origin
     (LAN IP or tunnel) — the pairing QR encodes a relay URI, but the
     session cookie flow runs against the web origin in the phone's browser
     only if testing mobile-web; for desktop-web + mobile-wallet pairing the
     desktop browser holds the session and only the WC relay crosses devices.
2. Fund the test accounts used for (d)/(e) from the devnet faucet accounts
   (`contracts/drills/` conventions). Devnet keys are throwaway
   (SECURITY.md); never a real-network key.

## Checklist — run per vendor column, record PASS/FAIL + notes

### (a) Pairing / connection over the supported transport

- figure-wc / arculus-wc: Connect wallet → vendor → QR renders → scan with
  the vendor app → approval lands, header shows the truncated address.
  *Verify:* one session per tab; disconnect from the wallet side is
  reflected on the next action (no zombie connected state).
- figure-ext: Connect wallet → Figure (extension) → extension prompt →
  approval lands. *Verify:* the adapter probe found the injected provider
  (`app/wallet/figure-extension.ts` — if the probe surface diverges from the
  real extension, fix THAT module only and note it in the §14.1 record).

### (b) Provenance chain support

- The approved WC session's namespace contains `cosmos:<devnet chain id>`
  with an account (CAIP-10); `cosmos_getAccounts` returns the address with
  a usable secp256k1 pubkey (33-byte, base64 or hex — the adapter
  normalizes; note WHICH encoding the vendor emits).
- Chain id, bech32 `tp` prefix, coin type 505, nhash denom accepted by the
  wallet (custom chain config in the vendor app where not native — record
  the exact config needed).

### (c) Arbitrary-nonce signing (§3 decision 5 session auth)

- The login prompt appears in the wallet showing the challenge text
  (`nvHASH session login / chain: … / nonce: …`) — record how the vendor
  renders it (text vs raw bytes).
- Approval completes the session: the header flips to connected, `/portfolio`
  shows the connected-address line, and the cookie is HttpOnly (DevTools:
  `document.cookie` does not contain `nvhash_session`).
- Decline in the wallet: the UI shows the "declined or failed" state and no
  session exists. *CI-covered baseline:* signature/nonce verification, replay
  → 401, cookie flags (`test/session.test.ts`) — the manual run proves the
  VENDOR produces a verifiable ADR-36 signature over the standard
  `cosmos_signAmino` method (for Arculus this is the §14.1 re-confirmation
  of the firsthand-verified capability, now over WC v2 namespaces).

### (d) §10.2 message set with decoded preview — AFTER the 5.2 commit

- Stake and redeem sign flows: the wallet displays the vault
  `MsgSwapInRequest`/`MsgSwapOutRequest` (record: decoded, or raw JSON?);
  the App's confirm step showed the exact JSON before the wallet did; the
  broadcast relay accepts the signed tx and it lands on devnet.

### (e) §10.3 flow rules over a full drill cycle — AFTER the 5.2 commit

- Against `contracts/drills/p2p-drill.sh` history: SwapIn preview rate
  labeling, SwapOut three-timing-facts confirmation, tracker states through
  expedite and maturity. (The e2e-live suite automates the assertions; this
  manual pass is the vendor-in-the-loop confirmation.)

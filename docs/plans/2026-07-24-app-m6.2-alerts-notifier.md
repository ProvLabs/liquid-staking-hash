## 1. Origin & problem statement

Master plan §2 M6.2: "Alert rules + in-app notifications + notifier worker:
rule CRUD, evaluation on indexer ticks, `notifications` log, bell UI.
Default-on rules per spec R2 (redemption matured/expedited; operator
arrears)." Dependencies 5.1 (sessions) and 2.5 (reconciler/incidents) are

- **Hook sites on record:** the 5.4 exit tracker recorded the default-on
  subscription deferral (app-spec §8.4 revision note); the 6.1 Portfolio
  recorded "alert settings are a recorded 6.2 deferral, not an empty shell"
  (app-spec §8.2 revision note).
- **What does not exist** (grep-verified): any `alert_rules`/`notifications`
  table, any internal route, any notifier code, any `/alerts/*` web route,
  any `mintInternalAssertion`.

Constraints that shape the design:

1. **ADR-001 Decision 3 is fixed:** the notifier is a worker entrypoint in
   `apps/web` sharing the web tier's models layer; it reads indexed facts
   **only** through `internal:notifier`-scoped `services/api` endpoints (its
   DB credential has no `indexed` grants to carve exceptions from), and the
   `internal:notifier` scope never grants personal reads.
2. **Data minimization is structural, not aspirational** (`SECURITY.md`).
   Adding `app`-schema tables is the design-review event the allowlist gate
   exists for; this plan is that review. Rules and notifications must not
   accumulate for addresses that can never see them, and stored payloads
   carry no amounts.
3. **Exactly-once is a mechanism, not a hope.** The indexer replays and the
   worker restarts; duplicate notifications would be a trust bug on the
   most personal surface in the App.

## 2. Mechanism

### 2.1 `app`-schema tables (three new model files, `apps/web/prisma/`)

`alert_rules.prisma` — **preference overrides, not subscription rows:**

```prisma
model AlertRule {
  address   String
  kind      AlertKind
  enabled   Boolean
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@id([address, kind])
  @@map("alert_rules")
  @@schema("app")
}

enum AlertKind {
  nav_step_posted
  redemption_update        // matured | expedited | refunded (one settings row)
  vault_status             // paused | halted
  validator_set_incident
  operator_arrears
  @@schema("app")
}
```

**Absence-means-default semantics (the core simplification):** no row means
"the kind's default" — ON for `redemption_update` and `operator_arrears`
(the R2 set), OFF for the rest. A row is only ever an explicit override:
`enabled=false` is the opt-out (§10.3 "opt-out, not opt-in"),
`enabled=true` an opt-in. A user who never touches settings has zero rows —
data minimization by construction. There is **no params column**: of the
§8.2 kinds only market-spread is parameterized (X bps), and that kind is
**deferred with §14.4** (no market data exists in v1; recorded in §6 —
adding it later is an enum migration + allowlist review + `thresholdBps`
column, a spec-recorded amendment, not a config toggle).

`notifications.prisma`:

```prisma
model Notification {
  id          BigInt    @id @default(autoincrement())
  address     String
  kind        AlertKind          // NOT a rule FK: default-on kinds have no rule row
  dedupeKey   String             // replay-stable event identity (§2.4)
  payload     Json               // closed per-kind zod shape; identifiers only, NEVER amounts
  deliveredAt DateTime  @default(now())
  readAt      DateTime?

  @@unique([address, kind, dedupeKey])   // THE exactly-once mechanism
  @@index([address, readAt])             // bell unread count
  @@index([deliveredAt])                 // retention sweep
  @@map("notifications")
  @@schema("app")
}
```

- **Payload minimalism is enforced, not stylistic:** each kind has a closed
  zod shape carrying only identifiers/ordinals — `{ epoch_index }`,
  `{ request_id, event: "matured" | "expedited" | "refunded" }`,
  `{ incident_kind }`, `{ valoper, epoch_index }` — plus nothing else. No
  amounts: a stored amount goes stale and violates §12.1 (the linked surface
  shows live/indexed amounts with freshness labels), and the rule makes the
  6.3 push payload a strict subset of an already-minimal shape. In-app copy
  is rendered at read time from the payload keys + i18n.
- **No `channel` column** — a recorded deviation from §9.1's parenthetical
  column list (`rule; address; channel; payload; delivered_at; read_at`):
  in-app is the always-on channel, so the row's creation *is* the in-app
  delivery and `deliveredAt` records it. Channel-specific delivery state
  belongs to the channel that needs it (6.3's push machinery keys off
  `notifications.id` with its own bookkeeping). Amended into §9.1 in the
  same change (§6).

`notifier_checkpoints.prisma`:

```prisma
model NotifierCheckpoint {
  stream    String   @id      // "nav_step" | "redemptions" | "incidents" | "arrears"
  cursor    String            // per-stream monotonic value, decimal-serialized
  updatedAt DateTime @updatedAt

  @@map("notifier_checkpoints")
  @@schema("app")
}
```

The cursor is an **efficiency device, never the correctness mechanism**:
streams cursor on different monotonic values (height, incident id, epoch
index), each stream zod-parses its own cursor on read, and a garbage or
stale cursor merely re-scans — the `notifications` unique constraint absorbs
the duplicates. After a full indexer rebuild the incidents id-cursor may
overshoot; the bounded re-scan + dedupe-key identity (never autoincrement
ids, §2.4) is the honest answer, stated here rather than papered over.

**Allowlist amendment (the design-review record):**
`test/app-schema-allowlist.test.ts` extends by exactly:
`AlertRule: [address, kind, enabled, createdAt, updatedAt]`,
`Notification: [id, address, kind, dedupeKey, payload, deliveredAt, readAt]`,
`NotifierCheckpoint: [stream, cursor, updatedAt]`. Every column is public
chain data (`address`, `kind` targets), a closed enum, a preference bit, or
minimal operational metadata — nothing identity-, device-, or IP-shaped.
Any column beyond this list is a stop-and-ask event (§8).

### 2.2 Default-on evaluation population

**Population = addresses with app presence (`address_activity` rows), never
"all indexed addresses."** An in-app notification can only ever be seen by
an address that has opened the App and established a session;
`address_activity` (the accepted first/last-seen exception) is exactly that
marker, and it is `app`-schema-local — the notifier reads it through the
models layer, no API hop, no new grant. Generating rows for pure on-chain
users would accumulate dead personal-adjacent data, the precise thing
`SECURITY.md` minimization forbids. Consequence stated honestly: a holder's
first-ever login shows notifications only for events after that first
presence (the sweep starts at their `firstSeenAt`-era cursor state); they
could never have seen earlier ones anyway.

Per kind:

- `redemption_update` (default-on): for each terminal transition fact,
  notify `owner` iff `owner ∈ address_activity` and no
  `(owner, redemption_update, enabled=false)` row.
- `operator_arrears` (default-on): arrears facts carry the `operator`
  account from `validator_registry`; same presence + no-opt-out filter
  (§8.6 "on by default for operator sessions").
- `nav_step_posted`, `vault_status`, `validator_set_incident` (default-off):
  fan out to `SELECT address FROM alert_rules WHERE kind = ? AND enabled`.

The **effective-settings merge** (closed kind list × override rows ×
`DEFAULT_ON = {redemption_update, operator_arrears}`) is one pure function
in `app/lib/services/alerts.server.ts`, shared by the settings UI and the
notifier, unit-gated.

### 2.3 Internal read surface (`services/api`, commit A)

NAV steps need no new route (the public `/api/v1/epochs` already serves
epoch snapshots). Public surfaces do **not** suffice for the rest: public
incidents deliberately omit the dedupe identity, owner-keyed redemption
transitions have no public surface, and operator economics are excluded
from public `/validators`. Three new registry routes, all `GET`,
`auth: "internal:notifier"`, enveloped, zod-bounded — registry membership
auto-attaches the envelope/read-only/query-bounds/rate-limit harnesses:

| Route | Query (zod) | `data` rows |
| --- | --- | --- |
| `/api/v1/internal/alert-facts/redemptions` | `since_height` int ≥ 0 default 0; `limit` 1–500 default 200 | `{ request_id, owner, status, enqueued_at, expedited_at, matured_at, refunded_at, last_height }` from `redemption_requests` where `lastHeight > since_height`, ordered `lastHeight` asc |
| `/api/v1/internal/alert-facts/incidents` | `since_id` int ≥ 0 default 0; `limit` 1–500 default 200 | `{ id, kind, severity, dedupe_key, opened_at, opened_height }` where `id > since_id`, id asc — **no payload passthrough** (minimal response; the notifier needs identity, not detail) |
| `/api/v1/internal/alert-facts/arrears` | none | for the latest `epochIndex` in `validator_epochs`: `{ valoper, operator, epoch_index, commission_due }` where `commissionDue > 0`, joined to `validator_registry` rows with `unregisteredAt` null |

- `IndexedReader` port additions (`src/reader.ts` + `reader-prisma.ts` +
  the honest-empty reader + `test/reader-fake.ts`):
  `redemptionsChangedSince(height, limit)`, `incidentsSince(id, limit)`,
  `latestArrears()`. Row shapes frozen in `@nvhash/api-types`
  (`AlertRedemptionFact`, `AlertIncidentFact`, `AlertArrearsFact`);
  amounts as decimal strings at the boundary, per `derive.ts` convention.
- **Cross-address gate extends registry-driven:** `test/cross-address.test.ts`
  derives `INTERNAL_PATHS` from the registry
  (`routes.filter(r => r.auth === "internal:notifier")`) and asserts the
  full matrix: no credential → 401; `address:` scope on an internal path →
  403; `internal:notifier` on an internal path → 200; the standing
  `internal:notifier`-on-personal-path → 403 cases unchanged. Future
  internal routes join the matrix automatically.
- **Minting side:** `assertion.server.ts` gains
  `mintInternalAssertion(key, nowSeconds)` (scope literal
  `"internal:notifier"`, same 60 s lifetime and field order), with a new
  golden vector cross-pinned in **both** assertion test files (the standing
  drift mechanism).
- **Cross-lane touch (indexer-owned, index-only):** `redemption_requests`
  gains `@@index([lastHeight])` via an indexer migration on this branch
  (rebuildable, no allowlist impact; §7 Q6 confirms the ride-along).

### 2.4 Idempotent delivery

Two layers; correctness never rests on the cursor:

1. **Unique constraint** `(address, kind, dedupeKey)`; every tick inserts
   with `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`).
2. **Per-stream cursor** advanced in the **same `app`-schema transaction**
   as the insert batch. Crash before commit → cursor unmoved → re-fetch →
   duplicates skipped. Crash after → nothing lost.

Dedupe keys are **replay-stable chain/indexed identities, never
autoincrement ids** where avoidable:

| Kind | dedupeKey | Stability argument |
| --- | --- | --- |
| `nav_step_posted` | `epoch:<epoch_index>` | chain-canonical ordinal |
| `redemption_update` | `req:<request_id>:<event>` | request id + which terminal leg; a request that matures then refunds correctly produces two notifications |
| `vault_status`, `validator_set_incident` | `incident:<kind>:<dedupe_key>` | the indexer's own `@@unique([kind, dedupeKey])` pair — stable across drop-and-rebuild, unlike `incidents.id` |
| `operator_arrears` | `arrears:<valoper>:<epoch_index>` | one alert per validator per epoch in arrears |

**Incident→kind mapping (closed table in the notifier):**
`vault_status` ← `{vault_paused, contract_halted}`;
`validator_set_incident` ← `{jail_report, slash_write_down}`;
`reconciler_divergence` / `indexer_lag` / `epoch_overdue` /
`redemption_refund` excluded (ops-facing, or covered per-owner by
`redemption_update`). `vault_paused` and `jail_report` are 2.5 fast-follow
reconciler kinds without producers yet — the mapping is ready and simply
starts firing when they land. No close/"resumed" notifications in v1
(§7 Q3).

### 2.5 Notifier worker (`apps/web/notifier/`, commit B)

- **Entrypoint** `apps/web/notifier/index.ts` — outside `app/` so the React
  Router build never bundles it; package script `"notifier"`. It shares the
  models layer per ADR-001 Decision 3; the **only new Prisma import site**
  is `app/lib/models/alerts.server.ts`: an `AlertStore` port (rules
  upsert/list, notifications list/count/markRead/insertMany-skipDuplicates,
  checkpoint get/set) with Prisma and in-memory implementations — the
  `session.server.ts` split, so routes and tests run storeless.
- **Config** (zod-bounded; `.env.example` placeholders only): `DATABASE_URL`
  (app_writer; **required, fail-fast** — a notifier without its store is
  pointless), `API_SERVICE_ASSERTION_KEY` (≥ 32 chars, required),
  `API_BASE_URL`, `NOTIFIER_TICK_SECONDS` (default 60, bounded 10–600),
  `NOTIFIER_FACT_LIMIT` (default 200, ≤ 500).
- **Tick loop** (indexer `runtime/worker.ts` discipline; injectable
  clock/sleep/fetch so one pass is unit-testable): per stream — mint a fresh
  internal assertion → fetch one bounded fact page → evaluate (pure core:
  facts × effective settings × presence → candidates with dedupe keys) →
  `insertMany(skipDuplicates)` + cursor advance in one transaction. Network
  I/O never inside a DB transaction (the indexer's two-phase rule).
- **Failure behavior:** per-stream try/catch — one failing stream never
  blocks the others; API down/timeout → structured log, cursor unmoved,
  retry next tick (no crash loop; no backoff machinery needed at 1-minute
  cadence); stale indexer → facts simply stop advancing (observable via
  envelope heights); the notifier never fabricates. Boot misconfig → loud
  exit. Logs carry no IP/device data beside addresses (standing scrub rule).
- **Retention sweep** rides the tick (bounded batch): delete notifications
  read > 90 days ago, and any > 180 days old (proposal values, §7 Q4) —
  minimization applied to our own table.

### 2.6 Web surfaces (commit C)

Resource routes **outside** the `:lang?` segment (the `tx-*` /
`portfolio-export` precedent), all `requireSession`, acting address only
ever the session address:

- `app/routes/alerts-notifications.tsx` — `GET
  /alerts/notifications?page=` (session address's rows, newest first,
  zod-bounded page) and `POST` mark-read, body zod-bounded
  `{ ids: string[] } | { all: true }` (≤ 100 ids; the UPDATE is scoped
  `WHERE address = session.address AND id IN (...)` — mark-read can never
  cross addresses).
- `app/routes/alerts-rules.tsx` — `GET /alerts/rules` (effective settings:
  closed kind list × effective enabled × is-default flag) and `POST` upsert
  `{ kind, enabled }` (zod enum mirroring `AlertKind`; unknown kind → 400).

**Bell** (`chrome/alerts-bell.tsx`): the anonymous branch keeps the advert
verbatim (§8.0). The session branch renders the bell + unread badge; the
count rides the existing `root.tsx` loader (add `countUnread(address)`
beside `getSessionContext` — only the integer crosses to the client).
Opening the popover fetches `/alerts/notifications` and posts mark-read;
each item deep-links to its surface (`/portfolio`, `/exit`; validator-set
items link to `/validators` until 6.4 ships `/validators/mine`, recorded as
a 6.4 hand-off).

**Alert settings** (`app/components/portfolio/alert-settings.tsx`): joins
the Portfolio page, fulfilling the recorded 6.1 deferral — one toggle per
kind in the closed list, default-on kinds annotated "on by default";
`operator_arrears` shown only when the session's roles report operator
(the 5.1 role read; UI convenience only — the notifier's server-side
operator filter is the mechanism). The market-spread row is **absent**
(deferred with §14.4), not an empty shell. Toggles post to `/alerts/rules`.

**The 5.4 exit-tracker hook resolves to copy, not a mutation:** under
absence-means-default, the §8.4 "subscribes by default" needs no write at
SwapOut time — the owner is covered the moment the redemption exists. The
tracker adds one sentence ("You'll be alerted here when this matures or is
expedited — manage in alert settings") linking to the settings section,
closing the recorded deferral. **Payout-timing copy** in redemption
notifications and settings descriptions uses §14.12 framing: the 60-day
guarantee is the promise position; "typical" language appears only where
the sample-sufficient statistic already does. No new statistics are
computed here.

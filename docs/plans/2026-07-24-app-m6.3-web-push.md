## 1. Origin & problem statement

Master plan §2 M6.3: "Web Push channel (§10.4, decision §14.7 recorded):
per-browser opt-in, opaque revocable endpoint tokens, minimal payloads,
deletion on opt-out/session delete." The single dependency is 6.2 (merged
before this starts). §14.7 is DECIDED: Web Push is the one external channel,
accepted because per-browser opt-in + available opt-out + opaque revocable
token handling keep it inside the `SECURITY.md` data-minimization posture.
Email is excluded and is not an option.

What already exists on `main` once 6.2 lands (this plan builds on it):

- **The 6.2 machinery:** `notifications` rows as the delivery log (in-app
  delivery = row creation; channel state deliberately left to the channel —
  the recorded no-`channel`-column deviation), the notifier tick loop
  (`apps/web/notifier/index.ts`, per-stream try/catch, injectable deps),
  the `AlertStore` port (`app/lib/models/alerts.server.ts`), the alert
  settings section on Portfolio, and the live bell.
- **Session machinery** (5.1): `requireSession`, the sessions table and its
  logout/expiry paths — the lifecycle push subscriptions must be chained to.
- **Config plumbing:** `apps/web/app/config/config.server.ts` documents
  `WEB_PUSH_VAPID_*` as "documented-but-unconsumed until PR 6.3" — this PR
  consumes them. `check:bundle` classifies client-safe vars (§7 config
  table).
- **What does not exist** (grep-verified): any `push_subscriptions` table,
  service worker, `web-push` dependency, or push UI.

Constraints that shape the design:

1. **The SECURITY.md exception is narrow and literal.** Opt-in only; the
   token is opaque (the App attaches no identity to it and derives nothing
   from it); revocable; **deleted on opt-out and on session deletion**.
   Deletion is a mechanism with a standing CI gate from this PR on (master
   plan §4 names it) — not a cleanup habit.
2. **Payload minimalism is inherited and tightened.** 6.2 already stores
   identifier-only payloads; the push payload is a strict subset — kind +
   deep link, no amounts, nothing personal beyond what the push service
   must carry (§10.4: "event + link into the App, no amounts").
3. **Push is additive latency, never load-bearing.** Every alert kind has
   an in-app rendering; a user without push loses nothing but latency
   (§10.4). Push delivery failure therefore degrades silently to the in-app
   surface — logged, never fabricated, never blocking the tick.

## 2. Mechanism

### 2.1 `push_subscriptions` (`app`-schema, one new model file)

```prisma
model PushSubscription {
  id         BigInt   @id @default(autoincrement())
  address    String            // recipient scoping (public by nature)
  sessionId  String            // the creating session — the deletion chain
  endpoint   String   @unique  // the push service URL: THE opaque token
  p256dh     String            // subscription encryption material (opaque)
  auth       String            // subscription auth secret (opaque)
  createdAt  DateTime @default(now())

  @@index([address])
  @@index([sessionId])
  @@map("push_subscriptions")
  @@schema("app")
}
```

- The row is exactly the W3C `PushSubscription.toJSON()` triple plus the
  scoping/lifecycle keys. `endpoint`/`p256dh`/`auth` are opaque browser- and
  push-service-generated material: the App never derives anything from them
  and never logs them (endpoint URLs can fingerprint the browser vendor —
  they stay out of logs entirely, treated as secrets-adjacent).
- **Created only on explicit opt-in** (a user gesture in the settings UI →
  browser permission prompt → `pushManager.subscribe` → POST). Never
  auto-created, never re-created silently after deletion.
- **Deleted on:** opt-out (user toggles push off → unsubscribe + DELETE);
  logout (`session-logout` cascade by `sessionId`); session expiry/deletion
  sweep (same cascade); push-service `404`/`410` responses (dead-endpoint
  pruning at send time); and browser-side resubscription churn (a new
  endpoint for the same session replaces, not accumulates).
- **Allowlist amendment** (the design-review record):
  `PushSubscription: [id, address, sessionId, endpoint, p256dh, auth,
  createdAt]` joins `test/app-schema-allowlist.test.ts`. Justification:
  `address`/`sessionId` are the existing public/scoping identifiers; the
  triple is the accepted-exception token material itself; `createdAt` is
  minimal operational metadata. Nothing else may join (no user-agent, no
  device labels, no delivery counters keyed to the row).

### 2.2 Opt-in UI + service worker (commit A)

- **Service worker** `apps/web/public/push-sw.js` (static, framework-free,
  no bundler involvement — auditable as one small file): `push` event →
  `showNotification(title, { body, data: { url } })` rendered from the
  minimal payload + `notificationclick` → focus-or-open the deep link.
  It performs no fetches, caches nothing, and holds no keys.
- **Settings UI:** a per-browser "Push notifications on this device" block
  joins the 6.2 alert-settings section (`components/portfolio/
  alert-settings.tsx`). Browser permission states render honestly:
  `unsupported` (no Push API), `denied` (blocked at the browser — say so
  and point at browser settings; never a silent no-op), `prompt`
  (enable button), `granted+subscribed` (disable button). Per-browser is
  stated in the copy: enabling here enables this browser only.
- **Subscription management resource route**
  `app/routes/push-subscription.tsx` (outside `:lang?`, the `alerts-*`
  precedent), `requireSession`: `POST` body = zod-bounded
  `{ endpoint: httpsUrl ≤ 1024, keys: { p256dh: base64url ≤ 256,
  auth: base64url ≤ 128 } }` → upsert scoped to the session
  (replace-by-session semantics); `DELETE` → remove the session's
  subscription(s). The acting address/session is never a body field.
- **Config:** `WEB_PUSH_VAPID_PUBLIC_KEY` joins the client-safe allowlist
  (§7 config table amendment — a VAPID public key is public by
  construction, it ships in `pushManager.subscribe`);
  `WEB_PUSH_VAPID_PRIVATE_KEY` and `WEB_PUSH_VAPID_SUBJECT` stay
  server-only (`check:bundle` classifies all three). Absent config →
  the push block renders an honest "not configured for this environment"
  state (devnet default) and no subscribe path exists.

### 2.3 Notifier fan-out (commit B)

After 6.2's evaluation transaction commits (notifications inserted), the
tick's delivery phase — outside any DB transaction, per the two-phase rule —
sends each **newly inserted** notification to each of the recipient
address's subscriptions:

- Payload (strict subset of the stored §6.2-shaped payload):
  `{ kind, url }` where `url` is the in-app deep link (the bell's §2.6
  mapping). **No amounts, no addresses, no request ids** in the push body —
  the push service is a third party; it carries the minimum to say "open
  the App here". Title/body strings are generic per-kind i18n copy
  ("A redemption update is waiting in your portfolio").
- Delivery via the `web-push` npm package (VAPID signing +
  `aes128gcm` encryption). **This is the milestone's single new
  dependency** — a reviewed-dependency event per `SECURITY.md` supply
  chain: first-party-maintained (web-push-libs), no install scripts,
  pinned in the lockfile. No other dependency may ride along.
- Failure handling: `404`/`410` → delete the subscription row (dead
  endpoint pruning — the revocability mechanism working in reverse);
  timeouts/5xx → log (endpoint scrubbed) and drop — **no retry queue in
  v1** (in-app delivery is the guaranteed channel; push is latency sugar,
  §10.4). Fan-out failures never fail the tick.
- Fan-out state: "newly inserted" is the set returned by 6.2's
  `insertMany` step in the same tick — no `pushed_at` bookkeeping column
  on `notifications` (a crash between insert and fan-out loses only the
  push nudge, never the notification; the in-app surface has it). This
  keeps 6.2's table untouched and is recorded as the deliberate
  at-most-once push posture (§7 Q2).

### 2.4 Session-lifecycle deletion (commit B)

The deletion chain is wired at every session-removal site (5.1's logout
route and the expiry/deletion path in `session.server.ts`): removing a
session removes its `push_subscriptions` rows in the same transaction.
Data deletion on request (§12.3) already removes the user's rows — the new
table joins that enumeration.

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **Push-token deletion on opt-out AND session delete** — the SECURITY.md
   exception's condition, now a **standing CI gate** in `apps/web` from
   this PR on (master plan §4 forecast fulfilled). *Gate:*
   `test/push-token-deletion.test.ts` (new, standing).
2. **Opt-in-only creation.** No subscription row without an authenticated
   user gesture; session-scoped; replace-not-accumulate. *Gates:*
   `test/push-subscription.test.ts`; the settings e2e (no auto-subscribe
   path exists to test — asserted by route coverage).
3. **Payload minimalism to a third party.** Push bodies are `{ kind, url }`
   only — no amounts, no addresses, no identifiers beyond the kind.
   *Gate:* `test/push-payload.test.ts` (new, standing).
4. **All inputs validated and bounded at entry.** Subscription body
   zod-bounded (https-only endpoint, length caps, base64url keys); VAPID
   config all-or-none at boot. *Gates:* `test/push-subscription.test.ts`,
   config unit case.
5. **Key split.** VAPID public key is an explicit client-safe allowlist
   amendment; private key/subject never reach the bundle; the service
   worker holds no keys. *Gate:* `check:bundle` with the three vars
   classified.
6. **`app`-schema data minimization.** Exactly the §2.1 columns; endpoint/
   key material treated as opaque and kept out of logs. *Gates:* extended
   `test/app-schema-allowlist.test.ts`; the log-scrub assertion in the
   fan-out tests.
7. **Push is never load-bearing; failures never lie.** Fan-out errors
   drop to in-app-only with a scrubbed log line; dead endpoints prune;
   denied browser permission renders as denied. *Gates:*
   `test/notifier.test.ts` fan-out cases; the e2e permission-state
   assertions.
8. **No new attack surface on the API.** `services/api` is untouched by
   this milestone. *Gate:* no diff under `services/` (reviewer checklist).
9. **Dependency discipline.** `web-push` is the single named addition,
   lockfile-pinned. *Gate:* reviewer checklist against the lockfile diff;
   no other `package.json` delta.
10. **Standing gates continue:** the 6.2 suites (payload, notifier,
    allowlist, session scope), axe both themes on the settings block,
    i18n coverage, `check:bundle`.

## 7. Open questions

1. **VAPID key provisioning (Ira).** Which environments get real keys —
   proposal: devnet none (the honest "not configured" state), testnet +
   mainnet each their own pair, generated at deploy time and held as
   environment secrets (never in the repo; `.env.example` placeholders
   only). Confirm the per-environment posture.
2. **At-most-once push (no `pushed_at`, no retry queue).** Ratify §2.3's
   posture: a crash between insert and fan-out drops only the push nudge;
   in-app delivery is the guarantee. The alternative (delivery bookkeeping
   per subscription) adds a table and a retry loop for latency sugar.
3. **Live-lane coverage.** Real browser push is not exercisable in CI
   (permission prompts + third-party push services). Proposal: unit/fake
   transport coverage only, with the e2e-live lane explicitly not covering
   push and saying so in the spec note. Confirm, or scope a push-service
   stand-in for the devnet stack as a follow-on.
4. **Per-address subscription cap.** Proposal: cap active subscriptions
   per address (e.g. 5, oldest evicted) so a hostile client cannot grow
   the table through repeated re-subscription. Cheap and bounded — include
   unless there is a reason not to.

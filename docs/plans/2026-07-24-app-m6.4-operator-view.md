Constraints that shape the design:

1. **The §14.11 operator CSV needs per-payment facts the indexer does not
   hold.** The decided columns (`datetime_utc`, `block_height`,
   `epoch_index`, `payment_type`, `hash_amount`, `txhash`) are
   per-*payment* rows; `validator_epochs` carries only per-epoch cumulative
   totals with no txhash. Commit A therefore adds a small indexer
   capability: decode `PayCommission`/`PayTip` execute events into a new
   `indexed.operator_payments` table (public chain data; the indexer's
   schema-allowlist lint extends deliberately — a design-review event this
   plan is the review for).
2. **The broadcast relay's allowlist is the security boundary.** The
   operator actions ride `/cosmwasm.wasm.v1.MsgExecuteContract`; a bare
   typeUrl addition would open the relay to **arbitrary contract calls**.
   The extension must be a deep guard (§2.5), not a list entry.
3. **Privileged writes keep the Console's confirmation rigor** (§17.1,
   §10.2): graduating these flows to the consumer surface must not soften
   the preview/decoded-payload/danger-tier contract. The contract remains
   the enforcement boundary; UI preflight is convenience only.

## 2. Mechanism

### 2.1 Indexer: `operator_payments` (commit A)

New model `services/indexer/prisma/operator_payments.prisma`:

```prisma
model OperatorPayment {
  txhash      String
  msgIndex    Int
  valoper     String
  payer       String                       // bech32, public chain data
  paymentType OperatorPaymentType          // commission | tip
  amount      Decimal  @db.Decimal(39, 0)  // nhash attached to the msg
  epochIndex  BigInt?                      // epoch the payment credited (null if not derivable)
  height      BigInt
  occurredAt  DateTime

  @@id([txhash, msgIndex])
  @@index([valoper, height])
  @@map("operator_payments")
  @@schema("indexed")
}
```

The chain-events worker (2.1's tx-search leg) gains decode coverage for the
`PayCommission`/`PayTip` wasm execute events — same two-phase
collect/write, same checkpoint, idempotent by the `(txhash, msgIndex)`
natural key. **[VERIFY] at commit A start:** capture the pay events'
attribute shapes into the fixtures corpus from a devnet drill (the §14.2
pattern — attribute values are JSON-encoded strings, decoded through
`decode/attributes.ts`); if the contract emits no distinguishing event
attributes for these executes, the fallback is decoding the
`MsgExecuteContract` body + funds from the tx itself, recorded as such.
The indexer schema lint's allowed-fields list extends by exactly the
columns above (all public chain data; `payer` is the tx signer, already
public in the tx).

### 2.2 API: operator endpoints (commit B)

Two new registry routes, `auth: "address"`, joining `PERSONAL_PATHS` (the
standing cross-address gate). **The address→valoper mapping is enforced
server-side:** each handler resolves the asserted address against
`validator_registry.operator` and serves **only** that operator's
valoper(s) — an operator can never read another validator's private view
(the data is public chain data, but the *personal surface* stays
address-scoped like every other personal endpoint; the public projection
remains the 4.3 page).

| Route | Query (zod) | `data` |
| --- | --- | --- |
| `GET /api/v1/operator/summary?address=` | address bech32 (existing schema) | per owned valoper: registry row + latest `validator_epochs` row + peer context (`rank_by_tip`, `eligible_count`, `enrolled_count` for the latest epoch — computed over public rows, no other validator's identity beyond ordinal rank) + lifetime totals (`commission_paid_total`, `tip_paid_total` from `operator_payments`) |
| `GET /api/v1/operator/epochs?address=&valoper=&limit=&offset=` | valoper bech32 (must belong to the address — else 404-empty), pagination bounds (limit ≤ 200) | `validator_epochs` history rows, `epochIndex` desc, amounts as decimal strings |
| `GET /api/v1/operator/payments?address=&valoper=&format=csv` | as above; `format=csv` streams the **complete** history (the 6.1 CSV-completeness precedent — no silent pagination cap on a statement of fact) | payment rows; CSV columns pinned to §14.11: `datetime_utc, block_height, epoch_index, payment_type, hash_amount, txhash` — `csvField` injection guard, `X-*` freshness headers, the 3.3/6.1 CSV conventions |

`IndexedReader` additions: `operatorValopers(address)`,
`validatorEpochsFor(valoper, limit, offset)`, `operatorPaymentsAscFor
(valoper)` (internally chunked), `latestEpochPeerRows()`. Shapes frozen in
`@nvhash/api-types`.

### 2.3 Web read view (commit C)

- **Gate:** `getSessionContext` → anonymous renders the connect prompt;

- **Live plane:** contract `Validators {}` + `Config {}` (thresholds,

  `personalApiHeaders`: the three §2.2 endpoints.
- **Sections** (top to bottom): standing header (moniker, eligibility,
  uptime vs threshold with headroom per threshold, jailed state) with the

  `validators.rs` 2026-07-27, see the commission/TIP asymmetry below): *in
  arrears* (`commission_paid < commission_due`) at the serious/critical
  status tier; *current*; and **prepaid by N** when
  `commission_paid > commission_accrued`. The one-epoch grace state is made
  plain in all three (§8.6: Owen never *discovers* an obligation late; the 6.2
  arrears alert deep-links here); participation economics (current + historical program
  delegation on the shared `StepChart`; commission accrued/paid/due; TIP
  paid vs `rank_by_tip` effect); **net-benefit-after-fees** (labeled
  derivation: staking-commission earnings on program delegation are an
  **estimate** — flagged §7 Q2 — minus commission + TIP paid, each term
  shown); payment history table + "Export CSV" →
  `app/routes/operator-export.tsx` proxy (requireSession →
  `personalApiHeaders` → stream, the `portfolio-export` pattern, outside
  `:lang?`); per-epoch history table. Console verify links on material
  figures (§12.2 map: a validator → Console Validators).
- Every figure "n/a" when null, never 0; charts step-after; the `dataviz`
  skill loads before chart work.

**Commission vs TIP asymmetry (verified against `contracts/src` 2026-07-27,
Ira).** The two payment flows behave differently after an overpayment, and the
view must not imply otherwise:

- **Commission carries forward indefinitely.** `commission_paid` is a
  cumulative LIFETIME total that `epoch_rollover` never resets
  (`validators.rs::epoch_rollover` advances only the grace boundary:
  `commission_due = commission_billed`, `commission_billed =
  commission_accrued`). Eligibility is `commission_paid < commission_due` over
  those cumulative totals, so an overpayment is not "credit for the next
  epoch" — it raises the lifetime paid total and absorbs future accrual for
  however many epochs it takes.
- **TIP does not carry.** `tip_epoch` is zeroed at every rollover — it buys
  priority ranking in the current epoch only. An over-TIP is not refundable
  and not carried; like all payments it sweeps into vault principal, so it
  becomes a donation to NAV.
- **The prepaid credit is invisible in the events.** `pay_commission`'s
  `outstanding` attribute is `commission_accrued.saturating_sub(
  commission_paid)` — SATURATING, so an overpayment reports `0`, never a
  negative. The credit is therefore **derived from the live plane only**:
  `commission_paid − commission_accrued` from `Validators {}`, shown as its own
  labeled figure and never inferred from the indexed payment history (which
  cannot see it). This is a fact of the chain, not an estimate — it carries no
  estimate label, unlike the §7 Q2 net-benefit earnings term.

### 2.4 Operator transaction flows (commit D)

Five flows through the unmodified 5.2 lifecycle (`useTxFlow`; build →
preflight → simulate → confirm → sign/broadcast → track), each a
`MsgExecuteContract` on the staking contract:

| Flow | Execute msg | Funds | Preflight (live-read reasons) | Confirm tier |
| --- | --- | --- | --- | --- |
| Pay commission | `{ pay_commission: { valoper } }` | the payment, nhash | amount > 0 and ≤ spendable-incl-fee; valoper enrolled | warning — restates: non-refundable; overpayment prepays future accrual; sweeps into vault principal next epoch |
| Pay TIP | `{ pay_tip: { valoper } }` | the payment, nhash | as above | warning — restates: credits the **current** epoch only, resets at epoch completion; non-refundable |
| Enroll | `{ register_participation: { valoper } }` | none | caller is the valoper's operator account; validator exists on chain; not already enrolled | warning |
| Unregister | `{ unregister_participation: { valoper } }` | none | caller is operator (or admin); currently enrolled | **serious** — restates: program stake unbonds at the next epoch and is redeployed |
| Purge jailed (two-phase) | `{ report_jailed_validator: { valoper } }` then, after cooldown, `{ purge_jailed_validator: { valoper, claimant_valoper? } }` | none | reported validator actually jailed (live read); purge only after cooldown elapsed; halt-gate state surfaced | serious — the two-phase mechanics (report starts cooldown; purge moves stake; unjailed-in-interim clears the report) stated before signing |

Amount entry reuses `app/lib/amount.ts` (reject-never-clamp, no floats);
`claimant_valoper` defaults to the operator's own eligible valoper when
offered, always editable, always shown in the exact-JSON disclosure.
Preflight is convenience only — every predicate the contract enforces is
re-stated as a reason, never trusted (§12.1). Track lands back on
`/validators/mine` with the updated standing.

### 2.5 Broadcast deep-guard (commit D — the critical mechanism)

`ALLOWED_MSG_TYPE_URLS` gains `/cosmwasm.wasm.v1.MsgExecuteContract`, and
`broadcast.server.ts` gains a **second-level guard that runs for that
typeUrl only**:

1. Decode the `MsgExecuteContract` body; **reject unless
   `msg.contract === config.contractAddress`** (the configured staking
   contract — never any other contract) → else 400.
2. Parse `msg.msg` (the inner execute JSON); **reject unless it is an
   object with exactly one top-level key** ∈ the closed set
   `{ pay_commission, pay_tip, register_participation,
   unregister_participation, report_jailed_validator,
   purge_jailed_validator }` → else 400.
3. Validate the variant body against its zod schema (valoper bech32 with
   the valoper prefix; `claimant_valoper` optional valoper; **no extra
   keys**) → else 400.
4. Funds discipline: `pay_commission`/`pay_tip` require exactly one coin,
   denom `nhash`, amount a bounded positive integer string; **all other
   variants require empty funds** → else 400.

Admin/keeper msgs (`SetHalted`, `ClearPendingDelegations`, `RunEpoch`,
`ClaimRewards`, …) are **not** in the set and must be proven rejected. The
guard is pure and lives beside the allowlist in `app/tx/build.ts` /
`broadcast.server.ts` (one decode site, the 5.2 convention).

*Delivery notes (6.4 commit A, 2026-07-27):*

- **§7 Q1 RESOLVED by drill, not by fallback.** Ran enroll → pay-commission →
  pay-tip against the live devnet (`infra/devnet/actions/`) and captured the
  three txs verbatim into `packages/fixtures/fixtures/operator/`. Two findings
  the plan did not anticipate, both now pinned in `manifest.json`,
  `packages/fixtures/README.md` and app-spec §9.2:
  1. **Contract `wasm` attribute values are NOT JSON-quoted** — the extra
     quoting layer is a *vault module* quirk. `dequote` tolerates both, so no
     decode change was needed; the fact is recorded so nobody "fixes" it.
  2. **`pay_tip` emits no per-payment amount.** Its attributes are
     `action`/`valoper`/`tip_epoch`, and `tip_epoch` is the epoch-CUMULATIVE
     credit (it resets at epoch completion and aggregates across payers), so it
     can never be a payment's own nhash. `pay_commission` does carry `amount`
     (plus `outstanding`).
  Decode therefore reads the **pair**: the wasm event plus the bank `transfer`
  at the same `msg_index` whose recipient is the contract — the msg's attached
  funds, bounded to exactly one coin by the contract's own `must_pay`. That is
  the plan's recorded fallback in substance ("decoding the msg body + funds from
  the tx itself") but taken from the **event plane the worker already reads**,
  so no LCD round-trip per payment was added. Verified against the real
  `tx_search` response, not only the LCD capture: the two planes carry
  identical attribute shapes, and tx-level fee transfers carry no `msg_index`,
  which is what keeps them out of the pairing.
- **Deviation — `epochIndex` is null at ingest.** §2.1 hedged "null if not
  derivable"; it is not derivable in the worker without reading the
  epoch-history worker's `epoch_snapshots`, which would make replay
  order-sensitive and break the convergence property. The column ships as
  specified (nullable) and stays unwritten; commit B derives the §14.11
  `epoch_index` column by joining `epoch_snapshots` at read time (smallest
  `epochIndex` whose `endHeight >= payment.height`; null while the crediting
  epoch is still open). Recorded in the model file, app-spec §9.1 and the
  round-trip gate.
- **Fixtures were a partial capture, and say so.** A full
  `generate-corpus.sh` run would have reset the devnet this milestone is being
  driven against. The three operator fixtures come from a later bootstrap on a
  newer dev-node image than the 2026-07-14 corpus (addresses match only because
  the bootstrap is deterministic) — recorded verbatim in a new
  `manifest.partial_captures` block rather than by back-dating the corpus.
  `capture-fixtures.sh` now captures them in the main flow, so the next full run
  folds them in and the block disappears. No new drill was needed:
  `p2p-drill.sh` already drives all three actions (phases 1, 2, 8) — noted in
  its README and in `generate-corpus.sh`.
- **Schema delta is exactly §2.1** — `OperatorPayment` + the
  `OperatorPaymentType` enum, nothing else. The hand-written migration is
  `prisma migrate diff`-clean against the datamodel and applies cleanly as
  `indexer_writer`.
- **Gates run:** `@nvhash/indexer` typecheck; `test` 95/95 (chain-events decode
  grew 8 → 17 cases: both fixtures, the "wasm event has no amount key" shape
  pin, foreign-contract scoping, multi-msg indexing, and five loud-failure
  cases — missing/duplicate/multi-coin transfer, commission amount mismatch,
  tx-level fee transfer not mistaken for funds); `test:grants` 10/10 including

## 2. Mechanism

### 2.1 Policy discovery is set-valued, never "the admin policy"

`contracts/IMPLEMENTATION-STATUS.md` carries an open item: *"Dual x/group
policies (spec §12.1) [SMALL] — split single `admin` into
`admin_group_policy` and `ops_group_policy`."* Hardcoding one policy would be
exactly the topology assumption `SECURITY.md` forbids, and would need
rewriting when the split lands.

Discovery is a set: `contract.config().admin` (height-pinned) →
`groupPolicyInfo(admin)` → `{groupId}` → `groupPoliciesByGroup(groupId)` ∪
`groupPoliciesByAdmin(groupInfo.admin)`. Re-resolved per window. 1..n policies
are mirrored and `gov_proposals.groupPolicyAddress` already discriminates them,
so the pending split lands with **zero App change**. A plain-account
`Config.admin` — today's devnet, before commit A — yields an **empty set and
empty committed windows**: the honest no-governance state, not a crash.

### 2.2 Indexing is hybrid: events for provenance, state reads for authority

Three strategies were considered:

- **Pure tx-event** cannot work. Voting-period expiry and pruning happen in the
  group module's EndBlocker; `gov_votes` rows would end up the only record of a
  proposal whose own state was already gone.
- **Pure polling sampler** cannot work either, for two independent reasons: the
  existing `GovVote` schema carries `height` and `txhash`, and
  `votes_by_proposal` returns neither; and a sweep that runs after the prune
  window loses the row **permanently** (overview F4). The mirror is the durable
  record — that is its whole justification in app-spec §9.1.
- **Hybrid** is what this plan builds.

Three inputs, merged inside the standard two-phase `Worker` contract
(`collect(window)` = network only, `write(tx, window, batch)` = DB only; cursor
advance via `runWindow`, never written directly):

1. **Tx plane — provenance.** tx-search over `[window.from, window.to]` for
   group-module txs, decoding
   `cosmos.group.v1.Event{SubmitProposal, Vote, Exec, WithdrawProposal}` plus
   the `MsgVote` body for voter and option. Yields
   `{proposalId, kind, voter?, txhash, height, msgIndex}` — the **only** source
   of `txhash`/`height`. Same call shape as `collectCranks` in
   `src/workers/epoch-history/boundaries.ts`.
2. **Block plane — the EndBlocker.** `blockResults(h).finalizeBlockEvents` per
   height, filtered to the group event types commit A proves exist on this
   build. Exactly the mechanism `src/workers/chain-events/sources.ts` already
   uses for payout/refund/NAV. If commit A finds no voting-period-end event on
   this build, this input degrades to prune detection and input 3 carries the
   transition — **both branches are specified so the executor does not
   improvise** (§7 D2b).
> **CORRECTED 2026-07-29 (§3.5 findings 1 and 2): the state plane is not the
> authority for everything.** A proposal that executes SUCCESSFULLY is pruned in
> the same transaction, so `ACCEPTED` + `SUCCESS` is a pair the sweep can never
> observe; and votes are DELETED at the voting-period-end tally, so the sweep
> recovers votes only while a proposal is still open. The tx plane carries both.
> The sweep remains the authority for the status and tally of everything the chain
> still holds, and the sole observer of the eventless voting-period-end
> transition.

3. **State plane — authority, and the non-tx safety net.** Once per window,
   height-pinned at `window.to` via `PinnedLcdClient.getAtHeight`, for each
   discovered policy: `proposals_by_group_policy/{addr}`. Every proposal still
   on chain returns its **current** `status`, `final_tally_result`,
   `executor_result`, `voting_period_end`, `group_version`,
   `group_policy_version`.

   **This is what captures voting-period expiry with zero events:** the sweep
   at height H returns REJECTED where the previous sweep returned SUBMITTED,
   and the write records the transition with `observedHeight = H`. Cost is one
   paginated read per policy per window (policies number 1–2) — the
   validator-sampler's cost profile — and no DB read is needed inside
   `collect`, so the two-phase contract holds without deviation.

   For an id discovered by inputs 1/2 but **absent** from the sweep (pruned
   within the window), one `proposal/{id}` pinned at the discovery height
   recovers full state; a 404 there means it pruned faster than we read it, and
   the row is written from the event payload with `prunedAtHeight` set.

   > **CORRECTED 2026-07-29 (§3.5 finding 3): there is no 404.** The LCD answers
   > a missing proposal with **HTTP 500**, and the body is byte-identical for a
   > pruned id and one that never existed — as it is for an LCD outage or a bad
   > height pin. So a failed single-proposal read establishes NOTHING and writes
   > nothing. Prune comes from absence in a **successful** paginated sweep (the
   > `sweepOk` flag) or from an observed `EventProposalPruned`, which also carries
   > the terminal status and full tally.

   **3b — votes.** For each non-terminal touched proposal,
   `votes_by_proposal/{id}` pinned at `window.to` gives the authoritative
   option/submit-time set, left-joined onto input 1's provenance.

**Both state reads paginate to exhaustion** (`SECURITY.md`: all chain reads
paginate, iteration is capped). `proposals_by_group_policy` and
`votes_by_proposal` follow `pagination.next_key` through `parsePagination`
under a per-window page cap. Hitting the cap is an incident-worthy log, never a
silent truncation — a truncated sweep looks identical to a pruned proposal and
would corrupt the mirror.

### 2.3 Idempotency: a monotonic `observedHeight` guard

Upserts key on `proposalId` and `(proposalId, voter)`. The guard: a window
whose sweep observed height H **must not** overwrite a row already observed at
H′ > H. This is what makes replay converge — a replay from 0 re-reads state
pinned at old heights, and old-height state is correct *for that height* but
stale as a mirror. A 404 on a pruned proposal **preserves** the stored row:
never deletes, never nulls. That is app-spec §13's single-snapshot-retention
posture applied to governance.

### 2.4 The API stays DB-only; the web tier owns the live plane

`services/api` has no chain client, by design. It serves the durable mirror;
current policy state, member sets and decision policies are live reads owned by
the web tier at 7.2 — the division `/market` and `/portfolio` already use. The
list payload carries **`indexed_from_height`** (the stream start), because
proposals pruned before the indexer existed are unrecoverable and the page must
not imply a completeness it does not have.

### 2.5 The relay stays closed through this PR

Nothing here signs anything. `ALLOWED_MSG_TYPE_URLS` in
[`apps/web/app/tx/build.ts`](../../apps/web/app/tx/build.ts) is **unchanged**,
and the rejection matrix gains a row asserting `/cosmos.group.v1.MsgVote` is
still refused after this PR. The governance amendment to that allowlist is
[7.3–7.4](2026-07-28-app-m7.3-7.4-governance-write-path.md)'s focused review.

### 3.1 Commit A — devnet governance substrate + `chain-client` x/group reads

**`infra/devnet/bootstrap/nvhash-group-bootstrap.sh`** (new). Probes first that
the node image serves `x/group` (`provenanced q group groups-by-admin …`) and
fails loudly if not — a `[VERIFY]` in the §14.2 tradition, resolved here and
pinned in the fixture manifest. Then creates the group (3 members from the

The three members are existing throwaway devnet keys from the local keyring;
the script generates no key material, accepts no mnemonic, and writes none to
`state/` — `SECURITY.md`'s devnet posture, which this commit is the first to
exercise for governance. It points at the disposable local chain only.

**`infra/devnet/actions/gov-submit.sh` / `gov-vote.sh` / `gov-exec.sh`**
(new ×3) — siblings of the existing `infra/devnet/actions/*.sh`, sourcing
`_common.sh`.

**`contracts/drills/gov-drill.sh`** (new) — the state generator. Must produce
every terminal state the UI will have to render, because the 5.4 rule is that
e2e renders every terminal state from **real drill history**:

- SUBMITTED / open / partially voted, with yes, no, abstain and no_with_veto
  each present at least once
- ACCEPTED → EXEC → `executor_result: SUCCESS` (a benign `UpdateConfig`)
- ACCEPTED → EXEC → **`executor_result: FAILURE`** (an `UpdateConfig` the
  contract rejects) — the outcome `status` alone cannot express
- REJECTED at voting-period end **in a block with no group transaction** — the
  non-tx transition the whole indexing design turns on
- ABORTED by a mid-vote `MsgUpdateGroupMembers` — the case `groupVersion` /
  `groupPolicyVersion` exist to explain
- WITHDRAWN by the proposer
- **PRUNED** — sleep past the EndBlocker prune window; confirm
  `GET /cosmos/group/v1/proposal/{id}` 404s while the indexed row survives

**And every C1 multiplicity case.** Terminal-state coverage is necessary and
not sufficient: M6.4's drill produced every terminal payment state and never a
batched payment, which is why its fixture corpus could illustrate the plan's
natural key but never contradict it. The drill must therefore also emit:

- a proposal with **two proposers**
- a proposal carrying **two messages**
- **one transaction carrying two `MsgVote`s** for different proposals, at
  different `msgIndex`es
- **two proposals transitioning in the same block** at voting-period end
- an attempted **vote change** — the same voter submitting `MsgVote` twice for
  one proposal. Record whether the chain accepts or rejects it in
  `manifest.json` `pinned_facts`; **acceptance invalidates the
  `(proposalId, voter)` key and must be resolved before commit B is written**
  (§4b C1)
- enough proposals on one policy to force **at least two pages** of
  `proposals_by_group_policy`, so the pagination path is exercised by the
  corpus rather than assumed

**`packages/fixtures`** — capture into `fixtures/queries/group/` (group-info,
group-policy-info, group-members, proposals-by-group-policy, per-status reads,
votes-by-proposal) and a new `fixtures/governance/` (submit/vote/exec txs and
the voting-period-end **block_results**). `manifest.json` gains `sources`
entries and new **`pinned_facts`** answering, from observation rather than
assumption:

- whether `cosmos.group.v1.EventProposalPruned` and any VP-end tally event
  appear in `finalize_block_events` on this build (§7 D2b);
- whether group event attribute values are JSON-quoted (the corpus already
  records that vault values are and contract values are not, and `dequote`
  tolerates both);
- whether the LCD serves `cosmos/group/v1/proposal/{id}` under
  `x-cosmos-block-height` pinning;
- the devnet-only short voting period, **labeled devnet-only** so nobody reads
  it as a mainnet fact.

**`packages/chain-client/src/group.ts`** (extend): `proposal(id)`,
`proposalsByGroupPolicy(policyAddress, params)`, `votesByProposal(id, params)`,

**Schema columns.** `GovProposal` is nine columns today; each addition must
earn its place:

| column | type | why it must exist |
| --- | --- | --- |
| `groupId` | `BigInt` | the policy→group link at proposal time; member-set resolution without a second live read |
| `proposers` | `String[]` (replaces `proposer`) | x/group permits multiple proposers; one column is a lie when there are two |
| `votingPeriodEnd` | `DateTime` | the §8.7 countdown — **and** the only thing that explains a status change with no transaction |
| `yesCount`, `noCount`, `abstainCount`, `noWithVetoCount` | `Decimal(39,0)` ×4 | tally-vs-threshold for a proposal the chain has pruned. Weights are unbounded ints, so these join `AMOUNT_FIELDS` |
| `executorResult` | `String` | `NOT_RUN\|SUCCESS\|FAILURE`. "Passed but execution failed" is invisible in `status` and is exactly what Grace needs to see |
| `groupVersion`, `groupPolicyVersion` | `BigInt` ×2 | x/group ABORTs on group/policy change; without these the UI can assert an abort but not explain it |
| `decisionPolicy` | `Json` | the threshold **in force at submit**. The live policy can change; a historical tally-vs-threshold is otherwise unrenderable |
| `observedHeight`, `observedAt` | `BigInt`, `DateTime` | the AS-OF of the mirrored status/tally — the §12.1 freshness fact and the replay-monotonicity key. `height`/`txhash` keep their existing meaning: **submit** provenance |

`GovVote`: add `weight Decimal(39,0)?` (the voter's weight at the vote height —
membership rotates, and a stored tally line is otherwise unexplainable; null
means "not recoverable", never 0); add `metadata String?` (a public chain
field, symmetric with the already-allowlisted `GovProposal.metadata`); and
**widen `height`/`txhash` to nullable** (a vote recovered from state has no tx
provenance — null is honest, a fabricated height is not).

Indexes: keep `@@index([groupPolicyAddress])`, add
`@@index([groupPolicyAddress, proposalId])`. **No keyset machinery** —
proposals per policy are tens, not the 300 000 `operator_payments` rows that
forced `$queryRaw` row comparison. Stated so nobody cargo-cults 6.4's streaming
into a structurally tiny table.

### 3.3 Commit C — `services/api` governance endpoints

address keying, so no `PERSONAL_PATHS` entry is created. Registered by adding
objects to the array in `services/api/src/routes.ts` via `defineEnveloped<Q>()`,

### 3.5 Delivery notes (2026-07-29)

**Commit A — DELIVERED.** `x/group` is served on this build; the 2026-07-14 empty
`groups.json` reflected an unbootstrapped devnet, not a missing module.
`nvhash-group-bootstrap.sh` creates a 3-member group with **two** threshold
policies — two deliberately, so the set-valued discovery of §2.1 is exercised by
data rather than claimed — and prints the primary policy for
`nvhash-deploy-p2p.sh`'s `CONTRACT_ADMIN` hook. `gov-drill.sh` passed **30
assertions, 1 skipped** against a governed chain. `generate-corpus.sh` now
bootstraps the group before the deploy, so the corpus records the governed
topology `liquid-staking-spec` §12.1 describes instead of the plain-account admin
every earlier capture ran against.

**Six findings, and FOUR contradicted this plan.** They are corrected in
app-spec §9.1/§9.2, `services/indexer/CLAUDE.md` and the code; the fixture
manifest's `pinned_facts` is the authority where this document still reads
otherwise:

1. **A successfully executed proposal is pruned in its OWN transaction**, so
   `ACCEPTED` + `SUCCESS` is a pair no state read can ever return. §2.2's "state
   reads for authority" is wrong for the happy path — `EventExec.result` plus
   `EventProposalPruned` (which carries the terminal status AND the full tally)
   are its only record.
2. **Votes are DELETED at the voting-period-end tally**, even for a proposal that
   passes. §2.2's input 3b recovers votes only while a proposal is OPEN; per-voter
   history for anything closed exists solely in the tx plane. This is the
   strongest justification in the PR for `gov_votes` existing at all, and it is
   not the one the plan gave.
3. **A missing proposal answers HTTP 500, not 404**, with a body byte-identical
   for a pruned id and one that never existed — and an LCD outage answers 500
   too. §2.2's "a 404 there means it pruned faster than we read it" and §4
   invariant 4's "a 404 preserves the stored row" are both wrong about the
   mechanism. Prune is established ONLY by absence from a **successful**
   paginated sweep or an observed `EventProposalPruned`. This is invariant 4's own
   disproof line, and it turned out to be a live hazard rather than a
   hypothetical.
4. **Voting-period-end transitions are EVENTLESS**; `EventProposalPruned` is the
   only x/group EndBlocker event across 295 scanned heights. Both branches §2.2
   specified turned out to be half-true at once — the block plane carries prune
   detection, the state sweep carries the transition.
5. `EventVote` carries only `proposal_id` + `msg_index`; voter and option come
   from the `MsgVote` **body**. The `Vote` payload has **no weight** field.
6. A second `MsgVote` from the same voter is **rejected by the chain**, so
   `(proposalId, voter)` holds — measured, not assumed.

One state was NOT produced: `PROPOSAL_STATUS_ABORTED` is unreachable on this
build (a mid-vote group-members change did not abort an open proposal; the
proposal executed successfully at `group_version` 1 against a group at version
2). It stays in the status enum because it is in the module's proto, and 7.2 must
treat its ABORTED rendering as unexercised by drill data.

### 3.5b PR #23 review — two issues, both valid, both fixed

**P1 — event-only proposals were discarded (`write.ts`). VALID, and it was a
silent data-loss bug in the common case.** A proposal submitted, executed and
pruned inside ONE window is absent from that window's ending sweep, and every
event-derived write is an UPDATE on `proposalId` — so with no base row the
submit provenance, exec result, terminal tally and prune stamp all affected zero
rows and the proposal was simply gone. Its votes, which insert on
`(proposalId, voter)`, survived as **orphans**: rows the detail endpoint can never
reach, asserting participation in a proposal the mirror cannot show. Reproduced
before fixing: zero proposal rows, one vote row.

Not an edge case. A successful exec prunes in its own transaction (§3.5 finding 1)
and a 500-height window is roughly eight minutes, so it is the normal outcome for
any promptly executed proposal — the drill's own proposals 1, 2 and 7 all had this
shape, and a single-window backfill would have lost all three.

**The root cause is a mechanism dropped, not a case unforeseen.** §2.2 specified
the recovery read — *"one `proposal/{id}` pinned at the discovery height recovers
full state"*. It was removed while correcting the 404-means-pruned semantics: the
mechanism went out with the wrong error handling rather than being re-based on the
right one.

Fixed by restoring it, with the corrected semantics: recover by a height-pinned
read at a height the proposal was demonstrably ALIVE, carry the AS-OF of that read
rather than the window's end, and — where recovery is impossible — log loudly and
refuse the orphan votes instead of storing half a record. Choosing the pin height
turned out to have its own bug (a naive minimum across submit and terminal heights
can pin before the proposal existed), which a test caught rather than review.

**§4b did not prevent this, and the reason is worth recording.** C1 enumerated
cardinality and C4/C5 were n/a, so no cell asked "which windows can a proposal's
lifecycle span?" — a *temporal* space none of the five covers. Worse, the replay
suite contained an invariant named exactly for this behavior — *"records
`ACCEPTED` + `SUCCESS` from EVENTS ALONE"* — which seeded the row in a PRIOR
window and then applied the prune. It verified the easy variant and passed while
the defect it named was live. **That is precisely the M6.4 failure the whole §4b
apparatus was built to prevent**, reproduced inside the PR that piloted it, and it
argues for adding a temporal cell (C6: which windows can one entity's lifecycle
span, and does each write path work when they collapse into one?) rather than for
trusting the existing five.

**P2 — proposer truncation was unreported (`derive.ts`). VALID, lower severity.**
`proposers.slice(0, MAX_GOV_PROPOSERS)` trimmed silently while `messages` and
`votes` both carried flags — so a 40-proposer proposal was indistinguishable from
a 32-proposer one. It contradicted this PR's own stated rule that truncation is
always flagged, and it matters more than a display trim because *who proposed
something* is identity data. Fixed with `proposers_truncated` on
`GovProposalRow`. No data was lost (the mirror keeps the full array; only the wire
view trimmed), which is why this is a P2 and the above is not.

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **Indexed additions are public chain data only, allowlisted, and
   amount-disciplined.** Every new `GovProposal`/`GovVote` column is enumerated
   in §3.2; tally counts and `weight` are `Decimal(39,0)`. *Gate:*
   `services/indexer/test/schema-allowlist.test.ts` over the extended
   `test/security/allowed-fields.ts` — a column added to the migration but not
   the allowlist fails CI.
2. **Replay converges and never regresses.** Natural-key upserts; a lower
   `observedHeight` cannot overwrite a higher one, enforced by a **conditional
   update** rather than a read-compare-write (§4b C3). *Gate:*
   `test/workers/governance-replay.test.ts` — replay from 0, random restart
   points, out-of-order-window monotonicity, and a concurrent
   backfill-beside-live case.
   *Disproof:* two writers committing the same row in an order the statement
   does not itself constrain — i.e. convergence that depends on stream
   scheduling rather than on the SQL.
3. **Non-tx status transitions are observed, not inferred.** Voting-period
   expiry is captured by the state sweep, never by a clock. *Gates:* the
   `governance-replay.test.ts` VP-expiry case (a window containing **no
   transaction** flips SUBMITTED→REJECTED); `governance-sources.test.ts`.
4. **The mirror outlives chain state and never claims otherwise.** ~~A 404~~
   **absence from a SUCCESSFUL sweep, or an observed `EventProposalPruned`**
   (corrected 2026-07-29 — the disproof below turned out to describe the actual
   transport) preserves the row and sets `prunedAtHeight`; the API serves it with
   `pruned: true` and no verify affordance. *Gates:* the replay prune case;
   `services/api/test/governance-endpoints.test.ts`.
   *Disproof:* a 404 that is **not** a prune — an LCD outage, a wrong height
   pin, or a node serving a pruned-state snapshot — being recorded as
   `prunedAtHeight`, which would durably assert "the chain discarded this" about
   a proposal the chain still holds. The prune path must be distinguishable from
   the read-failure path before it writes.
5. **The list never implies completeness it lacks.** `indexed_from_height`
   rides the envelope payload. *Gate:* `governance-endpoints.test.ts`.
6. **No governance surface is address-scoped.** All three routes are
   `auth: "public"`; no `PERSONAL_PATHS` entry is created. *Gates:* the
   registry-derived `services/api/test/cross-address.test.ts` (automatic since
   6.4); the registry-driven `test/envelope-contract.test.ts` GET-only/405 gate.
7. **Every input bounded at entry.** `id` = u64 decimal string, `policy` =
   bech32, `status` = closed enum, pagination = the shared schema. *Gates:*
   `services/api/test/query.test.ts`; the registry harness.
8. **Unknown on-chain shapes fail honestly, never silently and never
   fatally.** An unrecognized decision-policy type or proposal message parses to
   a tagged `unknown` preserving the raw JSON — no throw that stalls the worker,
   no fabricated summary. *Gates:* the group block in
   `packages/chain-client/test/chain.test.ts`;
   `services/indexer/test/workers/governance-decode.test.ts`.
   *Disproof:* an undecodable element causing its **siblings** to be dropped
   rather than just itself — the M6.4 decoder marked the whole message
   undecodable and committed the window without any of its payments. Quarantine
   must be per-element, and a quarantined element must be visible, not absent.
9. **Empty governance is an honest state.** A plain-account `Config.admin`
   yields an empty policy set, empty committed windows, and `[]` with real
   heights. *Gates:* `governance-sources.test.ts`; the envelope harness's
   honest-empty pass (automatic).
10. **Free-form on-chain text is stored but never logged.** Proposal and vote
    `metadata` are public and mirrored; they do not enter structured logs.
    *Gate:* the standing `services/indexer/test/log-scrubbing.test.ts`.
11. **The grant boundary is unchanged.** Only `indexer_writer` writes
    `indexed`; `api_reader` selects. *Gate:* the standing
    `services/indexer/test/integration/grant-boundary.test.ts`.
12. **The substrate does not weaken role detection.** With a real group policy
    behind `Config.admin`, the previously-dead `groupPolicyInfo → groupMembers`
    branch of `apps/web/app/lib/services/roles.server.ts` goes live, and the
    plain-account fallback stays reachable. *Gate:*
    `apps/web/test/roles.test.ts`, extended with the group-policy path.
13. **The relay stays closed — this PR adds no signing path.**
    `ALLOWED_MSG_TYPE_URLS` is **unchanged**; a governance message must still be
    refused after this PR. *Gate:* the standing
    `apps/web/test/broadcast-guard.test.ts` rejection matrix, with an added row
    asserting `/cosmos.group.v1.MsgVote` is rejected.
14. **No unbounded chain reads.** Both state-plane reads paginate to
    exhaustion under a per-window page cap; hitting the cap logs an incident
    rather than truncating, because a truncated sweep is indistinguishable from
    a prune and would corrupt the mirror. *Gates:*
    `governance-sources.test.ts` multi-page and cap-reached cases;
    `packages/chain-client/test/chain.test.ts` pagination-follow case.
15. **Verification is reproducible and recorded.** `gov-drill.sh` is scripted,
    re-runnable against a disposable chain, and its result is written to
    `contracts/IMPLEMENTATION-STATUS.md` with a date and the build it ran
    against. *Gate:* shellcheck plus the drill's own exit status; the ledger
    entry is a commit-A deliverable, not a follow-up.
16. **Devnet key posture.** The bootstrap script uses existing throwaway
    keyring entries, generates no key material, accepts no mnemonic, writes
    nothing to `state/`, and points only at the disposable local chain.
    *Gate:* review of commit A plus the standing secret-scan on the diff.
17. **Standing gates continue on every commit:** fixture-corpus completeness,
    `pnpm -r` typecheck/test, envelope/read-only/rate-limit harnesses, and
    shellcheck on the new `infra/devnet` and `contracts/drills` scripts.

### C1 — Natural keys & cardinality

Multiplicity is sourced from `x/group`'s own rules, **not** from what the drill
happens to emit. This is the row that M6.4 got wrong.

| Key / collection | Uniqueness | Max multiplicity | Handling |
| --- | --- | --- | --- |
| `GovProposal.proposalId` | x/group assigns monotonically, chain-global across all policies | 1 row per id | PK as-is |
| `GovProposal.proposers` | — | **N > 1** — x/group permits several proposers | `String[]`, replacing the scalar `proposer` |
| `GovProposal.messages` | — | **N > 1** — a proposal may carry several messages | `Json` array, stored **verbatim** |
| Proposals per policy | — | **unbounded** | paginated to exhaustion under a page cap (§2.2) |
| Policies per program | — | **1..n** — the dual-policy split is open | set-valued discovery (§2.1) |
| `GovVote` PK `(proposalId, voter)` | one vote per voter per proposal | **[VERIFY] — assumed 1, must be proven** | see disproof below |
| Group messages per **tx** | — | **N > 1** — a tx may carry several `MsgVote`/`MsgExec`, for different proposals | tx plane keys discovery per **`msgIndex`**, never per txhash |
| Proposals transitioning per **block** | — | **N > 1** | block plane iterates all matching events per height |

> **`(proposalId, voter)` is the one key in this PR that rests on an
> assumption.** *Disproof:* a voter successfully submitting a second `MsgVote`
> for the same proposal — a vote change — which would make the key lossy in
> exactly the way `(txhash, msgIndex)` was lossy for batched payments.
> `x/group` v1 is believed to reject a second vote, but **belief is what
> produced the M6.4 defect.** Commit A's drill must attempt a vote change and
> record the chain's actual answer in `manifest.json` `pinned_facts`. If the
> chain accepts it, the key gains a discriminator before commit B is written.

### C2 — Wire bounds

**This row exists because PR #19 shipped exactly this defect** — `yield_by_epoch`
was uncapped server-side against a `.max(2_000)` Zod cap, and the whole derived
read nulled out. That fix was instance-wise; the class is still open, since
`packages/api-types/src/rows.ts:310` couples the two sides **in a comment**
while nothing imports or tests the pairing.

Every bound below is **declared once in `@nvhash/api-types` and imported by
both sides**, with a test asserting the producer's cap is strictly inside the
consumer's:

| Payload | Bound |
| --- | --- |
| `/governance/proposals` → `proposals[]` | `MAX_GOV_PROPOSALS_PAGE`, inside the web Zod array cap |
| `/governance/proposal` → `votes[]` | `MAX_GOV_VOTES_PER_PROPOSAL` — note this is **not** page-bounded by the caller, so the server must trim and flag rather than rely on the group being small |
| `GovProposalRow.messages[]` | `MAX_GOV_PROPOSAL_MESSAGES`, with the over-limit proposal served flagged, never silently truncated |
| `/governance/policies` → `policies[]` | `MAX_GOV_POLICIES` |
| every string field (`metadata`, addresses, txhash) | length bounds shared the same way |

*Gate:* `packages/api-types/test/bounds.test.ts` — a table-driven assertion over
every declared pair. A new bounded field that is not in the table fails it.

### C3 — Concurrency

| Read-then-write | Remedy |
| --- | --- |
| The `observedHeight` monotonicity guard (§2.3) — read current row, compare, write | **DB-level conditional update** (`UPDATE … WHERE observedHeight < $new`, and the insert arm via `ON CONFLICT … WHERE`), *not* a read-compare-write in application code. Stream serialization via `runWindow` makes concurrent writers unlikely, but "unlikely by topology" is the assumption class `SECURITY.md` forbids relying on, and a backfill running beside the live worker is a real scenario |
| Vote/proposal upserts during replay-beside-live | Same conditional-update arm; convergence is then a property of the statement, not of scheduling |
| Checkpoint advance | Unchanged — already owned by `runWindow` |

### C4 — State × affordance

**n/a for this PR** — 7.1 ships no UI and no actions. It carries the *forward
obligation* of supplying the discriminators 7.2's matrix will need:
`status`, `executorResult`, `prunedAtHeight`, `groupVersion` vs current. A
proposal state that 7.1 cannot express is a state 7.2 cannot render honestly.

### C5 — Plane precedence

The precedence table itself is 7.2's obligation (the API is DB-only, D12). 7.1's
obligation is to make the **stale** column expressible at all: `observedHeight`
and `observedAt` are the as-of stamp, and `prunedAtHeight` distinguishes "chain
no longer holds this" from "we could not read the chain". Without those three,
7.2 could only distinguish *ok* from *down* — which is precisely the axis
M6.4's honesty matrix was missing when the stale-registry P1 leaked.

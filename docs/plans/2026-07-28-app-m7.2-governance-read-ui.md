## 1. Origin & problem statement

Master plan §2 PR 7.2: *"Governance center read UI (§8.7): decoded proposals,
tallies, per-member status, outcome history."*

App-spec §8.7 asks for: proposal list and detail with **decoded messages
(human-readable summary above the exact JSON)**, proposer, submitted/expiry
times, tally vs threshold, per-member vote status (who, how, when), and outcome
history — durable and indexed, the audit trail the personas require.

What exists on `main`: `app/routes/governance.tsx` is a **registered stub**
(title + placeholder), already in the `e2e/axe.spec.ts` route list, with two
i18n keys (`governance.title`, `governance.placeholder`). What 7.1 delivers:
three public endpoints and the frozen `@nvhash/api-types` governance shapes,
plus `GroupClient` proposal/vote/policy reads for the live plane.

This PR is the read surface only. Vote, execute and proposal creation are all
[7.3–7.4](2026-07-28-app-m7.3-7.4-governance-write-path.md). Keeping the write
path out of this PR is deliberate: M6.4 grew from a read view into a read view
plus five privileged writes and became the milestone's 95-file outlier.

## 2. Mechanism

### 2.1 Two planes, and which one is canonical

App-spec §12.1.1 names governance tallies **live-canonical**. So:

- **Open proposals** — status, tally and voting-period countdown come from the
  **live** `GroupClient` read. The indexed row is history and fallback.
- **Closed proposals** — the indexed row is the record, because the chain may
  have pruned it entirely (overview F4). `prunedAtHeight` non-null means the
  chain no longer holds it, and the UI says so.
- **Live read fails** — dim to the indexed value with a stale badge carrying
  its `observedHeight`/`observedAt`. **Never blank, never
  indexed-presented-as-current.** This is the `operator-data.test.ts` honesty
  matrix applied to governance.

The member set (for "who hasn't voted yet") and the current decision policy are
**live reads only** — D5 in the overview. No `gov_group_members` snapshot table
is built; that would be a third table for a display nicety.

### 2.2 Decoding never invents meaning

`app/governance/decode.ts` is pure and locale-aware. A **closed typed union**
of known message types produces a human summary; anything else renders as a
tagged `unknown` — "unrecognized message type" plus the exact JSON. A
best-effort heuristic summary is disqualified by §12.1 (never present an
invented meaning) and by `SECURITY.md`'s never-lie-about-state rule.

The exact JSON is shown for **every** message, known or not, beneath the
summary — §8.7's ordering, and Grace's "what exactly does this do" question.

**One vocabulary for one action.** Summaries for `MsgExecuteContract` against
the program contract import their variant vocabulary from
[`apps/web/app/tx/build.ts`](../../apps/web/app/tx/build.ts) (`OPERATOR_VARIANTS`
and the admin-variant list) rather than restating it, so this reader and 7.4's
composer cannot describe the same action differently.

### 2.3 Membership drift is stated, not papered over

A closed proposal whose stored `groupVersion` ≠ the current group version was
decided by a **different electorate**. Rendering today's members against it
would imply they were the voters. Instead: recorded votes only, plus an
explicit "group membership changed since this proposal" note. This is what the
`groupVersion`/`groupPolicyVersion` columns 7.1 adds exist to enable.

Similarly, tally-vs-threshold for a historical proposal uses the
`decisionPolicy` **snapshot** stored at submit, not the live policy.

### 2.4 No verify link

Overview D8: the `governance` verify-link target stays absent through M7. The
typed union in `apps/web/app/components/verify-link.tsx` stays closed, and its
totality assertion is the gate. A pruned proposal has nothing on chain to link
to at all, which makes the absence correct rather than merely unfinished.

### 3.4 Pre-build revision (2026-07-30) — §7's refinement gate discharged

This plan was written before 7.1 captured the governance corpus. Read against
the delivered corpus (`packages/fixtures/fixtures/queries/group/`, manifest
`pinned_facts` + `governance.drill_observations`) and the frozen
`@nvhash/api-types` shapes, **eight facts change the design below.** Where this
section and §2–§3.2 disagree, this section is authority.

**R1 — the offline corpus is UNGOVERNED, and cannot be re-captured in this PR.**
`queries/contract/config.json` is from the 2026-07-14 full capture and its
`admin` is a plain account (`tp18kkn2…`); the `queries/group/*` fixtures are a
2026-07-29 **partial** capture onto the same devnet, where the contract had been
deployed long before the group existed. F2 (no admin-rotation message) is
exactly why the two cannot be reconciled without a fresh chain, and a full
regeneration is independently blocked (`generate-corpus.sh` cannot complete on a
mid-month fresh chain, E-CAL). So offline, policy discovery correctly resolves to
*"the program's admin is not a group policy"*.
*Consequence:* the offline e2e exercises the **indexed** plane end to end (the
three 7.1 endpoints, served by MSW from the drill proposals) plus the honest
live-unresolved state. The **governed** live plane is exercised by
`governance-data.test.ts` with MSW overrides and by e2e-live. This is a
narrowing of §3.2's "rendering every terminal state from the 7.1 drill corpus" —
every terminal state is still rendered, but through the mirror, which is where a
closed proposal's state lives anyway (7.1 finding 2).

**R2 — the live plane has THREE outcomes, not two.** `groupPolicyInfo` on a
plain account and `groupPolicyInfo` against an unreachable node both throw. The
seam therefore reports `governed` / `not-governed` / `unavailable`, deciding
"not a policy" **only** on an `LcdError` with status 404 and treating every
other failure as `unavailable`. That asymmetry is deliberate: a missing
*proposal* answers 500 on this build (pinned fact), so a status code is not
generally a semantic signal here, and the conservative direction ("we could not
check") never claims a governance topology that is not there.
*Unverified, and named as such:* no fixture pins what the LCD answers for
`group_policy_info` on a non-policy account. If it turns out to be 500, this
build reports `unavailable` where `not-governed` is true — honest, and covered
by an e2e-live assertion rather than by a guess here.

**R3 — every proposal message in the corpus is `MsgSend`.** The drill's ten
proposals all carry `/cosmos.bank.v1beta1.MsgSend`; no
`MsgExecuteContract`-inside-a-proposal shape was captured, though
`infra/devnet/actions/gov-execute-contract.sh` produces one. So the closed union
of §2.2 is: `MsgSend` (shape pinned by the corpus) and `MsgExecuteContract`
against the **configured program contract** (shape pinned by
`contracts/src/msg.rs` and `app/tx/build.ts`). Everything else — including an
`MsgExecuteContract` against any other contract, and any x/group message — is a
tagged `unknown`. Adding an x/group message arm on proto knowledge alone would
be precisely the confident-wrong summary invariant 2's disproof line names.

**R4 — the variant vocabulary is not importable today.** `OPERATOR_VARIANTS` is
exported from `app/tx/build.ts`; the admin/keeper set exists only as prose in
that file's comment and as string literals in `test/broadcast-guard.test.ts`.
§2.2's "import their vocabulary rather than restating it" therefore requires
exporting `ADMIN_VARIANTS` and `KEEPER_VARIANTS` from `build.ts` and switching
the rejection matrix to iterate them. **`ALLOWED_MSG_TYPE_URLS` and
`guardOperatorExecute` are untouched** — naming the rejected set is not
admitting it, and the matrix gets stronger because it can no longer drift from
the list the decoder reads.

**R5 — membership drift has real data, and the disproof line resolves.**
`groups.json` is at `version: 2` while proposals 4/5/6 carry `group_version: 1`
and proposal 8 carries `2`, because the drill changed members mid-vote. So the
7.1 drill measured what invariant 6's disproof asked for: a members change DOES
bump the **group** version, while both policies stayed at `version: 1`. Group
version tracks the electorate; policy version tracks the rule. Invariant 6
stands as written, now on measured ground.

**R6 — an empty live vote list is not "nobody voted".**
`votes-by-proposal-closed.json` is `{"votes":[]}`: the module deletes votes at
the tally. The live vote read is consulted **only** for an open proposal, and
only ever ADDS voters the mirror has not caught up to; it can never remove or
blank a recorded vote.

**R7 — a live read failure is never evidence of a prune.** A missing proposal
answers HTTP 500 with a body identical to a node outage's. `pruned` is decided
by the mirror's `pruned_at_height` alone, and a pruned row is never live-read at
all. Same rule for closed proposals: the live plane is consulted only for rows
that are OPEN (`status === "submitted"`) and not pruned, which also bounds the
live work the list route does.

**R8 — the detail route has a live-only state.** `/governance/proposal?id=`
404s for an id the mirror has never seen, but a proposal submitted since the
last indexer window is on chain right now. The detail seam therefore composes
`{indexed?, live?}` and renders four states: both, indexed-only (the normal
closed case), live-only (labeled "not mirrored yet"), and neither (404).

**File-plan deltas** against §3.1/§3.2, all recorded rather than slipped in:
`app/tx/build.ts` + `test/broadcast-guard.test.ts` (R4); `app/mocks/handlers.ts`
gains the x/group LCD reads as well as the three API endpoints;
`app/governance/params.ts` holds the two route-boundary parsers (the
`portfolio/page-param.ts` precedent).

### 3.5 Delivery notes (2026-07-30)

**All three commits DELIVERED.** §3.4's eight revisions held as written; what
follows is what the build added to them.

**One finding contradicted the plan, and it is the sharpest thing in this PR: a
proposal's `final_tally_result` is ZEROS for the whole voting period.** The
module writes it only when it tallies. §2.1 said an open proposal's status and
tally come from "the live `GroupClient` read" — but that read is the state plane,
whose tally for an open proposal is all zeros, and rendering it would have said
*nobody has voted* on the page where votes are cast. The fix is x/group's own
`TallyResult` query, added as `GroupClient.tallyResult` (a **file-plan delta
outside `apps/web`**, recorded here rather than slipped in). Two consequences:

- The corpus cannot pin the new read's response envelope, so both
  `{ tally: … }` and a bare tally object are accepted, and the tally SHAPE is
  the already-pinned `TallyResult`. The offline mock serves each proposal's own
  captured `final_tally_result`, which for the open ones is genuinely zeros.
- `packages/chain-client/test/chain.test.ts` gained the assertion that makes
  this falsifiable rather than believed: **every SUBMITTED proposal in the
  captured sweep carries an all-zero final tally.** If a later build starts
  maintaining a running tally in state, that test fails and the extra read
  becomes redundant instead of silently duplicated.

**Status and tally move as ONE unit across the plane boundary.** The live plane
is used only when BOTH the proposal read and the tally read succeed; otherwise
the row falls back to the mirror with its `observed_height`. A live status beside
a mirrored tally would label a figure with a freshness it does not have, and C5
lists the two in one row for exactly that reason.

**Live work is bounded, and the bound is visible.** Live reads happen only for
OPEN, unpruned proposals; the per-proposal tally read is capped at
`MAX_LIVE_TALLY_READS` (25) per list render, and a proposal past the cap renders
on the mirror **with the same stale badge a failed read gets** — never a
quieter, different degradation. Policy and member sweeps paginate to exhaustion
under `GROUP_MAX_PAGES`, and a capped policy sweep is reported.

**§4b C1's own gap, filled by the build:** a `TallyVM` count is `string | null`,
not `string`. The live-only-with-failed-tally cell has no honest count at all,
and a non-nullable field would have forced a `0` into precisely the figure that
must never be fabricated.

**Delta from §3.2's component list:** eight components, not six —
`plane-badge.tsx` (the freshness label is used by both routes and is the
mechanism invariant 5 rests on) and `policy-panel.tsx` (the live/historical
policy set, which has no home on the detail page) join the six named. Two
further pure modules landed beside them, `format.ts` (deterministic UTC
instants and the coarse duration, so SSR and the browser cannot disagree) and
`labels.ts` (label maps total over each wire union).

**One standing gate was amended rather than worked around.**
`test/i18n-coverage.test.ts`'s `INDIRECT_KEY_ALLOWLIST` — previously empty —
now carries the six valoper-bearing program-action summaries. They reach `t()`
through `VARIANT_SUMMARY_KEYS`, which exists so the summary set is TOTAL over
the imported vocabulary (invariant 3), and that totality is not replaceable by
literal call sites. The exemption's stated condition is met: ONE call site,
which always supplies `{ valoper }`, and `governance-decode.test.ts` asserts the
substituted output of all six against goldens.

**`test/broadcast-guard.test.ts`'s admin/keeper rejection matrix now iterates
`ADMIN_VARIANTS ∪ KEEPER_VARIANTS`** over a total body map, instead of restating
nine string literals. The matrix could previously have drifted from the variant
set it was proving closed; it now fails to compile if it does.

**What is NOT covered, stated rather than implied.** The GOVERNED live plane is
exercised offline only through MSW overrides, because the corpus is ungoverned
(§3.4 R1) and regeneration is independently blocked. `e2e-live/governance.spec.ts`
is where it meets a real chain, and it also carries §3.4 R2's unverified claim —
whether `group_policy_info` on a non-policy account answers 404 or 500 — as an
assertion rather than a guess. `PROPOSAL_STATUS_ABORTED` renders and is unit-
tested, and remains unexercised by real data (7.1's drill could not produce it).

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **The relay stays closed — this PR adds no signing path.**
   `ALLOWED_MSG_TYPE_URLS` in `apps/web/app/tx/build.ts` is **unchanged**; a
   governance message must still be rejected after this PR. *Gate:* the
   standing `apps/web/test/broadcast-guard.test.ts` rejection matrix, including
   the `/cosmos.group.v1.MsgVote` row added at 7.1.
2. **Decoded messages never fabricate meaning.** Known types get a summary from
   a closed union; anything else renders "unrecognized message type" plus the
   exact JSON, which is present for *every* message. *Gate:*
   `test/governance-decode.test.ts`, including an unknown-type case and a
   malformed-payload case.
   *Disproof:* a message type the union claims to know but summarizes
   **wrongly** — a confident wrong summary is worse than "unrecognized", and no
   unknown-type test can find it. Every known variant needs a golden summary
   pinned against the contract's own field semantics, not against the
   decoder's.
3. **One vocabulary for one action.** The `MsgExecuteContract` summaries import
   their variant vocabulary from `app/tx/build.ts` rather than restating it, so
   this reader and 7.4's composer cannot diverge. *Gate:*
   `governance-decode.test.ts` cross-references `OPERATOR_VARIANTS` and the
   admin-variant list.
4. **Tally arithmetic is BigInt, scale-then-floor, never float**, and a
   percentage policy with no live total-weight read renders "n/a", never 0.
   *Gates:* `packages/api-types/test/tally.test.ts` (shared, golden-pinned both
   sides); `apps/web/test/governance-tally.test.ts`.
   *Disproof:* a decision-policy type whose pass condition is **not** the
   comparison this helper implements — x/group's percentage policy measures
   against total group weight while threshold measures absolute weight, and a
   third type (or a future one) may do neither. The `unknown` policy arm must
   render "n/a" rather than fall through to the threshold comparison.
5. **Chain-canonical for open proposals.** §12.1.1 names governance tallies
   live-canonical. Live-read failure dims to the indexed value with a stale
   badge carrying its observed height — never blank, never
   indexed-presented-as-current. *Gate:* `test/governance-data.test.ts`
   degradation matrix (the `operator-data.test.ts` precedent).
6. **Per-member status is honest about membership drift.** When a closed
   proposal's `groupVersion` ≠ the current group version, the page shows
   recorded votes only plus an explicit membership-changed note, and uses the
   `decisionPolicy` snapshot rather than the live policy. *Gate:*
   `governance-data.test.ts`.
   *Disproof:* membership changing **without** `groupVersion` moving — if
   x/group bumps the version only on some mutations, or bumps the *policy*
   version while the *group* version stays, then equal versions would not
   actually mean an unchanged electorate and this check would silently pass on
   drifted data. 7.1's drill mutates members mid-vote; confirm which version
   fields move.
7. **A pruned proposal is labeled, not silently rendered as live.** A row with
   `prunedAtHeight` set says the chain no longer holds it. *Gate:*
   `governance-data.test.ts`; the pruned case in `e2e/governance.spec.ts`.
8. **No verify link is rendered.** The §12.2 typed union in
   `app/components/verify-link.tsx` stays closed with no `governance` target.
   *Gate:* the standing `apps/web/test/verify-link.test.ts` totality assertion.
9. **Public read, no new authorization surface.** §8.7 is "public read; member
   write" — the page renders anonymously, and session-address highlighting
   never becomes a gate. *Gates:* `apps/web/test/session-scope.test.ts` (the
   governance routes must **not** join the personal-route list); an
   anonymous-render case in `e2e/governance.spec.ts`.
10. **Honest-empty with no policies.** An empty policy set renders the
    honest-empty page and the nav entry stays — §8.0's rule is that the nav
    must never 404, and hiding it is a different lie (overview D15). *Gate:*
    `governance-data.test.ts`; an empty-state case in the offline e2e.
11. **Offline-buildable from mocks.** *Gate:* `e2e/governance.spec.ts` against
    `app/mocks/handlers.ts`.
12. **i18n coverage** for every new `governance.*` key. *Gate:* the standing
    `apps/web/test/i18n-coverage.test.ts`.
13. **a11y both themes, both routes.** *Gate:* `e2e/axe.spec.ts`.
14. **No new client-exposed config.** The LCD reads are server-side in
    `.server.ts` modules. *Gates:* standing `check:bundle`;
    `apps/web/test/client-config.test.ts`.
15. **Standing gates continue:** `check:palette` on any token change,
    `pnpm -r` typecheck/test.

## 4b. Completeness obligations

Per [overview §7](2026-07-28-app-m7-governance.md).

### C1 — Natural keys & cardinality

No new persistence. The **rendering** cardinalities this page must handle,
sourced from `x/group` rather than from the drill's typical shapes: a proposal
with **several proposers**; a proposal carrying **several messages** (each
decoded separately, §2.2); **zero** votes on an open proposal; a member set
larger than the vote set and vice versa; **zero policies** (D15). Each gets a
case in `test/governance-data.test.ts` and, where visible, the offline e2e.

### C2 — Wire bounds

Consumes the bounds 7.1 declares in `packages/api-types/src/bounds.ts`. **This
page must not restate a numeric cap.** Every Zod array cap in
`app/api/api.server.ts` for a governance payload imports its bound from
`api-types`, so the pairing is checked by `packages/api-types/test/bounds.test.ts`
rather than by eye. A locally-written `.max(N)` on a governance array is a
review failure — that is the literal shape of the PR #19 defect.

Additionally: the server **trims and flags** rather than truncating silently,
so this page must render the flagged state (`…_truncated`) for every trimmable
collection instead of presenting a partial list as complete.

### C3 — Concurrency

**n/a** — read-only page, no writes, no shared mutable state. The live-plane
reads are per-request and uncached beyond the request (§8 stop-and-ask).

### C4 — State × affordance

The full matrix, filled. This is the row whose absence produced M6.4's
"inactive validators retain actions" P1 — and note that state arose from
*fixing* another finding, so the matrix is re-derived whenever a state is
added.

| Proposal state | Affordances this PR offers |
| --- | --- |
| open, not yet voted by session address | read only (vote arrives in 7.3–7.4) |
| open, already voted | read only; own vote highlighted |
| open, anonymous session | read only, no highlight, no prompt implying a gate |
| accepted, not executed | read only; `min_execution_period` shown if pending |
| accepted, executed SUCCESS / FAILURE | read only; `executorResult` shown distinctly from `status` |
| rejected / aborted / withdrawn | read only; outcome + reason |
| **pruned** (`prunedAtHeight` set) | read only from the mirror; explicit "chain no longer holds this"; **no verify affordance** |
| `groupVersion` ≠ current | recorded votes only + membership-changed note (§2.3) |
| no policies discovered | honest-empty page, nav entry retained |

**Every row's affordance column is "read only" in this PR**, which is exactly
why the matrix must be written down now: 7.3–7.4 adds actions, and it inherits
this table as the set of states each new affordance must be decided against.

### C5 — Plane precedence

Per field, over `{live ok, live stale, live down} × {indexed ok, stale, down}`.
**Stale is a distinct column from down** — conflating them is what produced
M6.4's stale-registry P1, where a successful-but-old indexed read silently
overrode canonical live ownership.

| Field | Precedence |
| --- | --- |
| status, tally (open proposal) | **live canonical** (§12.1.1). Live stale → live value + as-of; live down → indexed value + stale badge carrying `observedHeight`; both down → "n/a", never 0, never blank |
| status, tally, outcome (closed proposal) | **indexed canonical** — the chain may have pruned it |
| member set / "who hasn't voted" | **live only**. Live down → recorded votes only + explicit "membership not checked"; never today's members against a historical proposal |
| decision policy / threshold | **snapshot from the proposal row**, never the live policy, for any proposal not open |
| proposal messages | **indexed verbatim** — immutable once submitted |
| `indexed_from_height` | always shown when the list could be incomplete |

*Gate:* the `test/governance-data.test.ts` degradation matrix walks this table
cell by cell, including the four stale-but-successful combinations.

## 7. Open questions

*Milestone decisions are in [the overview](2026-07-28-app-m7-governance.md) §4.
D5, D6 and D15 are this PR's to resolve and are designed above (§2.1, §2.2,
invariant 10). Remaining:*

- **Q1 — outcome-history grouping. RESOLVED 2026-07-30 as proposed.** One list,
  `?status=` filter over the closed wire union defaulting to all, open proposals
  pinned above the rest, newest-first within each group. The corpus settles it:
  ten proposals across two policies, of which one is open — a two-section split
  would render an empty "open" heading on most loads, and "outcome history" is
  satisfied by the terminal rows carrying their outcome, not by a second page.
- **Q2 — countdown presentation under clock skew. RESOLVED 2026-07-30, and the
  proposal is REVISED.** The absolute expiry stays the primary fact, as proposed.
  The relative countdown is computed **server-side against the server clock and
  labeled approximate**, not against the browser clock: a client-clock countdown
  is a hydration mismatch and makes the axe-scanned page differ per client, and
  the server clock is no more authoritative than the browser's — it is merely
  deterministic, which is what a secondary hint should be. The devnet voting
  periods (300s/40s) are drill affordances, so nothing about the display may
  assume a period long enough for a countdown to be useful.
- **Q3 — how much of a long `messages` array to render inline. RESOLVED
  2026-07-30 as proposed, with one addition.** Summaries for all; the exact JSON
  rides in a `<details>` per message, open on the first and collapsed after. The
  addition: `messages_truncated` renders its own explicit note above the list,
  because the corpus cannot exercise it (every drill proposal carries exactly
  one message) and a trimmed array that only *looked* short is the state §4b C2
  requires to be visible.

## 2. Mechanism

### 2.1 What joins the allowlist

`ALLOWED_MSG_TYPE_URLS` gains exactly three types:
`/cosmos.group.v1.MsgVote`, `/cosmos.group.v1.MsgExec`, and
`/cosmos.group.v1.MsgSubmitProposal`. Every other `cosmos.group.v1` type stays
rejected, and the M6.4 `MsgExecuteContract` matrix is unchanged.

### 2.2 Two guard classes, because the payloads differ in kind

`MsgVote` carries `{proposal_id, voter, option, metadata, exec}` and `MsgExec`
carries `{proposal_id, signer}` — closed scalar payloads embedding no other
message. Their guard is structural: type URL → signer ↔ session-address
binding → closed field set with bounded values → canonical re-encode.

`MsgSubmitProposal` carries **`messages []Any`**. A plain type-URL entry would
let the relay carry arbitrary messages destined for the **policy account, which
is the contract's admin** — strictly worse than the `MsgExecuteContract` hole
M6.4 closed. Its guard has **six conditions**:

1. **Type URL** is `/cosmos.group.v1.MsgSubmitProposal`.
2. **Proposer ↔ session binding.** Every entry in `proposers` equals the
   session address; a proposal cannot be submitted on another's behalf.
3. **Group policy address** is one of the discovered program policies — not an
   arbitrary account.
4. **Each inner `Any`** is matched against the **closed template set** (§2.3):
   its type URL, its target contract address, its variant, and its full field
   set. An inner message that is not exactly a template instance is rejected.
5. **Byte-identical canonical re-encode per inner message** — M6.4's condition
   5, applied element-wise. This is what takes the guard out of a parser arms
   race: it does not try to detect every malicious shape, it demands the
   payload equal what this module would itself have built.
6. **`exec` is pinned** to the no-try value (§2.4).

### 2.3 The template set is closed and mirrors the contract exactly

Templates target the admin-gated `ExecuteMsg` variants in
[`contracts/src/msg.rs`](../../contracts/src/msg.rs): `UpdateConfig` (ten
optional fields), `SetHalted`, `PauseVault`, `UnpauseVault`,
`ClearPendingDelegations`. Bridge config joins if and when §14.3 resolves —
until then its template is **absent, not stubbed** (§7 Q1).

Each template declares its parameters with the **same bounds the contract
enforces**, so the composer cannot build a message the contract will reject for
a bound violation. Preflight remains convenience only; the contract is the
enforcement boundary (`SECURITY.md`). Numeric entry follows the repo-standard
**reject-never-clamp** rule, reusing `test/amount.test.ts`'s subject.

`UpdateConfig` is the interesting one: only supplied fields change, so the
composer must distinguish "not supplied" from "supplied as the current value",
and the **diff view** (§8.7's named requirement) shows current → proposed for
exactly the fields being changed, with untouched fields visibly untouched.

**One vocabulary, three consumers.** The template registry is the single source
of admin-action semantics: 7.2's decoder reads proposals *containing* these
messages, the confirm step *discloses* them, and the composer *builds* them.
All three import from the registry, so a proposal composed by the App and read
back by the App cannot be described differently (§4 invariant 6).

### 2.4 One dangerous subtlety: the `exec` field

Both `MsgVote` and `MsgSubmitProposal` carry an `exec` field that, set to
`EXEC_TRY`, attempts execution in the same transaction. That silently turns a
vote — or a submission — into a vote **plus** execution of whatever the
proposal contains, which after this PR includes admin program-ops.

**The guard pins `exec` to the unspecified/no-try value on both messages and
rejects anything else.** Execution is always a separate, separately-confirmed
`MsgExec` with its own decoded-payload disclosure. A user who intends both
performs two confirmations. This is §17.1 confirmation rigor: the danger tier
is not something to bundle into a cheaper action.

### 2.5 Would-fail simulation before sign

Per the §10.2 lifecycle: simulate before the wallet is asked to sign, and
surface a would-fail reason through `app/tx/reasons.ts` rather than letting the
user sign into a revert. Preflight remains **convenience only** —
`SECURITY.md`: the contract, and here the group module, remain the enforcement
boundary.

The governance-specific would-fail cases worth naming: for `MsgExec` —
proposal not yet passed, voting period not closed, `min_execution_period` not
elapsed, already executed, pruned; for submission — not a member, policy not
found, parameter out of bounds.

### 2.6 The decoded payload is shown before signing

§8.7 and §10.2: the confirm step shows the human summary above the exact
message JSON, reusing 7.2's `app/governance/decode.ts` rather than a second
vocabulary. For `MsgExec` this means showing **what the proposal will
execute**, not merely "execute proposal 12" — that is the whole of Grace's
question. For submission it means the exact `MsgSubmitProposal` JSON including
every inner message.

**Danger tier, framed accurately.** Submitting a proposal is not itself the
dangerous act — passage and execution are. The confirmation says so (this
proposes X; if it passes and is executed, X happens) without using that framing
to soften the disclosure. The console's `Admin.tsx` copy is the reference for
tone and specificity.

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **The relay admits exactly three new types, each only in canonical form.**
   Every other `cosmos.group.v1` type is rejected. *Gate:*
   `apps/web/test/broadcast-guard.test.ts`, extended with: each admitted type
   in canonical form accepted; unknown group types rejected; **the M6.4
   `MsgExecuteContract` matrix unchanged and still passing**.
2. **`MsgSubmitProposal` passes only when every inner message is an exact
   template instance.** *Gate:* matrix rows for — an inner message outside the
   template set; an inner message targeting a different contract; a proposal
   with **zero** inner messages; a proposal **mixing one valid template with
   one arbitrary message**; a valid template with one field mutated
   post-encode.
3. **Inner messages are canonically re-encoded individually.** A proposal is
   only as safe as its least-checked element. *Gate:* per-element canonical
   cases in `broadcast-guard.test.ts`.
4. **`exec` is pinned on both `MsgVote` and `MsgSubmitProposal`.** Any value
   that would attempt execution inside the same transaction is rejected
   (§2.4). *Gate:* an explicit case per non-permitted `exec` value on each
   message.
5. **Sole signer is the session address.** `voter`/`signer`/every entry in
   `proposers` must equal it; a mismatch is rejected server-side, not merely
   hidden in the UI. Policy addresses must be discovered program policies.
   *Gates:* signer-mismatch and foreign-policy cases in
   `broadcast-guard.test.ts`; the standing session-scope suite.
6. **Compose and decode agree.** A proposal built by the composer, read back
   through 7.2's decoder, yields the same summary — one vocabulary, three
   consumers (§2.3). *Gate:* the round-trip case in
   `test/governance-templates.test.ts`.
7. **The template set matches the contract.** Every template's parameter
   bounds equal the contract's, and no template exists for a variant not in
   `contracts/src/msg.rs`. *Gate:* `governance-templates.test.ts`, with a case
   that fails if a template's field set drifts from the contract schema.
   *Disproof:* the contract gaining an admin variant with **no** template — the
   drift test as described catches a template that no longer matches, but not a
   variant that never got one. The test must assert the mapping is **total in
   both directions** against the committed `cargo schema` output, so a new
   admin capability fails CI here rather than being quietly unreachable.
8. **The direct-admin path stays closed.** After this PR a *direct*
   `MsgExecuteContract` carrying an admin variant must **still** be rejected —
   admin ops reach the chain only through governance. *Gate:* the M6.4
   admin-variant rejection rows, unchanged and still passing. **This is the
   invariant most at risk of accidental erosion here.**
   *Disproof:* an admin action reaching the chain by a route the matrix does
   not model at all — a template whose inner message is itself a
   `MsgSubmitProposal` (governance nesting), a template targeting the group
   module rather than the contract (e.g. `MsgUpdateGroupMembers`, which changes
   who governs), or an `authz`/`MsgExec`-wrapped admin message. The matrix
   tests direct `MsgExecuteContract`; it must also prove these three are
   refused, because each reaches the same authority by a different path.
9. **Reject-never-clamp on every numeric input**, with contract bounds at
   entry, and `UpdateConfig` never silently changes an unsupplied field.
   *Gates:* the reused `test/amount.test.ts` subject;
   `test/governance-compose.test.ts` bounds and diff cases, including
   supplied-as-current-value.
10. **No key material; the wallet signs everything.** The flows build messages
    only; the relay forwards fully user-signed bytes; no privileged capability
    exists server-side to misuse. *Gates:* the unchanged 5.2 suites;
    `test/tx-confirm.test.ts` (disclosure = signed bytes).
11. **Preflight is convenience; the group module and the contract are the
    enforcement boundaries.** A would-fail reason never becomes an
    authorization claim, and a passing preflight never implies acceptance.
    *Gate:* `test/tx-preflight.test.ts`, including a
    preflight-passes-chain-rejects case.
12. **Confirmation rigor on privileged writes** (§17.1): consumer summary plus
    exact JSON on every flow; `MsgExec` discloses **what the proposal will
    execute**; submission discloses every inner message; danger-tier framing is
    accurate about proposal-vs-execution (§2.6). *Gates:*
    `test/tx-confirm.test.ts`; confirm assertions in the offline e2e.
13. **All inputs validated and bounded at entry.** `proposal_id` u64, `option`
    a closed enum, metadata length-bounded, template parameters
    contract-bounded. *Gate:* `test/tx-preflight.test.ts`; the guard field-set
    checks.
14. **Size and rate caps unchanged.** The existing relay caps apply to the new
    types with no exemption. *Gate:* the standing relay caps suite.
15. **Standing gates continue:** axe on the new route, i18n coverage,
    `check:bundle`, `pnpm -r` typecheck/test.

## 4b. Completeness obligations

Per [overview §7](2026-07-28-app-m7-governance.md). For this PR C1 is not a
persistence question — it is a **guard** question, and it is where a missed
cell is an exploit rather than a display bug.

### C1 — Cardinality inside guarded messages

| Collection | Max multiplicity | Guard obligation |
| --- | --- | --- |
| `MsgSubmitProposal.messages[]` | **N > 1**, unbounded by the module | Every element validated and canonically re-encoded **individually**; a per-element bound is enforced and an over-bound proposal is rejected, not truncated |
| `MsgSubmitProposal.messages[]` = **0** | legal on the wire | **Explicitly rejected** — an empty proposal is not a template instance |
| `proposers[]` | **N > 1** | **Every** entry must equal the session address, not just the first |
| Messages per **transaction** | **N > 1** — a tx may carry several governance messages | The guard runs over **every** message in the body; a tx that pairs one valid `MsgVote` with one unguarded message is rejected |
| `UpdateConfig` optional fields | 10, each present-or-absent → **2¹⁰ shapes** | The canonical builder omits absent fields; the re-encode comparison makes the shape space irrelevant to the guard, which is why condition 5 exists |

> *Disproof for the whole C1 block:* any construction where the guard's verdict
> is decided by **one** element of a collection while another element rides
> along unchecked. M6.4's batched-payment P1 was that failure in a decoder,
> where the cost was lost history; here the cost is an arbitrary message
> executed by the contract's admin. The matrix rows in §4 invariant 2 —
> zero-element, mixed valid+arbitrary, and post-encode mutation — exist
> specifically to falsify this.

### C2 — Wire bounds

Consumes 7.1's `packages/api-types/src/bounds.ts`. New bounds this PR
declares there rather than inline: `MAX_PROPOSAL_MESSAGES` (the guard's
per-proposal element cap), `MAX_PROPOSAL_METADATA_LEN`, `MAX_VOTE_METADATA_LEN`
if Q3 keeps it. **A guard bound written as a literal in `build.ts` is a review
failure** — the composer, the guard and the reader must not be able to disagree
about the same limit.

### C3 — Concurrency

| Read-then-write | Remedy |
| --- | --- |
| Double-submit of the same proposal (user double-clicks, or retries a timed-out broadcast) | Idempotent by construction on-chain — a second `MsgSubmitProposal` creates a **second proposal**, which is a real hazard rather than a duplicate row. The flow disables re-submit after broadcast and the confirm step states that submission is not idempotent |
| Vote raced against voting-period end | Chain-enforced; preflight surfaces it, chain decides (invariant 11) |
| `MsgExec` raced by two callers | Chain-enforced — the second fails as already-executed; the UI must render that as a benign outcome, not an error state |

No application-level uniqueness or cap enforcement exists in this PR, so C3's
default remedy (DB constraint) does not apply.

### C4 — State × affordance

Inherits 7.2's table and fills the affordance column that 7.2 left uniformly
read-only. **This is the row M6.4 got wrong** — an action panel rendered
against a state the action could not validly operate on.

| Proposal state | vote | execute | notes |
| --- | --- | --- | --- |
| open, not yet voted, session is member | **offered** | hidden | |
| open, already voted | hidden (x/group forbids re-vote — [VERIFY] via 7.1's drill) | hidden | if the chain *accepts* re-votes, this cell becomes "offered, as a change" |
| open, session not a member | hidden, with the reason stated | hidden | never a disabled control with no explanation |
| open, anonymous | hidden; connect prompt | hidden | |
| accepted, `min_execution_period` pending | hidden | **shown, disabled**, with the eligible-at time | disabled-with-reason, never hidden — the user needs to know it is coming |
| accepted, executable | hidden | **offered** (Q2 decides member-only vs anyone) | danger-tier confirm |
| executed (SUCCESS or FAILURE) | hidden | hidden | FAILURE is terminal; x/group does not permit re-exec |
| rejected / aborted / withdrawn | hidden | hidden | |
| **pruned** | hidden | hidden | no action can reference a proposal the chain discarded |
| `groupVersion` ≠ current | hidden | per state above | membership changed; voting is moot on a closed proposal |

*Gate:* a table-driven case per row in `test/governance-flows.test.ts`, plus
the e2e assertion that no action control renders for any terminal state.

### C5 — Plane precedence

Unchanged from 7.2's table for display. The one addition: **affordances are
decided from the live plane only.** An action must never be offered on the
strength of an indexed row that a live read has not confirmed — a stale
"accepted" that has since been executed would offer an execute button that
always fails. When the live read is down, actions are **hidden with the reason
stated**, never rendered optimistically. *Gate:*
`test/governance-flows.test.ts` live-down case.

- **Q3 — vote and proposal `metadata`.** x/group allows free-form metadata on

  plain-text field on proposals** (a human rationale is genuinely useful and

  before commit A — it changes the guards' field sets.
- **Q4 — multi-message proposals.** x/group permits several messages per
  proposal. Proposed: v1 composes **one** template per proposal, while the
  guard still validates element-wise so multi-message proposals submitted
  elsewhere read correctly in 7.2. Confirm before commit A; allowing several
  later is additive, restricting later is not.
- **Q5 — would-fail simulation depth for `MsgExec`.** A full simulation
  executes the proposal's inner messages. Proposed: simulate and surface the
  inner failure reason, since "passed but will fail to execute" is exactly what
  7.1's `executorResult` column exists to make visible. Confirm the simulation
  is side-effect-free against the node.
- **Q6 — does the composer surface `min_execution_period`?** A passed proposal
  is not immediately executable. Proposed: show it on the confirm step so the
  proposer knows the real timeline.

**Pre-build refinement gate:** revise §3 and Q1–Q6 in a same-file revision once
7.2 is merged and §14.3's status is known.

## 8. Implementation guidance (delegated executor)

**Read first, in order:** `SECURITY.md`;
**`2026-07-24-app-m6.4-operator-view.md` §2.5 and §4** — the guard idiom this
PR extends and the reasoning for each of its five conditions;
[the overview](2026-07-28-app-m7-governance.md) §4 D7; this document; app-spec
§10.2–§10.3, §12.3, §17.1; `contracts/src/msg.rs` in full for the admin
variants; `apps/console/src/pages/Admin.tsx` and `src/tx/messages.ts` as the
working reference; `apps/web/CLAUDE.md`.

**Ordering.** Commits A and B before C, without exception: **no flow exists
until the guard, the template registry and the rejection matrix pass.** Never
land a bare type-URL allowlist entry, even transiently within the working tree.

**Hard rules.**

- **Never create or push commits.** Ira reviews and commits.
- **The guard is not optional or reorderable.** Conditions run in the specified
  order, and the canonical re-encode is last and non-negotiable.
- **Every inner message is canonically re-encoded and compared byte-for-byte.**
  Structural validation is conditions 1–4 and is not sufficient alone.
- **Do not open the direct-admin path.** Admin variants must remain rejected as
  direct `MsgExecuteContract` messages after this PR (invariant 8).
- **Do not relax the `exec` pin** for convenience.
- **Do not add a template for a variant not in `contracts/src/msg.rs`,** and do
  not widen a parameter's bounds past the contract's.
- **Do not weaken a test to make it pass.**

**Stop-and-ask triggers:** any allowlist entry beyond the three named types;
any additional field in a guarded message, however convenient; any template
whose bounds you cannot trace to a contract check; any need to relax a guard
condition to make a legitimate message pass (that is a signal the canonical
builder is wrong, not the guard); any suggestion to bundle vote and execute
into one signature; any test weakened to pass.

### 10.1 Three things the plan did not have right

**The guard had to become async, and §2.2 condition 3 is why.** "Is this
`group_policy_address` one of the discovered program policies" is a live,
set-valued read (D1). The plan wrote the six conditions as one ordered guard —
correctly — but left `guardSignedTx` synchronous, and the three ways out were:
hardcode a policy address (the topology assumption `SECURITY.md` forbids), move
condition 3 into the route (splitting a guard whose ordering §8 calls
non-negotiable), or make the guard async. It is async, the read happens **only**
for a transaction that actually carries a submission, and an unresolvable or
**truncated** policy sweep rejects **503** — a status the plan did not name,
chosen because the submission may be perfectly well-formed and "we could not
verify the policy set" is the honest thing to say.

**Guard 6 had to become per-shape, and this is the near-miss worth recording.**
Through M6.4 every carried message held its signer in field 1 (`owner` /
`sender`), so one check outside the type dispatch served all of them. `MsgVote`
field 1 is a **varint proposal id** and `MsgSubmitProposal` field 1 is the
**policy address**. Left as it was, the outer check would have compared a
proposal id against a bech32 address and rejected every governance message —
which from outside looks exactly like a guard working. Each governance guard now
performs its own binding (`voter`, `signer`, and **every** entry of
`proposers`), and the field-1 check runs only for the shapes it is about.

**§4b C5's rule needed a field the plan did not anticipate.** "Affordances are
decided from the live plane only" cannot be answered by `plane`: for a CLOSED
proposal the honest display plane is the mirror (x/group prunes), so execute —
which exists precisely for accepted proposals — would have been permanently
hidden. `ProposalDetailVM.liveState` is therefore a separate nullable field
meaning "the chain, just now, confirmed the state we are about to act on", and
`loadGovernanceProposalData` now live-reads accepted proposals too. That widening
pays for itself: a successfully executed proposal is pruned in its own
transaction, so a failed live read on an accepted proposal is **itself** evidence
not to offer the button.

### 10.2 Smaller decisions taken during the build

- **The inner message's `sender` is pinned to the POLICY address**, not the
  proposer. x/group executes a proposal's messages as the policy account, which
  is the contract's admin; a message with any other sender could never execute.
  The plan's condition 4 named the type URL, contract, variant and field set;
  the sender belongs in the same list and is now checked and canonically
  re-encoded with them.
- **`update_config` supplying NOTHING is refused.** Every field is optional, so
  the contract would accept it and change nothing — a governance vote on a
  no-op. Refused at the boundary rather than composed.
- **`pause_vault.reason` is bounded 1..256** — a deliberate narrowing past the
  contract, which accepts an empty string. The reason is rendered to users as
  the vault's `pausedReason`, and "paused, no reason given" is the state
  `SECURITY.md`'s never-lie rule exists to prevent. Recorded here because §8
  forbids widening a bound past the contract's and this narrows one.
- **Uints above `Number.MAX_SAFE_INTEGER` cannot be composed.** A representation
  bound, narrower than the contract's `u64`, and stated rather than hidden:
  `JSON.stringify` cannot emit one without losing precision, and a canonical
  form that rounded its own input would defeat condition 5. It binds only two
  second-counts where the ceiling is ~285 million years.
- **The template registry's imports are TYPE-ONLY**, because `build.ts` imports
  it at runtime for the guard and the relay decodes untrusted bytes through
  `build.ts`. `templateSummaryKey` therefore returns an i18n KEY plus its params
  rather than a translated string — which also makes invariant 6's round trip a
  comparison of two resolved strings rather than of two tables.
- **`test/governance-compose.test.ts` did not gain the composer cases.** §3.3
  listed it; the bounds, canonical-output, round-trip and diff cases all landed
  in `test/governance-templates.test.ts` instead, because they are properties of
  the registry and splitting them across two files would have separated a bound
  from the declaration it tests. 7.2's `governance-compose.test.ts` is unchanged.
- **The offline e2e write assertions went into `e2e/governance.spec.ts`, not a
  separate `e2e/governance-write.spec.ts`.** §3.3 named the second file. Offline
  the corpus is ungoverned and there is no session, so every write assertion is
  necessarily about an ABSENCE — no action control in any state, the composer's
  anonymous gate — and those read as amendments to the existing "renders
  anonymously" spec rather than as a suite of their own. Two of that spec's
  assertions had to change with this PR anyway (the read-only note is now false,
  and one connect prompt now legitimately exists inside the actions section),
  which is the same file. `e2e-live/governance-write.spec.ts` IS separate, as
  planned, because that is where the write path has a chain to act on.
- **`e2e-live/governance-write.spec.ts` needs a new key,
  `E2E_LIVE_GOV_MEMBER_KEY`** — a funded throwaway devnet key that is also a
  group member. The M6.4 precedent exactly: proposing and voting are
  membership-gated, so the generic `E2E_LIVE_SIGNER_KEY` cannot cover them any
  more than it could cover the enrol leg. Absent, those legs skip loudly and the
  gate assertions still run.
- **The canonical goldens for the three governance messages are HEX, not
  captured-transaction hashes.** §3.1 asked for golden vectors; the operator
  form (re-encode a captured devnet tx, require the hash to match) is not
  available because no governance transaction the App built exists in the corpus
  — 7.1's drill used the CLI. The hex goldens pin field order, the `exec`
  omission and the omitted-default rules so a re-encode is a visible diff;
  proving the canonical form is the ACCEPTED form remains `e2e-live`'s job until
  a transaction is captured. Worth a fixture-capture follow-on.

## 2. Mechanism

### 2.1 The `admin:` scope (ADR-001 Decision 2 amendment, decided at M7.0)

Today `RouteAuth` is `"public" | "address" | "internal:notifier"` and
assertions carry `scope: "address:<bech32>" | "internal:notifier"`. Neither
fits: §8.8 data is program-wide rather than address-scoped, but it is not
public either. **`admin:<bech32>` joins the union.**

Two alternatives were rejected at M7.0. Re-verifying membership *inside*
`services/api` would give the read API an outbound LCD dependency and put a
chain read in every admin request path — it has no chain client by design.
Keeping admin analytics in `apps/web` fails on ADR-001 Decision 1:
`app_writer` has **no grants on `indexed`**, so the web tier structurally
cannot read the history these panels need. So the web tier — which already
holds the LCD client and the role logic — mints the scope, and the API verifies
it in-process exactly as it verifies the other two.

**The minting rule is the security-critical part.** `detectRoles()` caches for
`ROLE_CACHE_TTL_SECONDS` (60 s), which is correct for *rendering* an operator
view and wrong for *minting a privilege*: a 60 s stale admin is 60 s of
retained capability after membership is revoked. **Minting an `admin:`
assertion performs a fresh on-chain group-membership read and bypasses the
cache**, and a degraded read mints nothing (401 downstream) rather than a
hopeful assertion. That is what makes app-spec §12's "re-verify group
membership on-chain per session refresh, not per cached role" a mechanism
instead of a description.

The envelope is otherwise unchanged — HMAC over `{scope, iat, exp}`,
`exp − iat ≤ 60 s`, constant-time compare, 10 s forward-skew bound,
fail-closed with no key — and the golden vectors stay cross-pinned in both
suites.

### 2.2 The admin gate is a capability gate, never a safety gate

`SECURITY.md`: never gate a safety property on who calls. Nothing behind
`/admin` is a write to program state; every panel reads data derivable from
public chain history, aggregated. The gate exists because the *aggregation* is
a product surface for administrators, not because the underlying facts are
secret. Stated explicitly so nobody later reasons "it's behind the admin gate,
therefore it's safe to expose X."

The only write is the incident acknowledgment, and it writes only to `app`.

### 2.3 Incident acknowledgment crosses a schema boundary

ADR-001 Decision 1 settled this: incidents are computed facts owned by the
indexer, and the acknowledgment is an app action, so it lives in an
**`app`-schema `incident_acks` table referencing the incident id**. The web
tier never writes `incidents`. There are no cross-schema foreign keys; the
reference is by id, validated on write against a live read of the incident.

Columns: `incidentId`, `acknowledgedBy` (a public bech32 address),
`acknowledgedAt`, a nullable `unacknowledgedAt` so reversal preserves the audit
trail rather than deleting it, and a bounded `note` (§7 Q2).

### 2.4 The funnel counters are aggregates by construction

§14.10 as resolved: the tension is that the program wants to know whether its
due-diligence material converts, while `SECURITY.md` forbids anything that
could deanonymize a wallet. Most analytics designs resolve that by promising
restraint. This one resolves it structurally — **there is no per-person record
to restrain.**

- **Storage:** one `app`-schema table, `funnel_counters`, keyed `(stage, day)`
  with an integer `count` and **no other columns**. No row per visit, session,
  wallet or device — the row *is* the aggregate.
- **Stages:** the closed §8.8 funnel — `visit`, `due_diligence_depth`,
  `connect`, `first_deposit` — plus a closed **page-class** enum on `visit`.
  `first_deposit` is derived from public chain history, not incremented from
  web behavior.
- **Increment site:** **server-side, in the route loader.** No client script,
  no beacon, no pixel, **no cookie, no client identifier**. A beacon design
  would fight §12.3's requirement that transacting pages function with
  third-party scripts blocked, and a consent banner would ask permission for
  something that collects nothing about the person.
- **Retention:** a stated, enforced window recorded in the allowlist comment.

**The honesty consequence is accepted, not hidden.** Without an identifier the
counters cannot deduplicate: a returning reader increments `visit` again. These
are **event totals, not unique people**, and the surfaces say so. The funnel's
terminal stage is exact (chain-derived) while its top is not, so the view must
not imply uniform precision across stages. Acquiring an identifier to make a
prettier number is not an available trade.

**Increment must not become a failure mode or a write amplifier.** A counter
write failure is logged and swallowed — a metrics table never takes a
user-facing surface down. And an upsert on one integer per `(stage, day)`
concentrates every visit of a day onto one row; commit C measures this on the
dev DB the way `operator_payments` was measured, and if contention is real the
mitigation is a bounded in-process buffer flushed periodically — **not** a
per-visit row, which would reintroduce exactly the per-event record this design
exists to avoid.

### 2.5 The dashboard is indexed-derived and honest about it

Every §8.8 panel derives from the `indexed` schema through
`services/api/src/derive.ts`, with the standard envelope carrying `meta.source`
and heights. Panels degrade **individually**: a panel whose input is
unavailable says so and shows "n/a", never 0 and never a blank that reads as
"nothing happened". The `operator-data.test.ts` honesty matrix is the idiom.

**Upkeep timeliness** derives from crank tx timing already in the indexed
history — epoch run after eligibility, capture-signal cadence gaps,
service-redemption latency. No new indexing.

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **The `admin:` scope is enforced in-process, regardless of network layout.**
   `address:` on an admin path → 403; `internal:notifier` on an admin path →
   403; `admin:` on another address's personal path → 403;
   absent/expired/bad-signature → 401. *Gate:* the `ADMIN_PATHS` matrix in
   `services/api/test/cross-address.test.ts`, alongside the registry-derived
   `PERSONAL_PATHS`/`INTERNAL_PATHS` matrices.
2. **Minting bypasses the role cache.** An `admin:` assertion is minted only
   after a **fresh** on-chain membership read; a degraded read mints nothing.
   *Gates:* `apps/web/test/roles.test.ts` cache-bypass case;
   `apps/web/test/assertion.test.ts` degraded-read case. **This is what keeps a
   revoked admin from retaining capability for 60 s.**
   *Disproof:* the **assertion's own lifetime** carrying the capability past
   revocation anyway. A fresh read at mint time does not reduce the window to
   zero — it reduces it from *60 s cache + 60 s assertion* to *60 s assertion*.
   Claiming this invariant eliminates stale-admin access would be false;
   confirm what the residual window actually is and state it in the ADR
   amendment rather than implying none exists.
3. **Assertion envelope unchanged.** *Gate:* the cross-pinned golden vectors in
   both suites — either side drifting fails its own CI.
4. **The admin gate is a capability gate, not a safety gate** (§2.2). No write
   to program state exists behind it. *Gate:* the registry's GET-only
   enforcement (`test/envelope-contract.test.ts`) — `services/api`
   structurally cannot register a write.
5. **`app`-schema data minimization.** `incident_acks` and `funnel_counters`
   carry exactly the §2.3/§2.4 columns. *Gate:* the extended
   `apps/web/test/app-schema-allowlist.test.ts` — a migration alone fails CI.
6. **Funnel counters are never keyed by wallet, session or device.**
   `FunnelCounter`'s columns are exactly `{stage, day, count}`, and the
   forbidden-substring denylist is extended for this model with `address`,
   `wallet`, `session`, `device`, `ip`, `user`, `fingerprint` — so a column
   named `address` trips here even though it is legitimate on other `app`
   models. *Gate:* `app-schema-allowlist.test.ts`. **This is the master plan §4
   security-executable check that gates `apps/web` CI from this PR onward.**
   *Disproof:* columns that are individually innocuous but **jointly
   identifying**. The denylist checks column *names*, not cardinality: a
   sufficiently granular `page_class` crossed with `day` can isolate a single
   rare visitor without any column being called `address`. Q3's enum membership
   is therefore a privacy decision, not a taxonomy decision, and the gate
   cannot make it for us.
7. **No call site can leak an identifier into the counter model.** `increment`
   accepts a closed stage enum and an optional closed page-class enum — no
   address, no request, no headers in its signature. *Gate:*
   `apps/web/test/funnel-counters.test.ts` signature and call-site cases.
8. **No client script, no beacon, no cookie, no third-party analytics.**
   Increments happen server-side in loaders; pages function with third-party
   scripts blocked (§12.3). *Gates:* the standing `check:bundle`; an offline
   e2e case asserting no analytics request leaves the page.
9. **The counters never take a page down.** A write failure is logged and
   swallowed. *Gate:* `funnel-counters.test.ts` failure case plus a
   loader-with-DB-down case.
10. **The web tier never writes `incidents`.** Acknowledgment writes only to
    `app`; `app_writer` has no `indexed` grants. *Gates:* the standing
    `services/indexer/test/integration/grant-boundary.test.ts`;
    `apps/web/test/incident-acks.test.ts`.
11. **Acknowledgment is bound to the session address**, never a
    client-supplied actor, and reversal preserves history rather than deleting.
    *Gates:* `incident-acks.test.ts`; the standing
    `apps/web/test/session-scope.test.ts`.
12. **Every admin route returns only what is derivable from public data.** No
    endpoint returns a per-wallet behavioral record. *Gates:*
    `services/api/test/admin-endpoints.test.ts`; review of the `derive.ts`
    additions.
    *Disproof:* an **aggregate that identifies by inference**. "Derivable from
    public data" is not the same as "does not single anyone out": a cohort of
    one, or the TVL-concentration panel (Q7), can name a holder without
    returning an address. Every panel needs a stated minimum group size below
    which it renders "n/a", and that threshold is part of this invariant rather
    than a display nicety.
13. **All query params bounded at entry.** *Gate:*
    `services/api/test/query.test.ts` plus the registry-driven harness
    (automatic for new routes).
14. **Panels degrade individually and honestly.** A missing input renders "n/a"
    with a reason, never 0 and never a blank. *Gate:*
    `apps/web/test/admin-data.test.ts` degradation matrix.
15. **The funnel view never overstates precision.** Stage totals are labeled as
    event totals, not unique people, and the view does not imply uniform
    precision across stages (§2.4). *Gate:*
    `apps/web/test/funnel-view.test.ts`.
16. **Retention is stated and enforced**, not aspirational. *Gate:* the
    retention job's test plus the allowlist comment recording the window.
17. **`/admin` is not reachable by a non-admin**, and a degraded role read
    renders the explicit "we could not check" state rather than granting or
    silently 404ing. *Gates:* `admin-data.test.ts`; anonymous and non-admin
    cases in `e2e/admin.spec.ts`.
18. **Logs carry no identifiers alongside counter or acknowledgment events.**
    *Gate:* the standing log-scrubbing discipline; a case in
    `funnel-counters.test.ts`.
19. **Standing gates continue:** axe on the new route (both themes), i18n
    coverage, `check:bundle`, envelope/read-only/rate-limit harnesses,
    `pnpm -r` typecheck/test.

## 4b. Completeness obligations

Per [overview §7](2026-07-28-app-m7-governance.md).

### C1 — Natural keys & cardinality

| Key / collection | Uniqueness | Max multiplicity | Handling |
| --- | --- | --- | --- |
| `FunnelCounter` PK `(stage, day)` | one aggregate per stage per UTC day | **1 by construction** — the row *is* the aggregate | PK; increments are `ON CONFLICT DO UPDATE SET count = count + 1` |
| `IncidentAck` key | **[DECIDE before commit B]** | see below | — |
| Acks per incident | — | **N > 1** if several admins ack, **N > 1 over time** if Q3's reversal is re-acked | key must accommodate it |
| Incidents per ack | 1 | 1 | reference by id, no cross-schema FK (ADR-001) |
| Cohort rows per epoch | — | unbounded in epochs | paginated / windowed, C2 |

> **`incident_acks` has the one undecided key in this PR, and it is the M6.4
> shape.** `incidentId` alone is the obvious choice and is wrong the moment two
> admins acknowledge, or one admin re-acknowledges after Q3's reversal — later
> writes would silently overwrite earlier ones, which is exactly how batched
> payments were lost. *Disproof:* two acknowledgments that must both survive.
> **Resolve to `(incidentId, acknowledgedBy, acknowledgedAt)` or an surrogate
> id with a uniqueness constraint on the live ack, before commit B.** Do not
> default to `incidentId`.

### C2 — Wire bounds

Consumes 7.1's `packages/api-types/src/bounds.ts`; every §8.8 payload array
declares its bound there and imports it on both sides. The ones that matter,
because each grows without operator action:

| Payload | Note |
| --- | --- |
| cohort retention series | grows with **epoch count** — the `yield_by_epoch` shape from PR #19 exactly. Server trims and flags; the client cap is strictly larger |
| adoption / net-flow per epoch | same |
| upkeep-timeliness distribution | bucketed, so bounded by bucket count, not by history |
| incident feed | paginated under the shared `MAX_PAGE_LIMIT` |
| funnel counters | bounded by `stages × retention days`, both closed — state the product |

*Gate:* `packages/api-types/test/bounds.test.ts`, extended.

### C3 — Concurrency

**The highest-value row in this PR** — one of the M6.3 P1s was precisely a
read-then-write on a cap.

| Read-then-write | Remedy |
| --- | --- |
| Funnel increment | **`ON CONFLICT DO UPDATE SET count = count + 1`** — atomic in one statement, never read-then-write. This also settles §2.4's contention question: the hazard is row lock wait, not lost updates |
| Incident ack under two concurrent admins | **DB uniqueness constraint** per C1's resolved key, not an application-level "already acked?" check |
| Ack / un-ack raced | Constraint plus an explicit conflict answer; never last-write-wins on a nullable `unacknowledgedAt` |
| `admin:` assertion minting | No shared mutable state — the fresh read is per-request by design (§2.1). The cache is deliberately **not** consulted, so no cache-stampede remedy is needed |

### C4 — State × affordance

| Incident state | Affordances |
| --- | --- |
| open, unacknowledged | acknowledge |
| open, acknowledged by session admin | un-acknowledge (Q3), showing who and when |
| open, acknowledged by **another** admin | acknowledge is **not** re-offered as if unacked; shows the existing ack |
| closed, acknowledged | read only; history retained |
| closed, never acknowledged | read only; no retroactive ack |
| indexed read down | feed dims with reason; **no ack control**, since acking an incident you cannot see is not a coherent action |

Panel-level: every §8.8 panel has `{data, cold-start / below-minimum-cohort,
input unavailable}` and renders "n/a" with a reason for the latter two — never
0, never blank (invariant 14).

### C5 — Plane precedence

Simpler than the governance surfaces: **every §8.8 panel is indexed-only**, so
there is no live/indexed contest to resolve. The obligations that remain:

- the envelope's `meta.source` and heights are surfaced on the dashboard, so a
  stale indexed read is visibly stale rather than presented as current;
- panels degrade **individually** — one unavailable input does not blank the
  page or, worse, render the others without saying which is missing;
- the **funnel panel** is the one cross-plane case, and only in the
  split-delivery scenario this merge eliminates: with 7.6 in the same PR it is
  simply another indexed panel. If the merge is ever undone, its "not yet
  collected" state returns as a C5 obligation.

## 7. Open questions

- **D20 / Q1 — cohort window definitions.** Proposed: cohort by first-deposit
  epoch, curves at 1/3/6/12 epochs, with a stated minimum cohort size below
  which the curve renders "n/a" rather than a noisy line — the §14.12
  cold-start discipline applied to cohorts. Confirm before commit D.
- **Q2 — does `incident_acks` carry a `note`?** Free operator text in a
  backup-critical `app` table. Genuinely useful ("acked, known upstream
  outage") and not PII by construction, but unbounded human text. Proposed:
  include it, bounded, with the allowlist comment stating the reason. Confirm
  before commit B — adding it later is another design-review event.
- **Q3 — the page-class enum's membership.** §8.8 names "due-diligence depth",
  implying shallow vs deep Learn material. Proposed: a small closed set
  (`learn_index`, `learn_deep`, `spec_link`, `validators`, `market`) chosen so
  no class identifies a niche page a rare visitor would read. Confirm before
  commit B — the enum is in the migration.
- **Q4 — retention window.** Proposed: 400 days of day rows, then aggregate to
  monthly. Long enough for year-over-year, short enough to be a real bound.
  Confirm before commit B.
- **Q5 — is `day` UTC?** Proposed: yes, stated in the column comment, so the
  series is not silently discontinuous across a DST boundary.
- **Q6 — does the Learn funnel view ship publicly or admin-only?** The 7.6 row
  says "the Learn funnel view"; §8.8 puts the funnel behind `/admin`. Proposed:
  the panel is admin-only and the Learn page gets no public funnel display. If
  a public view is wanted, its honesty labeling needs more thought than the
  admin panel's. Confirm before commit D.
- **Q7 — TVL concentration presentation.** §8.8 names it; concentration is a
  distributional fact that can identify a large holder by inference. Proposed:
  banded shares (top-1/top-5/top-10 as percentages) with **no addresses and no
  absolute amounts**. Confirm before commit D — the one §8.8 panel with a
  privacy edge.

  curves at 1/3/6/12 epochs. `MIN_COHORT_SIZE = 5` first depositors, below which
  the curve renders "n/a (cohort below the minimum)" rather than a noisy line.
  The threshold is invariant 12's minimum group size, not a display nicety — it
  is applied server-side in `derive.ts` and rides the payload as data, the
  `/redemptions/stats` precedent, so the web tier never re-decides it.
- **Q2 — `incident_acks` carries a bounded `note`.** `VarChar(500)`, nullable,
  allowlisted with the reason recorded in the allowlist comment. It is operator
  text about an *incident*, not about a person; the bound is what keeps it from
  being an unbounded free-text column in the one non-rebuildable schema.
- **Q3 — page-class enum: three classes, one per real loader call site.**
  `learn_index`, `validators`, `market`.
  The proposed five were first confirmed, then cut to three when implementation
  showed two of them are **not server-observable**: Learn is a single route with
  in-page progressive disclosure (no deep route to load), and the spec/audit
  links are plain external anchors. Observing `learn_deep` or `spec_link` needs
  client instrumentation, which §2.4 forbids outright — so shipping them would
  mean either breaking that rule or carrying two enum members nothing ever
  writes. Confirmed by Ira 2026-07-31.
  The privacy property Q3 was asked for is unaffected and strengthened: three
  broad classes name no niche page, so the cardinality hazard invariant 6's
  disproof identifies is smaller than under the five-member set. Adding a class
  later is a migration plus an allowlist review, which is what §14.10 intends.
- **Q3a — `due_diligence_depth` is a load of `/validators` or `/market`.**
  §8.1.7's funnel reads "arrive → scroll depth → due-diligence sections →
  connect → first deposit", and **scroll depth is not measurable here at all**
  without a client script. The stage is therefore defined as what a loader can
  honestly observe: the visitor went past the front page into the program's
  evidence surfaces. Those two routes increment `visit` (with their page class)
  and `due_diligence_depth` together. The surfaces say what the stage means
  rather than letting "due-diligence depth" imply scroll tracking.
- **Q3b — the page class is folded INTO the stage enum, not a fourth column.**
  §2.4 describes "a closed page-class enum on `visit`" while invariant 6 pins
  `FunnelCounter`'s columns at exactly `{stage, day, count}`; a `pageClass`
  column would satisfy the first and break the second, and §8's hard rules make
  adding one a stop-and-ask. So the stored enum is the product —
  `visit_learn_index`, `visit_validators`, `visit_market`,
  `due_diligence_depth`, `connect` — and the *call-site* API keeps stage and
  page class as separate closed types over a discriminated union, so a caller
  still cannot pass a page class to a stage that has none. Three columns, and
  the impossible call is unrepresentable.
  `first_deposit` is **not** an enum member: it is derived from chain history
  (§2.4), so a member for it would be one nothing may ever write.
- **Q4 — retention: 400 days of day rows.** Long enough for year-over-year,
  short enough to be a real bound. Recorded in the allowlist comment and
  enforced by the notifier tick's sweep, alongside the notification sweep.
- **Q5 — `day` is UTC.** Stated in the column comment; the series cannot go
  silently discontinuous across a DST boundary.
- **Q6 — the funnel view is admin-only.** The panel lives on `/admin`; the Learn
  page gets no public funnel display. §8.8 puts the funnel behind `/admin`, and
  a public view's honesty labeling needs more thought than the admin panel's.
  Consequence for §3.4: `app/components/learn/funnel-view.tsx` and the
  `e2e/learn.spec.ts` extension are **not built**; the panel is
  `app/components/admin/funnel-panel.tsx` and its state matrix is covered by
  `apps/web/test/admin-data.test.ts`.
- **Q7 — TVL concentration: banded shares only.** Top-1 / top-5 / top-10 as
  percentages of TVL, with **no addresses and no absolute amounts**, and the
  whole panel renders "n/a" below `MIN_COHORT_SIZE` depositors — a top-1 share
  in a program of three holders identifies a holder by inference even without an
  address (invariant 12's disproof).
- **C1 — `incident_acks` key: surrogate `id` plus a partial unique index** on
  `(incidentId, acknowledgedBy) WHERE unacknowledgedAt IS NULL`. History rows
  accumulate rather than being overwritten, and the "one live ack per admin per
  incident" rule is a DB constraint, not an application-level "already acked?"
  check (C3). `incidentId` alone is rejected as §4b states.

**§2.4's buffering question: NO BUFFER — measured, not guessed.** The remedy C3
already names — `ON CONFLICT DO UPDATE SET count = count + 1` — is one atomic
statement, so the hazard was never lost updates, only row-lock wait on the
single hot `(stage, day)` row. Measured on the dev database
(`apps/web/scripts/measure-funnel-contention.sh`, reproducible; postgres
17-alpine, 2026-07-31), with **every** client deliberately on the same row:

| Concurrency (all one row) | Mean latency | Throughput | Failed |
| --- | --- | --- | --- |
| 1 client (uncontended floor) | 0.21 ms | 4 765 tps | 0 |
| 8 clients | 2.05 ms | 3 894 tps | 0 |
| 32 clients | 10.06 ms | 3 182 tps | 0 |

And the property that matters: **82 000 concurrent increments produced a stored
count of exactly 82 000** — zero lost updates under 32-way contention, which is
what makes the single-statement upsert the whole remedy rather than a partial
one. Even the 32-client figure is a fraction of any page's budget, and the call
is fire-and-forget so the loader never waits on it at all.

A bounded in-process buffer is therefore **not built**: it would add a
flush-on-shutdown loss window and a second failure mode to avoid a cost that is
not there. Should a later measurement change that, the mitigation is the buffer
— **never** a per-visit row, which reintroduces exactly the per-event record
this design exists to avoid.

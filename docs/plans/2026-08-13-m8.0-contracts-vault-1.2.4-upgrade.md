## 1. What this PR delivers

ProvLabs cut the first formal vault releases carrying `AcceptAsset`:
v1.2.0 (2026-07-21) through **v1.2.4 (2026-08-12, latest)**. The contract's
vault seam was last reconciled against vault `main` as of 2026-07-08/09
(`contracts/src/vault_ext.rs`, spec §14), which predates the entire 1.2.x
line. This PR:

1. Updates the `vault_ext.rs` shim to the v1.2.4 wire format (`AcceptAsset`
   carries the full `Payment`).
2. Restructures the epoch crank's slash write-down for the new pause rules
   (repricing a held asset requires a paused vault; `AcceptAsset` requires an
   unpaused vault).
3. Adds a defensive NAV restate guarding against the new drained-entry
   removal behavior.
4. Re-pins the devnet node image to the published
   `ghcr.io/provlabs/vault-dev-node:v1.2.4-rc2` tag and fixes the bootstrap
   script for the changed `tx vault create` CLI.
5. Re-runs the drills and updates spec/status/comments in the same change
   (SECURITY.md spec-parity rule); retires the feature-probe compatibility
   language in favor of a version pin (IMPLEMENTATION-STATUS §3, 2026-07-13
   decision: "when the vault release lands: pin the version").

provwasm-std 2.8.0 and provwasm-test-tube 0.5.0 remain the latest upstream
releases (verified crates.io 2026-08-13), so the shim stays hand-rolled and
the money path still cannot run in CI — the "NOT covered" headline stands.

## 3. Design decisions

**D1 — Pause-bracketed sandwich with plain `PauseVault`/`UnpauseVault`, not
`RepriceVault`+`resume`.** The write-down becomes: pause → mark → unpause →
settle → pause → restore (+ reward deposit) → unpause, all inside the single
atomic epoch transaction, so no user message can interleave anywhere in the
sequence (same §9.9 atomicity argument as today). `RepriceVault` would save
two messages but adds a new shim type, couples the unpause to
strict-pause-taken-by-self semantics, and splits the pause-window idiom into
two mechanisms. The contract is both asset manager and NAV authority, so
plain pause/unpause (provwasm-std types, already in use) is available in
every bracket. Revisit only if the gas profile forces it.

**D2 — Unconditional defensive 1:1 NAV restate before the crank's first
settlement leg.** Emitted once per crank iff the crank emits any settlement
leg (`settle`, `write_down`, or `deployable` non-zero). Legal live in every
reachable state: if the entry was drain-removed (R4) the principal holds zero
receipt (removal implies drained) → not-held → allowed; otherwise the entry
is 1:1 and the restate `PricesSameAs` → allowed. A mid-sandwich 0-price
entry is unreachable across cranks (single-tx atomicity). Cost: one message.
The alternative — querying `NavValue` to restate conditionally — needs a new
query shim (provwasm-std 2.8.0 predates the NAV queries) for no safety gain.

**D3 — Devnet image: pin `ghcr.io/provlabs/vault-dev-node:v1.2.4-rc2`.**
The published dev-node tag carrying vault v1.2.4 is `v1.2.4-rc2` (note the
leading `v`; verified pullable 2026-08-13); it becomes the `IMAGE` default
in `dev-node.sh`. If the pin ever stops resolving, that is a hard blocker
for T4–T6 — pause there rather than substituting `:latest`. The
local-build fallback (Provenance checkout whose `go.mod` pins
`github.com/provlabs/vault v1.2.4` — a clean version pin now, not the
main-checkout `replace` described in IMPLEMENTATION-STATUS §5) stays
documented in `infra/devnet/README.md` for offline work, with `IMAGE` set to
the local tag. Either way the default stops being `:latest`: the entire
point of 8.0 is that "compatible vault" is a pin, not a probe.

**D4 — Terms can never diverge between the two settlement messages.** The
create-payment and accept-asset messages for one settlement are built from a
single `Payment` value by one helper (T2), making R1's exact-match
requirement structural rather than a discipline. A unit test decodes both
messages from the crank output and asserts the terms are identical (T3).

## 8. As-built notes (implementation, 2026-08-13)

Four things the plan got wrong or could not know, recorded here rather than
silently absorbed:

0. **D2's "one restate per crank" was not enough — it is now one per par
   settlement.** The plan placed a single par restate before the crank's first
   settlement leg. That leaves a reversion hole *within* one crank: the return
   leg settles receipt OUT of the vault, and on a full unwind (every minted
   receipt matured, `staked + unbonding == 0`) it drains the vault's holding,
   which makes the module remove the NAV entry — and the deploy leg later in
   the same crank is then rejected for having no entry, reverting the epoch.
   That is the forced-empty-vault edge the soak already models, so it is
   reachable, not theoretical. The return and deploy legs each carry their own
   restate now; the write-down extraction deliberately does not, since it must
   settle at the marked-down price. Pinned by
   `every_par_settlement_is_preceded_by_a_par_restate`, which also asserts the
   write-down leg is the sole exception.

1. **The "combined path" in T2 is unreachable.** `plan_return` sets
   `settle = min(matured, liquid)`, so `write_down > 0` implies
   `settle == liquid` implies `rewards_dep == 0`: a crank that writes down
   never has a reward surplus to deposit. The close-out bracket is still
   written to carry either or both (it stays correct if that changes), and
   the exclusivity is pinned by
   `write_down_and_reward_deposit_are_mutually_exclusive` so the dead branch
   is intentional and monitored. The planned third test vector was dropped.
2. **Drills cannot cover the write-down bracket this month.** `RunEpoch`
   eligibility is a calendar-month rollover of block time, block time on a
   single-node devnet is the container's real wall clock, and the dev image
   has no libfaketime — so a fresh contract gets exactly one crank.
   `p2p-drill.sh` verified phases 0–3 and stopped at phase 4 with
   `too soon: next run allowed at 2026-09-01`. The deploy settlement, the par
   restate on a live vault holding the receipt, and the v1.2.4 exact-match
   approval are confirmed on chain; the return, burn, expedite and write-down
   phases need a session spanning a month rollover. Recorded in
   `IMPLEMENTATION-STATUS.md` §3/§4. This constraint is pre-existing
   (`calendar-drill.sh` documents it) and applies to every drill session, not
   to this change.
3. **T8's grep expectation was too strong.** Surviving "feature probe"
   references live in app-side plans, `app-spec.md`, and
   `packages/fixtures/` — all inside the app 8.0 scope this PR excludes (§7),
   including that script's own `:latest` image default. Retiring them belongs
   with the fixture re-capture, since changing the wording without
   re-capturing would assert a verification that has not happened.

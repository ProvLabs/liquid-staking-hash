## 1. Origin & problem statement

The overview's §4.2 register schedules four carryover items here, and every
one of them already has a **recorded remedy** — this PR executes recordings,
it does not open design questions. Overview §3 row 8.0b: *"Carryover small-fix
tranche (app-side code hygiene with existing recorded remedies)."*

**CO-9 — the Prisma dual-generate race** (7.5–7.6 §10.4; `apps/web/CLAUDE.md`
"CI gates"). `apps/web/prisma/schema.prisma:23` and
`services/indexer/prisma/schema.prisma:24` each declare a
`generator client` with **no `output`**, so both write the same hoisted
`node_modules/@prisma/client` and the last `prisma generate` in a process tree
wins, globally. This is not hypothetical: it broke the `db-grants` CI job at
7.5–7.6 round 4 — `@nvhash/db-indexed`'s generate step runs **all** generators
of the indexer schema, including the default-output one, so it left the shared
client holding `indexed` models and `prisma.incidentAck` was `undefined`. The
workaround shipped then (`test:db` self-generates,
`apps/web/package.json:17`) makes one suite order-independent; the shared
mutable global stays, and every future schema or CI step re-rolls the dice.
The recorded durable fix: *"an explicit `output` for one of the two schemas
(the `@nvhash/db-indexed` precedent)"* — the precedent being the `dbIndexed`
generator in the same indexer schema file, which already declares
`output = "../../../packages/db-indexed/generated/client"`
(`services/indexer/prisma/schema.prisma:34–37`).

**CO-10 — the duplicated NAV helper** (m3 §3.1; app-spec §9.4 revision (d)).
`navHashPerShare` exists twice: the shared copy in
`packages/api-types/src/amounts.ts:33` (produced for the API's historical NAV
series at 3.1) and the original in `apps/web/app/learn/amounts.ts:39`. The
two are golden-pinned to the same fixture values from both suites
(`packages/api-types/test/amounts.test.ts`, `apps/web/test/amounts.test.ts`),
so drift fails CI — but the pin is damage control for a duplication the spec
already records as temporary: *"the web's switch to the shared copy is a
recorded follow-on"* (app-spec §9.4(d); restated in the api-types file header
as "stays services-only"). Web call sites today:
`apps/web/app/learn/learn.server.ts:26,90` and
`apps/web/app/portfolio/portfolio.server.ts:24,234`, plus the duplicated
`HASH_EXPONENT`/`SHARE_EXPONENT` constants in both files.

**CO-11 — the web-only collection bounds** (7.1 §3.5 delivery note). 7.1 built
the C2 mechanism — `packages/api-types/src/bounds.ts` plus its table-driven
`test/bounds.test.ts` — and adopted the governance, portfolio-metrics and
admin families into it. Its delivery note records the residue verbatim, and
`bounds.ts:341–347` carries it as the file's own "NOT YET COVERED" foot
comment: the collection bounds on `/validators` (500),
`/portfolio.active_redemptions` (500), `/market.depth_bands` (32) and
`.bridged_supply` (64), plus `ValidatorRow.failing_reasons` (32), *"still
live only in the web Zod schema with no declared producer cap"* — the
literals at `apps/web/app/api/api.server.ts:184,197,215,227,260`. That is
exactly the PR #19 defect shape the file exists to close: a producer that
legitimately outgrows a consumer literal nulls the whole derived read. And
two of these producers really are unbounded today:
`listValidators` reads the entire registry with no `take`

permissionless).

**CO-12 — audit gates in CI** (M0-era tail). `SECURITY.md` (Dependencies and
supply chain, lines 108–109): *"Run `cargo audit` / `npm audit` before

## 2. Mechanism

### 2.1 One default-output generator, or none (CO-9)

The race exists because **two** generators write one implicit destination. The
fix gives the **indexer's** `generator client` an explicit
`output = "./generated/client"` (resolved relative to the schema file →
`services/indexer/prisma/generated/client`, gitignored like the db-indexed
output — no binary artifacts in git), leaving `apps/web` as the **sole**
writer of the hoisted `@prisma/client`.

Why the indexer moves and not the web (§7 Q1 carries the alternative):

- The indexer runs under plain `tsc` and Node — no bundler anywhere in its
  path. Its 16 import sites (10 under `src/`, 6 under `test/`) are mechanical
  specifier swaps, mostly `import type`.
- `apps/web`'s five Prisma import sites are all deliberate *dynamic*
  `await import("@prisma/client")` expressions inside `*.server.ts` models
  (`session`, `alerts`, `push`, `incident-acks`, `funnel-counters`), tuned so
  the React Router/Vite build never pulls the client toward the browser
  bundle. Pointing them at a filesystem-relative generated directory puts a
  large generated artifact with native-engine loading in front of the SSR
  bundler — a new build-layer hazard introduced by the fix for a build-layer
  hazard.
- The precedent lives in the same file: the `dbIndexed` generator already
  outputs to an explicit path, and after this change **every** generator in
  the indexer schema does, so `pnpm --filter @nvhash/db-indexed run generate`
  (which runs all of that schema's generators) stops touching the hoisted
  client entirely — the exact step that broke `db-grants`.

Import sites switch through **one new re-export module**,
`services/indexer/src/prisma.ts`, re-exporting `PrismaClient`, `Prisma` and
the model types from the generated path; the 16 sites import from it. A future
output move then touches one file. The generated directory joins `.gitignore`.

What deliberately does **not** change: every `prisma generate && …` script
prefix stays. Its reason changes — the generated client is gitignored and must
exist before `tsc`/vitest, which is why `typecheck` has always generated first
— but the step is still load-bearing, and the `apps/web/CLAUDE.md` note that
says "do not remove it as redundant" is rewritten as that constraint rather
than as the race narrative (§6). The `db-grants` NOTE comment at
`app-ci.yaml:300–305` is rewritten the same way: the web `test:db`
self-generate stays as the belt (a suite must not depend on job step order),
and the race explanation becomes "apps/web is the only default-output
generator; the indexer's clients generate into explicit paths".

The mechanism gets a gate, not a comment: a **new**
`services/indexer/test/prisma-generator-output.test.ts` parses
`prisma/schema.prisma` and asserts every generator block declares an `output`
that resolves outside `node_modules`. Reverting the fix fails CI in the
indexer's own suite rather than in whichever downstream job happens to run
generates in the unlucky order.

### 2.2 One `navHashPerShare`, imported (CO-10)

`apps/web/app/learn/amounts.ts` drops its `navHashPerShare`, `HASH_EXPONENT`
and `SHARE_EXPONENT` declarations and **imports the trio from
`@nvhash/api-types`** (already a workspace dependency of the web app; already
exported at `packages/api-types/src/index.ts:130`). The module keeps its
display-only helpers (`formatBaseAmount`, `bpsToPercent`,
`formatHashCompact` — these have no API-side twin and stay web-local) and
**re-exports** the shared trio, so the two call-site files
(`learn.server.ts`, `portfolio.server.ts`) keep their `~/learn/amounts`
import and the change surface stays minimal. `@nvhash/api-types` is
zero-runtime-dependency and client-safe, so the re-export adds nothing to the
bundle-hygiene story.

The golden suites: `packages/api-types/test/amounts.test.ts` becomes the
single authoritative pin of the formula's fixture values. The
`navHashPerShare` describe block in `apps/web/test/amounts.test.ts:19–36`
**stays**, now exercising the re-export — it is four cheap cases, and it is
the closest thing available to a gate on the single-declaration property
itself: if someone re-introduces a local implementation, the web goldens run
against *that* copy and fail the moment it drifts by one floor step. The
honest residual (also §4 invariant 4): a re-introduced duplicate that is
*faithful* passes both suites — the mechanism prevents drift, and only review
prevents re-duplication. Both file-header comments that describe the
duplication as a pending follow-on are rewritten in the same commit (§6).

### 2.3 The five bounds join the registry, with real producer caps (CO-11)

Adoption per the file's own instruction: *"giving each a producer-side
constant … a change to those endpoints rather than to this one."* Five new
pairs, named **for their quantity** — the 7.5–7.6 round-2 finding #1 (an
epoch cap borrowed for a holder denominator silently overstated every
concentration band) is the naming rule's reason, and no constant here is
reused across quantities:

| Constant (producer / `_WIRE` consumer) | Quantity | Proposed producer | Existing web literal (becomes the `_WIRE` value) |
| --- | --- | --- | --- |
| `MAX_VALIDATOR_REGISTRY_ROWS` | `/validators.validators[]` — registry rows ever enrolled, live + churned | 300 | 500 (`api.server.ts:197`) |
| `MAX_ACTIVE_REDEMPTIONS` | `/portfolio.active_redemptions[]` per address | 400 | 500 (`api.server.ts:260`) |
| `MAX_MARKET_DEPTH_BANDS` | `/market.sample.depth_bands[]` | 16 | 32 (`api.server.ts:215`) |
| `MAX_BRIDGED_SUPPLY_ROWS` | `/market.bridged_supply[]` — one per remote chain | 32 | 64 (`api.server.ts:227`) |
| `MAX_FAILING_REASONS` | `ValidatorRow.failing_reasons[]` per row | 16 | 32 (`api.server.ts:184,341,362`) |

Producer values are proposals — confirmed at the §7 gate before commit C. Each
is sized from the producing system, not the happy path (§4b C1): the live
validator set is capped at 100 by the contract but the registry accumulates
churn, so 300 is generous headroom over the cap without pretending the table
is bounded; redemption enqueueing is permissionless, so 400 per address is a
griefing bound, not a product expectation; depth bands and bridged chains
have **no v1 producer at all** (the market/bridge samplers are the deferred
§14.3 cluster, overview CO-45 — `latestMarket` serves `{sample: null,
bridged_supply: []}` until they exist), so their producer caps bound future
sampler output and are exercised only by fixtures until then. Stated rather
than hidden: the market half of this adoption is dormant-path hardening.

The producer side **trims and flags, never silently truncates** — the
governance idiom (`derive.ts:900–938`), applied per collection:
`validators_truncated` on `ValidatorsPayload`, `active_redemptions_truncated`
on `PortfolioSummary`, `depth_bands_truncated`/`bridged_supply_truncated` on
`MarketSummary`, and per-row `failing_reasons_truncated` on `ValidatorRow`
(the `messages_truncated` per-row precedent). Reads that are unbounded today
gain `take: MAX + 1` (detect-then-trim, the `MAX_GOV_VOTES_PER_PROPOSAL + 1`
idiom at `reader-prisma.ts:400`) — which also closes the two genuinely
unbounded SELECTs named in §1 under the API's own "no SELECT is left
unbounded" convention. Trim direction is stated per collection: validators
keep registry order (moniker asc) and the flag says the *set view* is partial;
active redemptions are newest-first (`enqueuedAt desc`, already the read
order), so a trimmed set drops the oldest.

Consumer side: the five literals in `apps/web/app/api/api.server.ts` become
imports of the `_WIRE` constants (the file already imports fourteen `_WIRE`
constants; this extends the same import). The new flags enter the web Zod
schemas as **`.optional()`** booleans for deploy skew — services/api and
apps/web ship as separate components at 8.4, so a newer web against an older
API must not reject the whole payload over a missing honesty flag. The
absent-flag state is carried to the surfaces as *unknown*, treated
conservatively (§4 invariant 7 and the nullable-gates-affordance answer).

Registry mechanics: the five pairs join `WIRE_BOUNDS`, a new
`CORE_BOUNDED_FIELDS` family list joins the existing
governance/admin cross-checks in `bounds.test.ts` (add-an-array-forget-the-
pair stays a CI failure for this family too), and the `bounds.ts:341–347`
"NOT YET COVERED" foot comment is rewritten to say the registry is complete
for the v1 wire surface (§6) — a comment standard obligation, since the
comment would otherwise describe a gap that no longer exists.

### 2.4 Audit gates: fail closed, exceptions are named and owned (CO-12)

**Contracts side** — a new `audit` job in `contracts-ci.yaml`:
`cargo install cargo-audit --locked` (cached via the workflow's existing
rust-cache pattern) then `cargo audit` against `contracts/Cargo.lock`.
Unfixable advisories are ignored **only** via `contracts/.cargo/audit.toml`
[VERIFY: cargo-audit's documented config location relative to the cargo
workspace root — confirm on first run], where TOML comments carry
**owner + reason + review-by date per entry**. No `--ignore` flags in the
workflow, no severity floor: the contract custodies staked funds, and an
advisory that is genuinely inapplicable earns a named entry, not a threshold.

**App side** — a new `audit` job in `app-ci.yaml`:
`corepack pnpm audit` at the workspace root (production **and** dev
dependencies — the build chain decides what reaches the served bundle, so dev
advisories are in scope), plus `npm audit` in `apps/console` (outside the
pnpm workspace, so the root audit cannot see it). pnpm exceptions live in the
root `package.json` under `pnpm.auditConfig.ignoreCves` / `ignoreGhsas`
[VERIFY against the pinned `pnpm@11.13.0` — both keys are supported in
current pnpm majors; confirm the exact key names before wiring]. JSON carries
no comments, so the owner/reason obligation gets a mechanism instead of a
convention: a tracked register,
`docs/security/dependency-audit-exceptions.md` — one row per ignored
advisory id across **all three ecosystems** (cargo, pnpm, npm): id, package,
owner, reason, review-by date — and a **new** first-party check,
`scripts/check-audit-exceptions.mjs`, run by both audit jobs, which fails CI
if any id ignored in `audit.toml` or `auditConfig` lacks a register row (and
vice versa, so the register cannot rot into fiction). That is the "explicit
ignore-list with owner+reason per entry" this PR chooses **over** a blanket
`--audit-level` downgrade or `continue-on-error` — a blanket allow silences
every future advisory behind the first inconvenient one (§4 invariant 2's
attacker-gain line).

Console has no native npm ignore mechanism; until an exception is actually
needed there the job runs `npm audit` bare, and the register documents that a
console exception, if ever needed, routes through the same check script
(§7 Q5). The 8.4b constraint is recorded where it bites: when 8.4b re-adds
`@cosmjs/*` at audited versions, this job is the gate that proves "audited" —
the reviewed-dependency event the overview §7 map already assigns to it.

**Trigger posture** (§7 Q4 carries the alternative): the audit jobs run
**unguarded** on every PR and push to main — deliberately outside both
workflows' `changes` filters, because the input that moves is the advisory
database, which is never in the diff. Both jobs are minutes, and the
step-guard pattern exists to skip *expensive* work, not cheap gates. No cron
trigger in this PR: a schedule event would also wake every other job through
the fail-open `changes` logic, and the release points `SECURITY.md` actually
names (8.4's pilot deploy, Phase B S1, 8.5) all pass through PRs where the
gate runs anyway.

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **Exactly one generator writes the hoisted `@prisma/client`.** The indexer
   schema's generators all declare explicit outputs; `apps/web` is the sole
   default-output generator in the repo. *Gate:* **new**
   `services/indexer/test/prisma-generator-output.test.ts`. Not an
   authorization or honesty control — a build-correctness invariant — so no
   attacker-gain line; the failure it prevents is a test tier silently
   binding to the wrong schema's client, which is the "gate beside the
   defect" enabler 7.5–7.6 §10.4 documented.
   *Disproof:* a third schema added later with no `output` — the per-package
   test covers only the indexer's file, which is why the sole-writer rule is
   also stated in `apps/web/CLAUDE.md` where the next schema author will read
   it.
2. **A known advisory cannot ship silently.** Both CI pipelines fail on any
   advisory in `Cargo.lock` / `pnpm-lock.yaml` / console `package-lock.json`
   that is not an explicit, owned exception. *Gates:* the two `audit` jobs;
   `scripts/check-audit-exceptions.mjs` failing on any ignored id without a
   register row. *What an attacker gains if it does not hold:* a published
   vulnerability in a dependency of the custodial contract build, the signing
   web tier, or the served bundle rides into a release unexamined — the
   supply-chain half of `SECURITY.md`'s threat surface, on a codebase whose
   web tier constructs messages wallets sign.
3. **Exceptions are per-advisory, never a blanket.** No `--audit-level`
   floor, no `continue-on-error`, no workflow-side `--ignore` flags. *Gate:*
   the consistency check plus review of the workflow diff (the check verifies
   the lists; only review can see a `continue-on-error`). *What an attacker
   gains if it does not hold:* one inconvenient advisory becomes a standing
   allow-all, and every **future** advisory below the floor is silenced with
   it — the gate reports green while enforcing nothing.
4. **One NAV formula.** `navHashPerShare` has one implementation, in
   `@nvhash/api-types`, consumed by both tiers. *Gates:* the golden suites in
   both packages, now pinning one function's values from two sides. *What an
   attacker gains if it does not hold:* nothing directly — but the program
   gains the ability to lie to itself: a chart whose historical series and
   live point disagree by a floor step is a small honesty defect on the
   surface users price against (never-lie-about-state). *Disproof:* a
   faithful re-duplication — value-identical copies pass every golden. The
   mechanism closes drift; §9 directs review to check for re-duplication.
5. **Every v1 wire collection bound is one declaration, producer inside
   consumer.** The five adopted pairs end the registry's own recorded
   incompleteness. *Gates:* `packages/api-types/test/bounds.test.ts`
   (pairing, positivity, headroom, and the new `CORE_BOUNDED_FIELDS`
   cross-check). *What an attacker gains if it does not hold:* a
   permissionless actor who can grow a collection — anyone can enqueue
   redemptions against their own address, and validator churn grows the
   registry — can push a producer past a consumer literal, and the web
   schema then rejects the **whole** payload: a targeted blanking of the
   validators page or a holder's portfolio, at the cost of dust
   transactions. *Disproof:* a bounded collection that crosses the boundary
   and is in no `*_BOUNDED_FIELDS` family — the cross-checks only see
   enumerated families, which is why the foot-comment rewrite in §6 states
   the completeness claim where the next endpoint author will read it.
6. **No unbounded SELECT behind a public endpoint.** The registry and
   active-redemption reads gain `take` caps. *Gates:* the **new**
   `derive.test.ts` truncation cases (cap applied); review of the
   `reader-prisma.ts` diff for the `take: MAX + 1` idiom. *What an attacker
   gains if it does not hold:* a memory/transfer amplifier on a rate-limited
   but unauthenticated read — grow the rows, then have every `/validators`
   hit carry them.
7. **A trimmed collection says so; an unknown flag is never "complete".**
   Producer trims flag explicitly; the web surfaces render partial-data
   labels on flag-true and claim no completeness on flag-absent. *Gates:*
   the **new** derive cases (flag emitted); **new** cases in
   `validators-data`/`portfolio-data`/`market-data` suites (label on true,
   conservative copy on absent). *What an attacker gains if it does not
   hold:* concealment — an operator whose failing validator sorts past the
   cap disappears from the public set view with no marker that the view is
   partial; a holder's oldest active redemptions vanish from their own
   portfolio as a matter of display fact.
8. **The audit gate never weakens an existing gate.** The new jobs are
   additive; no `changes`-filter edit touches the existing jobs' guards.
   *Gate:* workflow diff review — the `changes` job outputs and every
   existing `if:` are byte-unchanged.
9. **Standing gates continue:** grant-boundary + both `test:db` suites (the
   proof commit A did not disturb client generation), byte-golden tx suites,
   broadcast guard, allowlist gates, `check:bundle` (the proof commit B's
   re-export pulled nothing server-only toward the client), axe, i18n
   coverage, `pnpm -r` typecheck/test, Biome, shellcheck.

**Nullable-gates-affordance question (overview §8):** the one nullable this
PR introduces that gates anything is the optional truncation flag on the web
schemas. `undefined`/absent means **unknown, not "not truncated"**: the view
models carry the tri-state explicitly (invariant 7), and the conservative
treatment is to withhold the completeness claim, never to display partial
data as the whole. No other nullable gains or loses a gating role here.

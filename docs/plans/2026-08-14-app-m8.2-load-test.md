## 1. Origin & problem statement

Master plan §2 row 8.2: *"Load test + rate-limit tuning on the public API"*
(2026-07-13-app-implementation-plan.md:214). Master plan §4's Load layer row
names the tool and the second half of the scope: *"k6 (or team standard) …
Public API under load with rate limits; indexer keeps lag under the DATA
DEGRADED threshold during backfill"* (:335). The overview §3 row 8.2 names the
inputs from the carryover review: CO-20 (the holder-lifecycle fold — measured
**349 ms at 400 k transactions / 40 k holders and 1 407 ms at 1.2 M / 120 k,
superlinear, uncached, on every `/admin` load**; recorded remedy: indexer-side
materialization, contingent on this PR's thresholds) and CO-21 (the accepted
seq scans, the `operatorPaymentTotalsFor` planner flip, and deep `OFFSET` —
**re-measure only; no speculative indexes**).

What exists:

- **The rate limiter names this PR as its own follow-on.** The limiter is a
  first-party in-memory fixed window (`services/api/src/rate-limit.ts`), and
  its header says so: *"A shared store (e.g. Redis) for multi-instance
  deployments is a deployment-time concern (load-test + tuning), not a scaffold
  decision"* (rate-limit.ts:5–8). The limits are env-tunable and bounded:
  `RATE_LIMIT_MAX` default **120**, `RATE_LIMIT_WINDOW_MS` default **60 000**
  (`services/api/src/config.ts:39–41`). Rate limiting is step 1 of the pinned
  429→404→405→401→400→403 pipeline, so it protects unknown paths too
  (`services/api/src/handler.ts:143–149`), keyed by `clientKey` — socket
  address unless `TRUST_PROXY=true` admits `x-forwarded-for`
  (`services/api/src/http-server.ts:23–31`, default off, config.ts:47–50).
- **Measured numbers already on record**, all from the dev DB: the three-form
  cursor comparison at 300 k payments on one valoper (14.8 s OFFSET chunking /
  6.2 s Prisma OR / **1.6 s row comparison** — api-design-notes.md:60–70); the
  `operatorPaymentTotalsFor` planner flip with the covering index **built,
  measured, and rejected — no effect** (:88–97); deep `OFFSET` accepted
  linear-by-construction with `MAX_PAGE_OFFSET` deliberately the shared bound
  (:99–104); the two structurally-tiny index-less tables `validator_registry`
  and `epoch_snapshots` (:106–109); the CO-20 fold figures
  (services/api/CLAUDE.md:83–87).
- **No load harness and no committed seeder.** The `test:db` suite seeds a
  handful of fixed rows (`services/api/test/integration/reader.test.ts`); the
  400 k / 1.2 M databases behind the recorded figures were seeded ad hoc during
  the M7.5–7.6 round-2 review and the tooling was not kept. The only committed
  measurement script is `apps/web/scripts/measure-funnel-contention.sh`. Every
  recorded number is therefore currently **unreproducible by anyone else**.
- **The DATA DEGRADED threshold** is `TOLERANCES.lagHeights = 120n` — ~5 s
  blocks, ≈10 min of trailing before `indexer_lag` opens
  (`services/indexer/src/reconciler/tolerances.ts:22–27`), evaluated every
  `RECONCILE_INTERVAL_MS` (default 30 s, indexer CLAUDE.md §Reconciler).
  Deliberately **not env-tunable** — widening it would silence the honesty
  alarm.

Two facts this plan corrects against its own sources, found while writing it:

1. **The Load row's lag criterion is unsatisfiable as phrased.** "Indexer keeps
   lag under the DATA DEGRADED threshold during backfill" cannot hold for any
   from-zero backfill deeper than 120 heights: `computeLag` exempts only the
   never-committed cold start (indexedHeight 0, no incident —
   `services/indexer/src/reconciler/lag.ts:36–48`); the moment the first
   window commits at a low height, `over` is true and `indexer_lag` opens —
   **which is the honesty machinery working correctly**, not a failure. §2.6
   restates the criterion as two measurable properties (steady-state margin;
   catch-up rate with a correct open→close incident cycle), and §6 amends the
   master-plan row to match.
2. **"Rate-limit tuning" is aggregate-channel sizing in the shipped topology.**
   The web tier calls this API server-side (`API_URL: http://api:8080`,
   infra/dev/compose.yaml:206; `apps/web/app/api/api.server.ts`), forwards no
   `x-forwarded-for` (no occurrence under `apps/web/app`), and `TRUST_PROXY`
   defaults off — so **every end user's traffic shares one limiter key: the
   web container's address**. Per-client limits as deployed bound the SSR
   tier's aggregate, not individual users. §7 Q2 carries the decision this
   forces.

## 2. Mechanism

### 2.1 Tool: k6, confirmed — in a container, per ADR-002

The master plan names k6; this plan confirms it rather than substituting.
What the choice must provide, and k6 does [VERIFY: grafana/k6 current docs at
implementation time]:

- **Executable thresholds** — pass/fail criteria declared in the scenario
  (`thresholds` on rate/duration metrics) that make the run itself exit
  non-zero. This is what §4b C7 demands: a threshold held by a process exit
  code, not by a report someone must read.
- **Scenario stages** (ramp, sustain, burst) and per-endpoint tags, so one run
  produces per-surface percentiles.
- **An official container image** (`grafana/k6` [VERIFY: exact tag pinned at
  implementation]), which keeps ADR-002 intact: the harness joins the
  `nvhash-dev` network as a compose service and hits `http://api:8080`
  in-network — **no host tooling, no downloaded binary, nothing in git but
  scripts** (no-binary-artifacts rule). k6 scenarios are plain JS files
  executed by the k6 runtime, not Node — they join no pnpm workspace and add
  no npm dependency (SECURITY.md dependency discipline).

Rejected alternative, recorded: a Node-based generator (autocannon or
hand-rolled) inside the existing tools container would avoid a new image but
reimplements stages/thresholds/tag-aggregation that k6 ships, and the master
plan already names k6 — "or team standard" exists for a standard we do not
have.

### 2.2 Seeded scales: the repo's two measured depths, made reproducible

Commit A lands `services/indexer/scripts/seed-load.ts` (the indexer owns the
`indexed` schema and its writer role — ADR-001 Decision 1; seeding as
`indexer_writer` mirrors how `test:db` seeds today). Properties:

- **Deterministic by seed.** One PRNG seed parameter; the same seed produces
  byte-identical rows, so a measurement is reproducible and a regression is
  re-runnable (the sim-suite seed-reproducibility discipline applied to load
  data).
- **Two named profiles matching the recorded scales** — the
  measure-at-several-depths practice, anchored to the numbers already in
  `services/api/CLAUDE.md`:
  - `depth1`: 400 k transactions / 40 k holders;
  - `depth2`: 1.2 M transactions / 120 k holders.
  Both include: a **skewed `operator_payments` distribution with one valoper
  holding ~300 k payments** (reproduces both the cursor-measurement depth and
  the "one valoper holds a large share" planner-flip condition,
  api-design-notes.md:62–64, 88–97); a **heavy holder address** with a six-digit
  transaction history (drives the `/portfolio/metrics` full-history fold and
  the CSV streams at their worst case); epoch snapshots, validator registry
  rows, redemption requests, gov proposals/votes, and reconciler runs sized so
  **every route in the registry returns populated data** — an empty payload
  load-tests JSON serialization, not the read path.
- **Synthetic addresses only** (SECURITY.md data minimization; overview §7
  row): every bech32 address is derived from the seeded PRNG, valid-shape for
  the API's zod address schema, and never sourced from any real chain history.
- **Devnet-only guard, fail closed:** the script refuses to run unless the
  target URL matches the dev-stack shape (the `postgres:5432/nvhash` /
  `localhost:5433` dev patterns) or an explicit `SEED_LOAD_I_KNOW=1` override
  is set — the SECURITY.md "drills point at nothing else" rule extended to
  seeding.

Run via `./dev pnpm --filter @nvhash/indexer run seed:load -- --profile depth2
--seed 1` against `./dev pg up` (host 5433). Seeding truncates the tables it
owns first, so re-runs are idempotent (reset-and-rebuild, not migrate — the
standing pre-8.4a posture).

The registry (`services/api/src/routes.ts:1140–1166`) is the enumeration
authority — the scenario suite is written against it and §4 invariant 7 keeps
the two from drifting. Scenarios, tagged per endpoint:

not read as a full-stack number).

Latency scenarios run with a raised test-profile `RATE_LIMIT_MAX` (it is
bounded env config, config.ts:39 — max 100 000); the `rate-limit` scenario
runs at the production default. Both configurations are recorded in the

### 2.4 Named thresholds and the contingency criteria — decided in advance

**Values below are RATIFIED as proposed (2026-08-14, Ira; §7.1)** — no longer
provisional. The *structure* — which metric, at which depth, gating what — was
always the plan.
All percentiles at `depth2` unless stated; error rate excludes deliberate
429s from the `rate-limit` scenario.

| # | Threshold | Pass | On breach |
| --- | --- | --- | --- |
| T1 | `public-mix` p95, 50 rps sustained | ≤ 250 ms; non-429 error rate 0 | investigate; no index without a measured, recorded case (§4 inv. 4) |
| T2 | `/portfolio/metrics` p95 — typical address / heavy address | ≤ 400 ms / ≤ 2.5 s | record; remedy design is a follow-on, not this PR |
| T3 | **`/admin/holder-cohorts` p95 under the `admin` scenario** | ≤ 2.5 s **and** concurrent `public-mix` p95 degrades < 50 % while the dashboard loads | **commit D lands** (the CO-20 recorded remedy) |
| T4 | `csv-export` completion at heavy depth | completes; API RSS delta during stream ≤ 64 MB (the streaming property, routes.ts csvStream) | streaming regression — fix, don't cap |
| T5 | `rate-limit` correctness at production defaults | ceiling exact; `Retry-After` ≤ window; full recovery post-reset | limiter defect — fix in this PR |
| T6 | `deep-offset` worst case (offset 1 M) | ≤ 2 s and growth not worse than linear | stays accepted (api-design-notes.md:99–104); re-open **only** on measured visible cost, and never by lowering `MAX_PAGE_OFFSET` per-route |
| T7 | indexer under load (§2.6) | steady-state lag < 120 heights over ≥ 30 min of full-suite load; backfill catch-up rate ≥ 10× head-advance; `indexer_lag` opens during deep catch-up and closes on convergence | ingestion or reconciler defect — measured, then designed |

**T3's decision criteria, stated in advance (the scope's requirement):**
commit D lands iff, at `depth2`, either (a) `/admin/holder-cohorts` p95
exceeds 2.5 s, or (b) the admin scenario measurably degrades concurrent public
p95 by ≥ 50 % — i.e. the fold's cost is either felt by the admin or exported
to the public. If neither holds at `depth2`, D does **not** land; the fold's
superlinearity stays recorded in `services/api/CLAUDE.md` with the new
measured points appended, and re-opening waits for a depth that breaches.
**Confirmed 2026-08-14 (§7.1): the values stand as proposed, and a T3 breach
lands commit D with no second decision round** — only a breach of the
criterion's *shape* (a defect elsewhere producing the number) returns for a
decision.

### 2.5 Rate-limit tuning as measured outcomes

Tuning is: run the suite at the production defaults, observe where the
ceiling binds against the measured aggregate demand of one SSR tier at target
concurrency (§1 fact 2), and record the resulting numbers — the chosen
`RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_MS`, the measured demand that justified
them, and the burst headroom — in the delivery notes and in
`api-design-notes.md` (§6). Constraints, from the overview §7 conformance map:
**tuning changes limits, never removes a bound**; the fixed-window
boundary-burst property (up to 2× max straddling a reset — inherent to the
algorithm, rate-limit.ts:63–84) is characterized and recorded, and replacing
the algorithm is out of scope unless T5 fails. If defaults change,
`config.ts`, `.env.example`, `test/rate-limit.test.ts` /
`test/client-key.test.ts` expectations, and `services/api/CLAUDE.md` move in
the same commit (C).

### 2.6 Indexer lag vs the DATA DEGRADED threshold — the honest restatement

Two measurements against the full `./dev` stack (`infra/devnet/stack.sh up`,
chain at `http://dev-node:1317`), replacing the Load row's unsatisfiable
phrasing (§1 fact 1):

1. **Steady-state margin.** With the devnet chain producing blocks and the
   full k6 suite loading the API on the **shared Postgres**, every worker
   stream's lag stays < 120 heights for ≥ 30 min. The API is SELECT-only
   (`api_reader`), so the coupling under test is Postgres contention, not
   locks.
2. **Backfill catch-up.** Reset the indexer's schema mid-run (`./dev pg
   reset` + migrate — the standing reset-and-rebuild posture) and measure
   catch-up: heights/s indexed under concurrent API load, versus the chain's
   head-advance rate (~0.2 heights/s at ~5 s blocks). Pass: catch-up ≥ 10×
   head-advance (a 10-min outage heals in ≈ 1 min), **and** the
   `indexer_lag` incident opens once the backfill's first window commits
   beyond tolerance and closes on convergence — asserted as correct behavior,
   the complement of 8.1's kill-drills. The devnet chain's history depth
   bounds this measurement (the E-CAL mid-month constraint); the depth
   actually available at run time is recorded with the result.

- **Maintenance:** in the chain-events worker's `write` phase, idempotent SQL
  in the standing style (conditional-update arms; first `swap_in` sets
  `firstDepositHeight` once; `exitHeight` recomputed from the running
  position the worker already tracks). Rebuildable from chain by
  construction; replay from 0 equals resume (the `-replay` suite extends).
- **Read swap:** `holderLifecycles(limit)` becomes an indexed
  `ORDER BY "firstDepositHeight" ASC LIMIT n` over the table — same shape
  (`HolderLifecycleFacts` carries no address, and the address column is never
  selected), same ASC-trim convention, same `holders_truncated` flag. No API
  wire change at all.
- **Equality gate (C7):** a new
  `services/indexer/test/integration/holder-lifecycle-materialization.test.ts`
  seeds transactions, runs the worker, and asserts the table equals the old
  window-function query's output over the same rows — breaking the
  maintenance SQL fails a test that computes the truth both ways.

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **Load tests never touch real user data.** Every seeded address is
   synthetic (PRNG-derived); the seeder refuses non-dev targets. *Gates:*
   `services/indexer/test/seed-load.test.ts` (**new**) — determinism,
   synthetic-derivation, fixture-disjointness, and guard-refusal cases.
   *Attacker-gain:* none directly (this is a self-harm guard) — but a seeder
   that ran against a real mirror would fabricate history under real
   addresses, i.e. make the program lie about state at scale; the guard is
   what makes "synthetic only" a mechanism instead of an intention.
2. **Rate limits are tuned, never removed, and stay unspoofable.** Whatever
   values C lands, the bound exists on every path, 429 precedes all other
   handling, and the client key honors `x-forwarded-for` only under
   `TRUST_PROXY` (http-server.ts:23–31). *Gates:* the standing
   `test/rate-limit.test.ts` + `test/client-key.test.ts`, updated in the same
   commit as any default change; the envelope-contract harness continues to
   iterate every route. *Attacker-gain if mis-tuned high or removed:*
   unmetered request volume against the shared Postgres — and this API's
   expensive reads (the 1.4 s fold, the full-history metrics fold) make each
   request a multiplier, so the gain is cheap denial of the indexer's DB and
   with it the program's public honesty surfaces going stale. *Attacker-gain
   if the key were spoofable:* limit evasion via header rotation — already
   gated by `client-key.test.ts`, re-asserted after any tuning.
3. **The harness targets devnet only.** `run.sh` accepts in-network service
   names only; the compose profile hardcodes `http://api:8080`; no
   environment override reaches a public host. *Gate:* a refusal case in the
   harness's own check (shellcheck-covered script; the refusal exercised in
   the Q1 lane's smoke run). *Attacker-gain:* n/a — the property protects
   third parties (a load tool pointed at a public endpoint is a DoS tool);
   that is exactly why it is enforced in the runner rather than documented.
4. **No speculative index or schema "fix" rides in on a measurement.** The
   CO-21 set is re-measured and its recorded decisions stand unless the new
   measurement shows the visible cost the notes name as the re-open trigger
   (api-design-notes.md:88–104). *Gate:* process — the §9 review checks the
   diff contains no migration outside commit D and no new index anywhere;
   the delivery notes must carry the EXPLAIN captures that would justify any
   exception. Named honestly: this is a review gate, not an executable one —
   the executable complement is that any schema change *would* trip the
   allowlist suite, which has no new entries outside D.
5. **Commit D (if landed) adds no new information class and the address never
   crosses the wire.** The table carries only already-public columns behind
   the existing allowlist gate; `HolderLifecycleFacts` stays
   `{firstDepositHeight, exitHeight}`. *Gates:* `schema-allowlist.test.ts`
   (extended entry); the standing `admin-endpoints.test.ts` bech32 sweep over
   POPULATED payloads; the new materialization equality suite asserts the
   fact shape at the port. *Attacker-gain:* a lifecycle row that carried
   behavioral columns beyond the two heights would be a per-wallet dossier a
   public-data sweep can't see — the allowlist is what makes "aggregate-only"
   checkable.
6. **The load run cannot silence the honesty machinery.** T7 asserts the
   `indexer_lag` incident opens during deep catch-up; tolerances stay in code
   and untouched (tolerances.ts:1–11 — not env-tunable by design). *Gates:*
   the T7 scenario's assertion in the harness; the standing reconciler-alarm
   integration suite. *Attacker-gain if a tolerance were widened to pass a
   load test:* a silenced DATA DEGRADED banner — users read stale figures
   presented as fresh, the precise lie §12.1 exists to prevent.
7. **The scenario suite covers the whole registry, structurally.** A route
   added to `routes.ts` without a scenario tag fails a check that diffs the
   registry against the suite's tag list. *Gate:*
   `services/api/test/load-coverage.test.ts` (**new**, unit-level: imports the
   registry, parses the scenario tag manifest from `infra/load/`) — the
   registry-derived-harness idiom (api-design-notes.md:161–172) applied to
   the load suite. *Attacker-gain:* n/a (completeness property); the failure
   mode is a surface shipping unmeasured.
8. **Assertion machinery is exercised, not weakened.** The harness mints real
   HMAC assertions with the dev key; no bypass flag is added to the API.
   *Gates:* the standing cross-address/`ADMIN_PATHS` matrices continue
   unchanged; the `rate-limit` scenario's 401 checks on bad assertions.
   *Attacker-gain if a bypass existed:* the whole ADR-001 Decision 2 boundary.
9. **Standing gates continue:** envelope contract, read-only 405 matrix, query
   bounds, `pnpm -r` typecheck/test, shellcheck on new scripts, Biome on
   harness JS.

**Nullable-gates-affordance question (§8 v2):** the one nullable this PR can
introduce is `holder_lifecycles.exitHeight` (commit D). `NULL` means **"no
exit observed as of `indexedHeight`"** — a known "no so far", not "unknown":
the fold is a complete-history computation, and its consumers (retention
curves, adoption) already treat an exit-less holder as active. During
backfill the row itself may not exist yet; absence — not null — is the
"unknown" state, and it is covered by the standing honest-empty envelope
(heights say how far the mirror has read). No affordance is gated on the
null in either tier.

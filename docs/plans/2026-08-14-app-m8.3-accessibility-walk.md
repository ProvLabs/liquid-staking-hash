## 1. Origin & problem statement

Master plan §2 row 8.3: *"Accessibility walk on both themes, keyboard-only
pass, reduced-motion audit; fixes."* Overview §3 sharpens it with the two
carryover closures ratified at D31:

- **CO-22** — the authenticated surfaces the offline axe suite never covered
  (alerts settings, portfolio, operator view, admin dashboard) join automated
  axe coverage. Origin: M6.2 §3 commit C deviation 1 — *"offline e2e has no
  session (no wallet — the portfolio.spec precedent)"* — after which every
  authenticated surface inherited the same recorded exception
  (`e2e/axe.spec.ts:20-29` reaches only the anonymous gate on
  `/governance/new` and `/admin`; `e2e/portfolio.spec.ts:3-7` and
  `e2e/alerts.spec.ts:2-7` state the precedent).
- **CO-23** — the §14.4 "coming soon" shells (the exit DEX column,
  `apps/web/app/exit/exit.server.ts:12`; the Market page,
  app-spec §14.4/§8) and every cold-start (§14.12) and below-threshold
  (`MIN_COHORT_SIZE`) state survive this pass as **labeled, accessible
  states** — perceivable to assistive technology, never `aria-hidden` gaps.

Two facts make this PR more than an audit round:

**The gap's premise is no longer true, and probably never was structural.**
Deviation 1 reasoned "no session because no wallet." But session establishment
is chain-free and wallet-free by construction: `login()` in
`apps/web/app/lib/services/session.server.ts:103-139` is consume-nonce →
`verifyAdr36` (pure secp256k1, no LCD read) → an opaque-id cookie over a
server-side row, and with no `DATABASE_URL` the store is in-memory
(`apps/web/CLAUDE.md` §Conventions) — which is exactly how the offline e2e
server runs (`apps/web/playwright.config.ts:34-72` sets no `DATABASE_URL`).
The live suite already scripts the whole mint
(`apps/web/e2e-live/portfolio.spec.ts:15-32`: nonce → `DevnetTestSigner`
ADR-36 signature → login → cookie), and the signer lives entirely in the test
process (`apps/web/e2e-live/signer.ts`). The offline suite can do the same.
§2.2 designs it; the one genuinely missing piece is **role-bearing** sessions,
because the fixture role-holders' private keys are not in the repo (§2.3).

**D22 turned the honesty surfaces into public, load-bearing caveats.** The
testnet pilot is publicly reachable, so the environment badge
(`app/components/chrome/env-badge.tsx`), the degradation banner
(`chrome/banner.tsx`), the freshness footer (`chrome/freshness-footer.tsx`),
and every "coming soon"/cold-start/stale label are what stands between a
public visitor and the belief that pre-certification state is certified. **An
inaccessible caveat is a caveat that does not exist for AT users** — the
program would be telling the truth in pixels and a lie in the accessibility
tree, to exactly the users least able to cross-check. That is why the D22
honesty surfaces are in the *automated* matrix (§4 invariant 2), not the
manual walk.

Per the master plan §4 principle (row "Accessibility": *axe in Playwright +
manual walk … WCAG AA both themes, keyboard operability, reduced-motion*,
line 332), everything automated here is a **standing CI gate from this PR
on**, not a one-time audit. The manual walk is scripted as a repeatable
checklist recorded in this plan's delivery notes, so the next walk (8.5's
pre-launch pass, or any post-incident re-check) re-runs the same script.

What exists: the axe suite over 11 hand-listed routes × {light, dark}
(`e2e/axe.spec.ts:8-54`); the route registry (`app/routes.ts` — resource
routes outside `:lang?`, pages inside); both theme palettes token-validated
(`check:palette` + `test/brand-tokens.test.ts`, app-spec §11.1); a single
global reduced-motion kill switch (`app/app.css:65-73`); the tx lifecycle's
confirm step as a pure component (`app/tx/confirm.tsx`); charts with built-in
table views (`app/components/charts/step-chart.tsx:119-140`, the dataviz
"every chart offers a table view" rule); and the degraded-server harness
(`NVHASH_MOCK_LIVE_DOWN`, second webServer at
`playwright.config.ts:15-16,53-71`).

## 2. Mechanism

### 2.1 The coverage matrix — route × auth state × theme × input mode

| Axis | Values | Source of enumeration |
| --- | --- | --- |
| Route | every page route under `:lang?` in `app/routes.ts` (11 today), parameterized routes bound to one corpus-derived instance (`/governance/4`, the existing choice) | **generated from the registry** (§2.4) |
| Auth state | anonymous · holder session · role session (operator + admin on one signer) | fabricated via the app's own mint path (§2.2, §2.3) |
| Theme | light · dark (cookie-pinned, the existing idiom); one representative auto-theme cell (§7 Q1) | `app/theme/theme.ts` three-way cookie |
| Input mode | axe semantic scan (automated) · keyboard-only (automated for enumerated flows + manual walk) · reduced-motion (automated + manual audit) | §2.5, §2.6 |
| Render state | what the corpus honestly yields: anonymous gates, authenticated empty/cold-start, labeled shells, LIVE_DOWN degraded | fixture corpus + the `NVHASH_MOCK_LIVE_DOWN` server; **populated states ride the live lane** (§2.7) |

Automated vs manual, stated once: **axe cells, reduced-motion cells, the
enumerated keyboard flows, and every labeled-state assertion are automated
standing gates.** Manual is only what needs human judgment — reading order,
focus visibility quality, zoom reflow, a screen-reader spot pass — and it is
scripted (§2.8) so it is repeatable, with its findings landed as fixes in
commit C.

Note on the theme mechanism, for anyone importing assumptions from other
codebases: this app does **not** use `next-themes`. The three-way preference
(`auto`/`light`/`dark`) is a hand-rolled bounded cookie
(`app/theme/theme.ts:8-33`) rendered server-side as a `data-theme` attribute,
with `auto` = no attribute and CSS `light-dark()` tokens following the OS.
The axe suite pins the two explicit themes by cookie; both palettes are
already contrast-validated by `check:palette`/`test/brand-tokens.test.ts`.

### 2.2 Fabricating a session offline — the app's own mint path, no seam

The offline suite gains a login helper that is the
`e2e-live/portfolio.spec.ts:15-32` recipe verbatim: POST `/session/nonce`,
sign the challenge with `DevnetTestSigner.signChallenge` (ADR-36, in the test
process), POST `/session/login`, install the `nvhash_session` cookie in a
browser context. Everything runs against the server's own HTTP surface — **no
test-injection seam is added to `app/`** (the standing rule,
`e2e-live/signer.ts:1-7`). `DevnetTestSigner` moves to a shared test-support
module importable by both `e2e/` and `e2e-live/` (it already carries the
`TEST_SIGNER_SENTINEL` that `check:bundle` scans for, so an accidental app
import fails CI; that gate rides along unchanged).

The holder session needs nothing else: any throwaway key logs in (login is
signature-verification only), and the MSW API handlers are deliberately
auth-agnostic honest-empty for any address
(`app/mocks/handlers.ts:288-355` — portfolio/metrics/transactions serve the
empty payloads the real API serves for an address with no history). So the
authenticated holder cells reach: the authenticated chrome (bell button
replacing the advert, wallet button connected state), `/portfolio`'s
authenticated sections including **alert settings**
(`app/components/portfolio/alert-settings.tsx`) and push settings, and the
personal empty/cold-start states — which are labeled states CO-23 wants
scanned anyway. The suite pins a **committed throwaway harness keypair**
(constant, sentinel-marked) rather than generating per-run, so the address is
stable for the role grant below and for debugging.

### 2.3 Role-bearing sessions — why a harness knob, and its shape

Offline role detection reads the fixture corpus: operator = address ∈ the
contract `Validators {}` operator set (`roles.server.ts:164`), admin = the
`Config.admin` path — and the corpus's admin is a **plain account**
(`tp18kkn…`, `packages/fixtures/fixtures/queries/contract/config.json`), so
the policy lookup 404s and address equality decides
(`roles.server.ts:137`, and the handler comment at
`app/mocks/handlers.ts:543-551`). Those fixture addresses' private keys exist
only in the devnet keyring the dev-node image generates into the gitignored
`infra/devnet/state/` (`dev-node.sh` `generate_config`; SECURITY.md devnet
rules). **They are not recoverable from the repo, so no committed signer can
be a fixture role-holder.** Two designs were considered:

- **Commit the devnet role-holders' keys into the corpus.** Rejected: it
  couples the fixture corpus to key material, every full-reset re-capture
  (CO-30, 8.0) silently rotates them, and it normalizes committed private
  keys — throwaway or not, that is a habit `SECURITY.md` spends a section
  suppressing.
- **A harness-only grant knob in the MSW layer** — adopted.
  `NVHASH_MOCK_GRANT_ROLES=<bech32>` (bech32-shape-validated at the handler,
  reject-not-clamp), classified **toolingOnly** in
  `scripts/server-only-env.json` beside `NVHASH_MOCK_LIVE_DOWN` — the
  existing precedent for classified harness-only injection
  (`handlers.ts:227-231`). When set, and only inside the MSW module (which
  loads only under `NVHASH_MOCK=1`, `handlers.ts:1-4`):
  1. `group_policy_info/{Config.admin}` answers the **captured policy
     fixture** re-pointed at the admin account — the governed plane, which is
     also the production topology after D25 (both policies created before
     instantiate on every non-devnet deployment), so the offline suite starts
     exercising the membership path production will actually take rather than
     the plain-account 404 path;
  2. `group_members/{groupId}` answers the captured member list **plus one
     appended member row** for the granted address (shape cloned from a
     captured row);
  3. the contract `validators` smart query answers the captured rows **plus
     one row cloned from a captured validator** with `operator` set to the
     granted address.

This bends the harness's "mocks must not invent state" rule
(`handlers.ts:12-14`) and the plan says so rather than hiding it: the
injection is **derived** (fixture rows + one appended entry), **classified**
(toolingOnly, same as the failure injection), and **provably inert when
unset** (§4 invariant 4 — with the knob absent the handlers are asserted
byte-identical to the fixtures). The durable fix is recorded in §6: the 8.0
full-reset re-capture (CO-30) should **enroll the harness address on the
devnet before capture** (group member + registered validator operator), after
which the corpus truthfully contains it and the knob retires.

With the grant, the role cells reach: `/validators/mine` as an operator
(standing surfaces over honest-empty operator data,
`handlers.ts:356-375`), `/admin` as an admin — the fresh membership read
behind `mintAdminAssertion` runs against the same handlers, so the real
`admin:` mint path executes — with every §8.8 panel in its honest-empty /
"n/a" / below-threshold state (`handlers.ts:416-486`), and `/governance/new`
past the anonymous gate.

### 2.4 The scan is generated from the route registry, not hand-listed

`e2e/axe.spec.ts:8-30` is a hand-maintained array whose completeness is
enforced by a comment ("New routes join its route list",
`apps/web/CLAUDE.md` §CI gates). That is the exact shape §4b v2's C4 rule
exists to kill (overview §8: *generated, not tabulated* — the M7.5–7.6 leak
happened on an axis the hand-written table did not have). The suite is
rebuilt to **import `app/routes.ts` and enumerate the page routes** — the
default export is plain data; the pages are precisely the children of the
`:lang?` subtree — with a small parameter-binding map for dynamic segments
(`:proposalId` → the corpus id `4`, the existing binding with its recorded
rationale). Resource routes and `healthz` are excluded structurally (they sit
outside `:lang?`). A unit case (`test/a11y-routes.test.ts`, new) pins the
enumeration function: every registered page route appears exactly once, every
dynamic segment has a binding (a new `:param` route with no binding fails the
unit suite, not silently drops out of the scan), and the expected cell count
is `pages × themes × auth states`.

Auth-state reachability is likewise not hand-tabulated: the three auth states
are run over **all** page routes (the full product — 11 × 2 × 3 = 66 axe
scans, well within the offline suite's budget) rather than a curated
"routes-with-authenticated-states" list that would rot the same way the route
list did.

### 2.5 Reduced-motion — audit finding and the gate that pins it

The measured state: motion is CSS-only. One animation exists
(`.flow-pulse`, the Learn hero pipeline, `app.css:38-52` +
`components/learn/hero.tsx`), transitions are the 150–200 ms house rule, and
the base-layer kill switch (`app.css:65-73`) zeroes
`animation-duration`/`transition-duration` under
`prefers-reduced-motion: reduce`. A repo grep finds **no JS-driven
animation** — no `requestAnimationFrame`, no animation library; the spec's
§11 mention of Recharts is stale (no such dependency exists in
`apps/web/package.json`; charts are the hand-rolled SVG
`step-chart.tsx` — §6 schedules the one-line spec correction). The only
timer-driven DOM update is the freshness footer's 15 s relative-time tick
(`freshness-footer.tsx:26`) — content, not motion, but the walk checks it is
not an over-chatty live region.

The gate (new, `e2e/motion.spec.ts`): under
`page.emulateMedia({ reducedMotion: "reduce" })`, the Learn hero's
`.flow-pulse` computes an effectively-zero animation duration and a
transition-bearing control likewise; under no emulation the animation is
present (so the gate cannot pass vacuously against a page that lost the
animation entirely). C7: deleting the `app.css` kill-switch block turns the
suite red; so does a future component shipping a JS-driven animation on a
scanned page only if it also adds CSS motion — which is why the audit half
(grep for rAF/animation libraries) joins the manual-walk script as a standing
checklist line rather than pretending the e2e case covers it.

### 2.6 Keyboard-only — automated flows and their honest limit

Automated (`e2e/keyboard.spec.ts`, new), keyboard events only, asserting
operability + focus landing + Escape behavior:

- **Wallet popover** (`chrome/wallet-button.tsx:7-8` — an inline popover with
  `aria-expanded`, deliberately not a modal): open with Enter, arrow/Tab
  through vendors, Escape closes, focus returns to the trigger.
- **Alerts bell popover** (authenticated cell, `chrome/alerts-bell.tsx`):
  same contract.
- **Theme toggle** (`components/theme-toggle.tsx`): cycles by keyboard,
  announces state.
- **Tx lifecycle, offline-reachable segment**: `/stake` and `/exit` forms —
  amount entry, validation errors surfacing as `role="alert"`
  (`routes/stake.tsx:105,184`), preflight reasons list, and the
  simulate-failure state (the offline harness refuses simulation by design,
  `handlers.ts:618-620`, and that refusal must itself be an accessible,
  focus-managed state).
- **Chart table views**: the disclosure on `step-chart.tsx` (the table is the
  chart's AT surface — `step-chart.tsx:21`), operable per instance on
  `/portfolio` (accrual) and `/validators/mine` (delegation).
- **Governance**: proposal list → detail → vote/execute affordances
  (disabled states reachable and explained), composer form
  (`governance/template-form.tsx`).

**The confirm dialog cannot be reached end-to-end offline** — the lifecycle
gates confirm behind a successful simulate (`app/tx/use-tx-flow.ts`:
preflight → simulate → confirm), and the mock refuses to fabricate gas. The
plan does not pretend otherwise: `app/tx/confirm.tsx` (the §10.2 step-4
confirm — an inline step, not an `aria-modal` dialog, which the walk
validates as a deliberate pattern rather than an omission) gets a
**component-level keyboard/semantics case** in the unit suite (tab order:
summary → disclosure → cancel → confirm; the disclosure operable; the tier
communicated by text, not color alone), and the **live lane's** existing
lifecycle specs gain the keyboard variant for the real confirm step
(§2.7). Everything not enumerated above belongs to the manual walk.

### 2.7 What stays on the live lane, and why that is honest

Offline cells render what the corpus honestly yields; **populated**
authenticated states (a portfolio with positions, an operator with epochs and
payments, admin panels with cohorts) would require inventing per-address
history the corpus does not hold — exactly what `handlers.ts:12-14` forbids.
So the populated-state axe/keyboard coverage is a **small live-lane
addition**: `e2e-live/axe.spec.ts` (new) runs the same AxeBuilder scan over
the authenticated `/portfolio`, `/validators/mine`, `/admin` and the
lifecycle specs' confirm step against the real devnet stack, skip-clean
without `E2E_LIVE_SIGNER_KEY`, on the scheduled stack lane 8.1 formalizes —
**an addition to the standing offline gate, not the closure mechanism**.
CO-22's closure is the offline coverage; the live lane covers the one stratum
offline structurally cannot.

### 2.8 The manual walk — scripted, so it is repeatable

The walk is a fixed script executed per route × theme × auth state, recorded
as a checklist table in this plan's §10 delivery notes (the M7.5–7.6
delivery-notes idiom), one row per surface with pass/finding/fix-commit:

1. Tab through the whole page: order matches reading order; nothing
   unreachable; nothing focusable-but-invisible; focus ring visible on every
   stop (both themes — the mint-green ring is contrast-validated, but
   *visibility against local backgrounds* is a judgment call).
2. Every popover/disclosure: Escape, focus return, no trap.
3. State changes (fetcher results, tx step transitions, mark-read): focus is
   not lost to `<body>`; new content is announced (`role="status"`/`alert`
   as appropriate, no double-announcement).
4. 200 % zoom / 320 px width: no loss of content or function (WCAG 1.4.10).
5. Screen-reader spot pass (VoiceOver, one route per feature area): labels,
   table semantics, the honesty labels of §4 invariant 2 actually announced.
6. Reduced-motion OS-level check on the Learn hero.
7. `aria-hidden` audit: every one of the 10 files using it
   (`learn/incident-history`, `learn/hero`, `charts/step-chart`,
   `chrome/banner`, `chrome/env-badge`, `chrome/alerts-bell`,
   `portfolio/position-summary`, `portfolio/active-redemptions`,
   `validators/set-table`, `validators/mine/commission-banner`) is confirmed
   decorative-only with the information available elsewhere in the tree —
   the CO-23 rule applied at the attribute level.

Findings become fixes **in this PR** (commit C), each with a regression case
where the fix is mechanical (a missing label, a wrong role) and a checklist
annotation where it is judgment (an ordering change).

## 4. Security & invariants (enforced mechanisms with gating tests)

Per D26, every authorization or honesty invariant carries its
attacker-gain/harm line.

1. **No page route can ship unscanned.** The axe matrix is derived from
   `app/routes.ts`; a new page route joins the scan by existing, and a new
   dynamic segment without a binding fails the unit suite. *Gates:* the
   rebuilt `e2e/axe.spec.ts` (new form); `test/a11y-routes.test.ts` (new).
   *Harm if broken:* a surface ships that AT users cannot operate — and if it
   is a caveat surface, see invariant 2.
2. **The D22 honesty surfaces are in the automated matrix.** The environment
   badge, degradation banner, freshness labels, feature-probe caveat, paused
   states, "coming soon"/cold-start/below-threshold labels are scanned by axe
   and asserted present in the accessibility tree in every state the offline
   harness can produce (including LIVE_DOWN). *Gates:* `e2e/states.spec.ts`
   (new); the axe cells covering `chrome/*` on every route. *Harm if broken:*
   **an inaccessible caveat is a caveat that does not exist for AT users** —
   on the public pilot (D22) a screen-reader user reads pre-certification,
   degraded, or estimated state as certified/current/exact. That is the
   never-lie-about-state rule failing for a class of users, which is worse
   than failing for all of them, because nobody notices.
3. **The harness key and grant knob cannot reach production, three ways.**
   (i) `TEST_SIGNER_SENTINEL` — `check:bundle` scans the client bundle
   (standing); (ii) `NVHASH_MOCK_GRANT_ROLES` is classified `toolingOnly`
   (`test/client-config.test.ts` sweep, standing); (iii) the knob's code path
   exists only inside the MSW module, which loads only under `NVHASH_MOCK=1`.
   *Gates:* named above. *Attacker gain if broken:* none direct — production
   role checks read the real chain, and the knob only rewrites mock
   responses that production never serves — but a shipped knob would be dead
   authorization-adjacent code inviting exactly the "it's only test code"
   drift `SECURITY.md`'s enumerated-trust-surfaces rule exists to prevent.
   Stated as defense in depth, honestly, not as a load-bearing single gate.
4. **The grant knob is inert when unset.** With the knob absent, every
   handler response is byte-identical to the captured fixture ("mocks must
   not invent state," `handlers.ts:12-14`, stays true for every consumer that
   does not opt in). *Gate:* `test/mock-role-grant.test.ts` (new) — knob-off
   identity is asserted against the fixture JSON, not against a second copy
   of the handler's output. *Harm if broken:* the whole offline suite starts
   validating invented chain state, silently — every downstream "offline
   green" claim inherits the fabrication.
5. **Session fabrication uses only the app's public surface.** No

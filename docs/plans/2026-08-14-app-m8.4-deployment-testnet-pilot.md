## 1. Origin & problem statement

Master plan §2 row 8.4: *"Deployment configs (`infra/`: Docker images per
component, ArgoCD, per-environment profiles) + testnet pilot alongside the
Console… per-environment secrets/config posture (overview D24), webfont
self-hosting via build-time fetch, bootstrap scripts encoding the
per-environment ledger requirements…, and an early testnet measurement of the
~639 KB artifact's ≈4.26 M-gas store against the per-tx cap."* App-spec §3
decision 15 names the pipeline: Docker image, ArgoCD, the team's standard
pipeline (`app-spec.md:96`).

**Nothing of this exists today.** `infra/` holds exactly two trees: `dev/`
(the ADR-002 compose toolchain) and `devnet/` (the disposable local chain).
There is no Dockerfile in the repository, no Kubernetes manifest, no ArgoCD
application, no per-environment profile beyond the console's three `.env.*`
files, and no bootstrap script that may legally touch a non-devnet chain
(`SECURITY.md` "Development environment": drills and devnet scripts point at
disposable chains only). This PR is greenfield deployment infrastructure plus
the first non-devnet deployment of the program.

Four ratified decisions shape it:

- **D27 — public Provenance testnet only, no program-operated fallback.** If
  the settlement-era vault module (v1.2.4+, `AcceptAsset`) is absent from the
  public testnet, the pilot **waits** on upstream availability. The scripted
  `AcceptAsset` feature probe is therefore the first task of the whole pilot
  and its go/no-go signal (§2.6.1).
- **D22 — testnet builds are publicly reachable.** The environment badge, the
  feature-probe/pre-certification caveat, and honesty labeling graduate from
  polish to **gating requirements of this plan** (§2.7): the public sees
  pre-certification state.
- **D24 — secrets constraints ratified; the concrete mechanism is chosen
  here.** Secret store only; nothing non-public in repo, images, or bundles;
  fail-closed deploy scripts; a repo-scan CI gate. §7 Q1 evaluates
  sealed-secrets vs external-secrets-operator vs SOPS and recommends one;
  final say at this plan's review.
- **D21 + D25 — bootstrap topology.** Both group policies exist before
  instantiate; `InstantiateMsg.admin` **and** the wasmd `--admin` are the
  admin group policy address. The devnet script does neither by default
  (`infra/devnet/bootstrap/nvhash-deploy-p2p.sh:240` passes
  `--admin "$ADMIN_ADDR"`, the deployer key) — the testnet bootstrap must not
  inherit that.

Carryover mapping: CO-26 (per-environment provisioning: VAPID pairs,
`WALLETCONNECT_PROJECT_ID`, `EXPLORER_URL`, LCD/CSP hosts) → §2.5; CO-27
(webfont self-hosting) → §2.8; CO-28 (bootstrap ledger requirements) → §2.6;
CO-29 (store-gas measurement) → §2.6.4.

## 2. Mechanism

### 2.1 Component runtime shapes → image design

Measured from the sources, not the overview's one-line descriptions. Two
facts below contradict casual descriptions elsewhere and are load-bearing for
the images; both are called out.

| Component | Build step | Runtime entry | Processes | DB role | Liveness |
| --- | --- | --- | --- | --- | --- |
| `services/indexer` | `prisma generate` only (no TS build) | `node src/index.ts` **with `NODE_OPTIONS=--experimental-transform-types`** | 1, replicas=1 (sole writer) | `indexer_writer` | heartbeat file via `scripts/healthcheck.mjs` (no HTTP) |
| `services/api` | none (strip-only TS) | `node src/index.ts` | 1 | `api_reader` (optional → dataless honest mode) | `GET /api/v1/health` |
| `apps/web` | `prisma generate` + `react-router build` | `react-router-serve ./build/server/index.js` | **2 workloads from 1 image**: web server + notifier (`node notifier/index.ts`) | `app_writer` | `GET /healthz` |
| `apps/console` | `tsc -b && vite build --mode <env>` | none — static files | 0 (static server) | none | static 200 |

- **The indexer is not strip-only TS.** `runtime/streams.ts` uses TS
  parameter properties, which Node's default strip-only stripping rejects;
  the compose service already carries the flag
  (`infra/dev/compose.yaml:113-117`). The image `CMD`/env must carry it too,
  or the container exits at boot.
- **The web image bakes the build; config stays runtime.** The compose `web`
  service builds at container start, which is the recorded stale-bundle trap
  (`docs/architecture/web-design-notes.md` "Live e2e re-run trap"; CO-18).
  The image build runs `react-router build` at **image build time** instead.
  This is safe across environments because the client-safe subset is
  serialized from **server env at request time** through the root loader
  (`apps/web/app/config/client.ts`; app-spec §7 revision 2026-07-15) — no
  `VITE_*` baking — so **one web image serves every environment**.
- **The console is the opposite: config is baked at build.** Every console
  value is a `VITE_*` compile-time constant (`apps/console/.env.{devnet,test,production}`),
  and the index.html CSP pins `connect-src` to the profile's LCD hosts
  (`apps/console/CLAUDE.md:56`; the per-environment mechanism is 8.4b's
  deliverable). The console image is therefore **built per environment** — a
  build-arg selecting the Vite mode (`build:test` for the pilot,
  `apps/console/package.json`) — and served by a pinned static-file image.
  One image tag per environment, e.g. `console:testnet-<sha>`.
- **The notifier is a separate deployed workload**, not a sidecar thread: a
  second Deployment running the web image with `command: pnpm notifier`
  (ADR-001 Decision 3; `apps/web/.env.example` "A SEPARATE process"). It
  requires `DATABASE_URL` + `API_SERVICE_ASSERTION_KEY` and the three
  `WEB_PUSH_VAPID_*` vars to deliver push.
- **Migrations are deploy-time Jobs, not server startup.** `migrate:deploy`
  exists in both schema-owning packages (`services/indexer/package.json`,
  `apps/web/package.json`); each runs as its own role against its own schema
  (ADR-001 Decision 1). This PR lands **after 8.4a**, so both schemas are in
  migration mode — the Jobs run `prisma migrate deploy`, never reset.

Multi-stage build shape, all four: a `deps` stage (`pnpm fetch` +
`pnpm install --frozen-lockfile` from the workspace root — the workspace
needs the root lockfile, so the build context is the repo root), a `build`
stage (prisma generate / react-router build / vite build), and a minimal
runtime stage copying only the built output + production `node_modules`.
`.dockerignore` excludes `.env*` (except `.env.example`), `infra/devnet/state/`,
`.pnpm-store`, and `contracts/` — the gating scan in §4 makes that exclusion
enforced rather than aspirational.

### 2.2 Base images and supply chain

Pinned to the ADR-002 toolchain, by digest: `node:22-bookworm-slim` (the
workspace `engines` floor, the same image the tools/app planes run —
`infra/dev/compose.yaml:31,104`), `postgres:17-alpine` where an environment
runs its own Postgres, and a digest-pinned `nginx:stable-alpine` (or
equivalently minimal static server) for the console. Bumping any base is a
one-line reviewed change, the ADR-002 posture. Images are built and pushed by
a new `images` job in `app-ci` (existing jobs: `changes`, `workspace`,
`web-gates`, `db-grants`, `console`, `shell-lint` —
`.github/workflows/app-ci.yaml`); registry choice is §7 Q6. **No secret of
any kind is baked into any image** — enforced by the `image-secret-scan` gate
(§4 invariant 1), which is the `check:bundle` idiom lifted one layer up:
build with sentinel values in every server-only var, then scan every layer of
every image for a sentinel.

### 2.3 ArgoCD app-of-apps and per-environment profiles

New tree `infra/deploy/`:

```
infra/deploy/
  docker/            {indexer,api,web,console}.Dockerfile + .dockerignore
  k8s/base/          one kustomize base per workload:
                     indexer (Deployment, strategy Recreate, replicas 1),
                     api (Deployment+Service), web (Deployment+Service),
                     notifier (Deployment, web image), console (Deployment+Service),
                     db-provision Job, migrate-indexed Job, migrate-app Job,
                     grant-verify Job
  k8s/overlays/
    testnet/         CONCRETE: image tags, config values (§2.5), ingresses,
                     ExternalSecret references (§7 Q1), sync-wave ordering
    mainnet/         SHAPE ONLY: same structure, every value a placeholder;
                     completing it is 8.5's work, not this PR's
  argocd/
    app-of-apps.yaml one Application per environment pointing at its overlay;
                     child Applications per workload, names {env}-{component}
```

**Devnet stays on compose.** The ADR-002 substrate (`./dev`, `stack.sh`) is
the development environment and is not migrated to k8s; the devnet overlay is
deliberately absent rather than half-built. The overlay set is
`{testnet concrete, mainnet shape}`, matching the scope boundary (mainnet
profiles beyond shape are 8.5).

**Ordering is sync-waves, mirroring `stack.sh`:** wave 0 `db-provision`
(applies the parameterized role split, §2.3.1) → wave 1 the two migration
Jobs (`indexer_writer` migrates `indexed`, `app_writer` migrates `app`) →
wave 2 `grant-verify` (the `stack.sh verify` grant-boundary gate re-pointed
at the environment database) → wave 3 the workloads. A failed wave halts the
sync — fail-closed at the profile level, not just the script level.

#### 2.3.1 Per-environment database provisioning

`infra/dev/postgres/roles.sql` establishes the two-domain split with
**throwaway literal passwords** (`roles.sql:25-31` — correct for dev, banned
beyond it). The per-environment equivalent is the same statements
parameterized: `infra/deploy/db/provision-roles.sh` renders the SQL with
per-environment credentials **read from the secret store at run time**
(`psql -v`-style substitution; the script refuses to run if any credential
variable is unset or matches a placeholder pattern — fail-closed, §4
invariant 3). The grants themselves are unchanged: `indexer_writer` owns
`indexed`, `app_writer` owns `app`, `api_reader` is SELECT-only via default
privileges, PUBLIC gets nothing (ADR-001 Decision 1). The standing
`grant-boundary` assertion (`services/indexer/test/integration/grant-boundary.test.ts`)
runs against the environment database as the wave-2 Job.

### 2.4 The D24 secrets mechanism (recommendation; decided at review)

Constraints (ratified): secret store only; nothing non-public in repo,
images, or bundles; fail-closed deploy scripts; repo-scan CI gate. The
evaluation and recommendation live in §7 Q1: **external-secrets-operator**,
because it is the only candidate under which the repository never carries
secret material *in any form, ciphertext included* — the repo holds
`ExternalSecret` references (names, not values), the store holds the values,
rotation happens in the store without a commit. What is secret per
environment: the three DB role credentials, `API_SERVICE_ASSERTION_KEY`,
`WEB_PUSH_VAPID_PRIVATE_KEY` (+`SUBJECT` treated server-only), and the pilot
operations key material (§2.6.5). Everything else in §2.5 is public by
construction and lives in the overlay in plaintext, deliberately — putting
public values in the secret store would blur exactly the boundary the
client-safe allowlist keeps sharp.

#### 2.5.1 VAPID generation is a scripted, store-only step

`infra/deploy/scripts/generate-vapid.sh`: runs
`web-push generate-vapid-keys` in the pinned container (the
`.env.example`-documented command, ADR-002 — never host node), writes the
pair **directly into the secret store**, prints only the public key. The
private key never touches a file, a terminal scrollback capture, or the
repo. The three vars are all-or-none at boot (app-spec §7, the `superRefine`
guard) — the script writes all three or aborts.

### 2.6 Testnet bootstrap — probe first, then scripted, assertable steps

New scripts under `infra/deploy/bootstrap/` (deliberately **not**
`infra/devnet/` — the devnet scripts' container/keyring assumptions and
throwaway-key posture must not blur into the real-network path, and
`SECURITY.md`'s "drills point at nothing else" rule stays intact; the devnet
drill scripts are never pointed at testnet). Shared idioms are inherited:
`set -euo pipefail`, the `tx()` broadcast-then-poll-then-assert wrapper, and
lookup-before-create idempotency (`nvhash-deploy-p2p.sh:64-78,150-162`).
What changes: keys come only from the store (§2.6.5), every step **asserts
its own on-chain effect and aborts the sequence on mismatch** (§4 invariant
4), and the endpoint is an operator-supplied testnet node, never `dev-node`.

#### 2.6.1 Step 0 — the `AcceptAsset` feature probe (go/no-go, D27)

`probe-accept-asset.sh`, the first task of the pilot and the condition for
everything after it — the x/group probe idiom
(`nvhash-group-bootstrap.sh:103-123`) applied to the vault module:

1. the vault module is served on the public testnet LCD under `/vault/v1`
   (the pinned path fact, app-spec §14.2);
2. the node's build carries `provlabs/vault` at **v1.2.4 or later** — read
   from the LCD node-info `build_deps` [VERIFY the exact field path on the
   testnet build] — because the contract's settlement path is shaped for
   v1.2.4 specifically and fails on earlier 1.2.x
   (`docs/plans/2026-08-13-m8.0-contracts-vault-1.2.4-upgrade.md` §1);
3. the probe result (pass/fail, version, date, node) is recorded in
   `chain-facts.md` with testnet provenance.

**Fail ⇒ exit non-zero and the pilot waits.** There is no program-operated
fallback chain (D27), no "deploy anyway" flag, and the remaining steps
refuse to run without the probe's success marker. The deploy waiting on
upstream is the designed outcome, not an error state.

#### 2.6.2 Steps 1–2 — group and both policies, before anything else

`testnet-group-bootstrap.sh`: create the program group and **both** policies
(`admin` and `ops`) on it — D25 says split-at-bootstrap on every non-devnet
deployment — with production-shaped voting windows (devnet's 300s/40s are
labeled devnet-only drill affordances, `nvhash-group-bootstrap.sh:43-58`;
testnet windows are a §7 Q3 ops parameter). Membership for the pilot is the
program engineering key set; thresholds remain 8.5 launch-ops parameters
(D25). Assertions: group exists with expected metadata, exactly the two
expected policies resolve by metadata, both policy accounts are funded. The
script prints the **admin policy address**; the deploy script consumes it.

**Order is load-bearing and mechanical:** the contract has no admin-rotation
message (`ExecuteMsg` has no variant that changes `Config.admin`;
`IMPLEMENTATION-STATUS.md` §2 dual-policy item, fact (b)), so a contract
instantiated before its policy exists can never be handed to it. The
sequence hard-stops before instantiate if the policy assertion fails.

#### 2.6.3 Steps 3–8 — marker, vault, NAV seed, store, instantiate, wiring

The Design C sequence (`nvhash-deploy-p2p.sh` as the semantic reference),
with the D21 correction and per-step assertions:

3. **Restricted receipt marker** with required attributes; name binding for
   the attribute root is a testnet-specific question (§7 Q4 — devnet binds
   `nvhash.pb` via its own validator, which does not transfer). Assert:
   marker exists, RESTRICTED, active, required attrs recorded.
4. **Vault create** (underlying `nhash`, share `nvhash`, no payment denom;
   `withdrawal_delay_seconds` derived from the **testnet** unbonding time,
   recorded) + share denom metadata. Assert: vault resolves by share denom,
   delay matches the computed value, metadata present.
5. **Seed internal NAV 1:1** (`update-vault-nav … 1nhash 1`). Assert: NAV
   entry present at exactly 1:1.
6. **Store the artifact** built by `contracts/scripts/build-artifact.sh`
   (never a committed binary). **Record `gas_used` of `MsgStoreCode`** —
   this is CO-29's measurement (§2.6.4). Assert: code_id parsed, on-chain
   code checksum equals the local artifact's sha256.
7. **Instantiate** with `InstantiateMsg.admin = <admin policy address>`
   **and** `--admin <admin policy address>` — both authorities are the
   group, per D21; the devnet default (`--admin "$ADMIN_ADDR"`,
   `nvhash-deploy-p2p.sh:240`) is exactly what this script must not do.
   Assert: `Config.admin` equals the policy; the wasmd `contract-info` admin
   equals the policy. **This step is irreversible per deployment** (master
   plan row 8.4a) — it runs only after every prior assertion has passed.
8. **Wiring:** `set-asset-manager` → contract; **NAV-authority rotation** →
   contract (the slash write-down sandwich requires it,
   `IMPLEMENTATION-STATUS.md` §1); **receipt-marker grant
   `mint,burn,transfer,deposit,withdraw`** → contract (the burn leg
   transfers receipt into the marker account before `MsgBurn` — Transfer is
   the one the ledger names); required attributes on contract, vault,
   principal, and the receipt marker's own account. Assert each: read the
   vault's `asset_manager` and `nav_authority`, read the marker grants, read
   each attribute — never trust the tx code alone.

A final `verify` subcommand re-asserts the complete end state from chain
reads only (the `stack.sh verify` precedent) and is safe to run any time;
it is also the post-pilot acceptance check.

#### 2.6.4 The store-gas measurement (CO-29)

Step 6's recorded `gas_used` is appended to
`contracts/IMPLEMENTATION-STATUS.md` §3 (the existing "~4.26M gas vs a
possible 4M cap" row) with date, chain-id, height, txhash, artifact size and
sha256. The point of measuring in Phase A: if the ≈4.26 M-gas upload is
above the mainnet per-tx cap, the remedy (artifact size diet or a confirmed
higher limit) is a contract-side change that must land **before the S1
audit freezes the contract** (overview §2 fact 1) — discovering it at 8.5
would be too late. The testnet cap is also read and recorded [VERIFY]; a
testnet store that fails on gas is itself the finding, loudly recorded, not
a blocker for re-running after remediation.

#### 2.6.5 Keys: store-only, the devnet rule extended

`SECURITY.md` already states it: never place mainnet/testnet keys in
scripts, env files, or `state/`. Mechanically here: the bootstrap reads the
pilot operations key from the secret store into the signing call and nothing
else; no mnemonic argument, no key file in the repo or image, no keyring in
a container layer. The scripts fail closed on a missing or
placeholder-shaped credential **before the first tx** (§4 invariant 3), and
the repo-scan gate (§4 invariant 2) keeps the failure mode "forgot the
store" from degrading into "pasted it into the script". Funding the pilot
key on the public testnet is §7 Q3.

### 2.7 The D22 public-pilot honesty gates

The public sees pre-certification state, so these are gating requirements,
not polish:

1. **Environment badge, loud on non-mainnet.** Already implemented in the
   chrome (app-spec §8.0: "quiet on mainnet, loud (warning-tinted, labeled)
   on testnet/devnet", `app-spec.md:365`; §14 item 14 records the testnet
   pilot as publicly reachable *with the loud badge*, `app-spec.md:2115`).
   This PR's obligation is the **mapping**: the testnet profile's `APP_ENV`
   value must actually produce the loud badge with the testnet chain-id
   rendered (§7 Q5), asserted by an e2e case against the built image, not
   assumed from the devnet behavior.
2. **Feature-probe / pre-certification caveat, both surfaces, until 8.0
   passes.** Mechanism: the caveat is keyed to the **fixture manifest
   status** — `packages/fixtures` `manifest.json` is `PROVISIONAL` until
   8.0's re-capture flips it (overview §5 checklist line 2). The App imports
   the status and renders the caveat (Learn trust panel + footer) whenever
   it is not certified; the console bakes the same fact at build time. No
   per-environment "certified" config flag exists to forget or to lie with —
   the caveat retires only when the artifact that defines certification
   changes, in the same commit. Gate:
   `apps/web/test/certification-caveat.test.ts` (renders when PROVISIONAL,
   absent otherwise) plus a console build assertion in the `console` CI job.
3. **Verify-link contract proven live, App↔Console.** Testnet is the first
   environment where both are deployed (master plan row 8.4: "the
   verify-link contract is only testable with both deployed"). A live e2e
   (`apps/web/e2e/verify-links.live.spec.ts`, the `test:e2e:live` lane)
   walks real verify links from App surfaces to the deployed console —
   including the 8.4b entity anchors and the `governance` target — and
   asserts each lands on the addressed entity with matching chain-id. This
   is the pilot's acceptance test, run against the deployment, not a CI
   suite.

### 2.8 Webfont self-hosting (CO-27, build-time fetch)

App-only: the console is system-fonts-only by spec with no `font-src`
exposure (`console-spec.md:550`). The §11 type stack (Funnel Sans body /
Space Grotesk display / Geist Mono — `app-spec.md:1799`, deferred note in
`apps/web/app/theme/tokens.css:15-18`) is fetched at **build time** by
`apps/web/scripts/fetch-fonts.mjs`: pinned upstream URLs, **pinned sha256
per file**, output to a gitignored `public/fonts/`, `@font-face` rules in
the theme CSS with `font-display: swap` and the system stack as fallback.
Production build fails on a checksum mismatch or fetch failure
(fail-closed); `dev` warns and falls back to the system stack so offline
development keeps working. No binary is ever committed (repo policy); a
repo check asserts no tracked font file (§4 invariant 10). License
provenance (all three are OFL/free-license families [VERIFY exact upstream
artifacts]) is recorded in the script header.

### 2.9 Indexer backfill from testnet height

Today only the governance worker takes a start height
(`GOV_START_HEIGHT`, `services/indexer/src/config.ts:81`); the
chain-events, epoch-history, and validator-sampler workers begin at height
0/unset (`services/indexer/src/runtime/worker.ts:103`). On devnet that is
free; on the public testnet it means walking millions of pre-contract
blocks — weeks of backfill during which the lag banner never clears. This
PR adds a bounded `INDEX_START_HEIGHT` (default 1, devnet-compatible) wired
to all chain workers, set per environment to the **contract store height**
recorded by the bootstrap. History before the contract exists is empty by
construction, so starting there loses nothing and is honest.

Backfill lag must stay under the DATA DEGRADED threshold (120 heights ≈
10 min trailing, `services/indexer/src/reconciler/tolerances.ts:25`) once
caught up; the catch-up window itself will legitimately show DATA DEGRADED
and **must** — tuning the threshold to hide the backfill would be the lie
the banner exists to prevent. The measured catch-up duration and steady-state
lag on testnet feed 8.2's load-test row (overview §3 row 8.2 names "indexer
lag under backfill vs the DATA DEGRADED threshold").

## 4. Security & invariants (enforced mechanisms with gating tests)

1. **No secret in any image.** Every layer of every image is scanned after a
   build performed with sentinel values present in the environment and build
   context; any sentinel found fails CI. `.dockerignore` excludes `.env*`
   and `infra/devnet/state/`. *Gate:* **`image-secret-scan`** (new, commit
   A), in the `images` job. *What an attacker gains if it does not hold:* a
   public-registry pull yields a live DB credential or the assertion-minting
   HMAC key — full write access to the `app` schema or the ability to forge
   `admin:`/address-scoped API assertions.
2. **No non-placeholder secret in the repository.** Placeholders match the
   `.env.example` patterns; anything credential-shaped outside them fails
   CI. *Gate:* **`repo-secret-scan`** (new, commit A) — the overview §7
   conformance row's named check. *Attacker gains:* the repo is
   audit-shared and heading public; a committed key is burned forever (git
   history), and on a public testnet it is spendable by anyone who reads it.
3. **Deploy scripts fail closed.** Any missing, empty, or
   placeholder-shaped credential or address aborts before the first side
   effect; no `--force`, no interactive continue. *Gates:* **fail-closed
   cases in CI** (commit B: run each script with a placeholder → non-zero
   exit, no output side effect); `set -euo pipefail` + explicit refusal
   checks reviewed per script. *Attacker gains:* a script that "continues
   anyway" is how a deployer key silently remains an authority (see 5–7) or
   how a deploy lands against the wrong chain.
4. **Every bootstrap step verifies its own on-chain effect and aborts the
   sequence on mismatch.** Reads, not tx codes: `Config.admin`,
   `contract-info` admin, `asset_manager`, `nav_authority`, marker grants,
   attributes, NAV entry — each asserted after its step, plus the
   end-to-end `verify` subcommand. *Gate:* **bootstrap assertions** (commit
   C; `verify` re-runnable any time). *Attacker gains:* a bootstrap that
   silently skips the NAV rotation leaves the **deployer key** holding NAV
   authority — a single key that can restate the vault's NAV at will, which
   is direct value manipulation; a skipped marker Transfer grant strands
   every redemption burn leg (funds stuck at first settlement).
5. **Both authorities at instantiate are the admin group policy** —
   `InstantiateMsg.admin` and the wasmd `--admin` (D21, D25). *Gate:* the
   step-7 assertions (config admin == policy, contract-info admin ==
   policy); the sequence refuses to instantiate before the policy
   assertions pass (§2.6.2). *Attacker gains:* whoever holds a
   single-key contract admin can pause/halt/reconfigure the program alone;
   a single-key wasmd admin can `MsgMigrateContract` — swap the running
   code — without any group threshold. Both are irreversible per deployment
   (no admin-rotation message), so a wrong instantiate cannot be repaired,
   only redeployed.
6. **Group + both policies exist before instantiate** (D25; M7 F2). *Gate:*
   ordering enforced in the script (hard stop) + the step-7 assertion can
   only pass if they did. *Attacker gains:* not an attacker but a
   dead-end — a contract whose admin is a nonexistent or plain account has
   either no governance or single-key governance, permanently.
7. **NAV authority is the contract, nothing else** after step 8. *Gate:*
   bootstrap assertion + `verify`. *Attacker gains:* as invariant 4; also
   the slash write-down sandwich cannot run at all without it
   (`IMPLEMENTATION-STATUS.md` §1), so losses would go unrecognized —
   a solvency lie by omission.
8. **Real testnet key material lives only in the secret store.** Never in
   repo, scripts, images, CI logs, or overlay values (the `SECURITY.md`
   devnet-keys rule extended to real networks, overview §7 row 1). *Gates:*
   invariants 1–3's scans + the store-only access path in `_lib.sh`
   (reviewed; no argument or file accepts a key). *Attacker gains:* the
   pilot's operating key spends real (testnet) funds and signs bootstrap
   authority transactions; leakage hands over the deployment identity.
9. **The public pilot never claims certification** (D22/D27). The caveat is
   keyed to the fixtures manifest status, not a config flag, so no
   deployment can assert a certification the corpus does not have; the
   environment badge is loud on testnet with the chain-id rendered. *Gates:*
   `apps/web/test/certification-caveat.test.ts`; console build assertion;
   the badge e2e case (commit D). *Attacker gains:* nothing to steal — but
   the program itself would be lying to the public about pre-certification
   state, which is the trust-architecture failure `SECURITY.md`'s
   never-lie rule exists to prevent, in front of exactly the audience D22
   makes real.
10. **No binaries in git** — neither the wasm artifact (built on demand,
    step 6) nor webfonts (build-time fetch, checksum-pinned). *Gates:* the
    existing artifact freshness discipline; **webfont checksum** build
    failure + the no-tracked-fonts repo check (commit A). *Attacker
    gains:* an unpinned fetched font is a supply-chain injection vector
    into every page of the public App; the checksum pin closes it.
11. **The client-safe boundary survives the production build.**
    `check:bundle` runs against the image-built bundle; the client-safe
    allowlist (`apps/web/app/config/client.ts`) is unchanged by this PR —
    no new client-visible key is added. *Gate:* the standing `check:bundle`
    + `test/client-config.test.ts`, now also exercised in the `images`
    job. *Attacker gains:* a server-only value (LCD host, API key) shipped
    in the public bundle.
12. **The public API's defensive posture is configuration, verified.**
    `TRUST_PROXY=true` is set only where the ingress provably overwrites
    `X-Forwarded-For` (asserted in the overlay's ingress config review;
    `services/api/.env.example` documents the hazard). *Gate:* overlay
    review checklist item + the standing rate-limit harness. *Attacker
    gains:* spoofing the rate-limit client key → rate-limit evasion → the
    load profile 8.2 tuned for is void (cheap DoS on the public API).
13. **The verify-link contract never crosses environments.** One console
    origin per environment; `CONSOLE_CHAIN_ID` must equal `CHAIN_ID` or the
    web tier refuses to boot (app-spec §7; `apps/web/app/config/config.server.ts`),
    and the vault-address cross-check against `Config {}` fails startup on
    mismatch. *Gates:* the standing boot checks (`test/boot-checks.test.ts`)
    now exercised with testnet-shaped values; the live verify-link e2e
    (§2.7.3). *Attacker gains:* a mainnet-looking claim "verified" against
    testnet data — the verification affordance itself becomes the phishing
    tool.
14. **The console's hosting encodes what its bundle cannot** — the two
    handoffs 8.4b hands to this PR (recorded in that plan's §7.1; added here
    2026-08-14 at verification, since this plan predates them).
    **(a) The SPA-fallback rewrite.** Anchor *fragments* cannot 404 at the
    host, but the console's *page paths* can: a verify link landing on a
    deep path (`/validators`, `/epoch`, `/governance`) returns the host's
    404 unless the static-hosting config rewrites unmatched paths to
    `index.html`. Without it the entity-anchor contract 8.4b builds fails in
    exactly the environment it exists to serve, and the failure appears only
    once both surfaces are deployed.
    **(b) The CSP as a response header**, generated from the same overlay
    LCD-host facts that feed 8.4b's build-time meta tag, so the two can
    never disagree. Headers additionally express `frame-ancestors`, which
    meta CSP cannot — leaving the public pilot (D22) framable without it.
    *Gates:* the live verify-link e2e (§2.7.3) is already the natural
    detector for (a) — it walks real App→Console links against the deployed
    pair and goes red on a host 404, provided its cases include at least one
    **deep-path** anchor rather than only root-path links; and a new
    **response-header case** in the same live lane asserting the served CSP
    matches the profile's origin list and carries `frame-ancestors`.
    *What an attacker gains if it does not hold:* (b) permits clickjacking
    of a wallet-connecting page on a publicly reachable origin; (a) is not
    an attacker gain but the honesty failure invariant 5 of the 8.4b plan
    names — verify links that dead-end train pilot users that the program's
    own verification path is unreliable, which is the soil for
    "use this other explorer instead" substitution.
15. **Standing gates continue:** grant-boundary (now also per-environment,
    wave 2), envelope/read-only/rate-limit harnesses, axe, i18n coverage,
    `pnpm -r` typecheck/test, Biome, shell-lint (now covering
    `infra/deploy/`).

**Nullable-gates-affordance review:** the nullables this PR touches all mean
"not configured" and are treated conservatively by existing machinery —
absent `EXPLORER_URL` renders no verify link (never a broken one), absent
VAPID renders the honest "not configured" push state with no subscribe path,
absent api `DATABASE_URL` serves the honest dataless state, empty
`CONTRACT_ADDRESS`/`VAULT_ADDRESS` fails boot closed (`infra/dev/compose.yaml:126-129`
records the posture; the overlays make the values required). No new
nullable gates an affordance.

### C3 — Concurrency

| Hazard | Remedy |
| --- | --- |
| Two indexer pods racing the checkpoint (rolling update overlap) | `strategy: Recreate`, `replicas: 1` — the old pod is gone before the new one starts; the sole-writer invariant is a deployment property, not a hope |
| Two concurrent bootstrap runs | chain serializes txs; every create is lookup-before-create, and the loser's create fails → `tx()` aborts → a re-run converges on the existing state. The irreversible step (instantiate) is preceded by assertions that pass only in the completed prior state |
| Migration Job racing workloads | sync waves: migrations complete (wave 1) before any workload starts (wave 3); a failed Job halts the sync |
| ArgoCD sync racing a manual bootstrap | the bootstrap is chain-side, the sync is cluster-side; their only shared fact is the address/height values, which enter the overlay in commit E **after** bootstrap completes — the workloads fail boot closed on empty addresses until then, by design |

### C4 — State × affordance (generated from the surface's inputs)

The one new user-facing surface is the certification caveat; its input is a
build-time constant, so the runtime enumeration is over

| Manifest status | Surface |
| --- | --- |
| `PROVISIONAL` (until 8.0) | caveat rendered on App (Learn trust panel + footer) and console; copy states feature-probe posture and claims no certification |

There is no "input unavailable" cell: a build without the manifest fails to

### C5 — Plane precedence

n/a — this PR adds no display plane and no live/indexed contest. The one
plane-adjacent obligation is honesty **during backfill**: DATA DEGRADED must
show while lag exceeds threshold (§2.9), which is the existing chrome
machinery doing its job, deliberately not tuned away.

### C6 — Temporal spans (bootstrap across restarts / partial failure)

Every bootstrap step is idempotent by on-chain lookup (marker exists → skip;
vault by share denom; group/policies by metadata; grants/attributes read
before write — the devnet precedent, `nvhash-deploy-p2p.sh:150-162,251-254`)
**and** asserted after effect. A crash between steps leaves a prefix state a
re-run walks through as skips, then continues. The irreversible instantiate
is protected in both directions: it does not run until steps 1–6's
assertions pass in this run, and once a conforming contract exists,
`existing_contract`-style detection reuses it rather than deploying a
second. The `verify` subcommand makes "where did it stop" a query, not
archaeology. Overlay value flow is likewise two-phase tolerant: workloads
fail boot closed until commit E lands the bootstrap outputs (C3 row 4).

| Mechanism | Breaking it makes this fail |
| --- | --- |

| `--admin` reverted to the deployer key | step-7 `contract-info` assertion red |
| `INDEX_START_HEIGHT` wiring reverted | the worker start-height test red; operationally, testnet backfill lag never clears — visible in the 8.2-coordinated measurement |
| Caveat component removed while PROVISIONAL | `certification-caveat.test.ts` red; console build assertion red |
| Webfont checksum pin edited to match a tampered file | it cannot be "edited to pass" silently — the pin lives in the reviewed script; an unpinned fetch fails the build |
| Recreate/replicas=1 loosened on the indexer | no unit test can see this — named as a **review checklist item** in §9, the honest answer; the grant-boundary and checkpoint tests do not exercise pod overlap |

  **Why this is defensible, stated precisely:** the receiver attribute is
  **defense-in-depth, not the primary control**. The structural guarantee is
  that the receipt is *not an accepted vault denom*, which is what makes
  receipt-denom extraction "structurally impossible" — the attribute is
  named as an additional layer on top of that
  (`liquid-staking-spec.md:108`). Removing the layer on a testnet pilot does
  not remove the guarantee.

  **Three consequences that must be carried, not assumed away:**
  1. **A certification-coverage gap.** The pilot does not exercise the
     attribute-gated holder restriction at all, so no evidence about that
     path comes out of Phase B. This is recorded in
     `IMPLEMENTATION-STATUS.md` alongside the existing coverage ledger —
     the "NOT covered" headline stays truthful (`SECURITY.md` audit
     readiness), and the auditor is told rather than left to infer it.
  2. **Mainnet must restore it, as a gate rather than a checkbox.**
     `nvhash.pb` attribute grants are already a
     `liquid-staking-spec.md` §14 launch-checklist item (line 584); this
     decision promotes it to a **hard 8.5 gate**, because mainnet would
     otherwise inherit a testnet-shaped deployment by omission.
  3. **The skip must be loud.** Per invariant 4's discipline (every
     bootstrap step verifies its own on-chain effect), "no required
     attribute was set" is an **announced and recorded** state in the
     bootstrap output and its `verify` subcommand — never a silently
     absent step, which is indistinguishable from a step that failed.
     The script keeps the attribute name as an explicit parameter so a
     bindable root can be supplied later without a code change.

  **Unchanged and still mandatory:** the contract's **Transfer** permission
  on the receipt marker (`IMPLEMENTATION-STATUS.md` §1) is a marker
  *permission*, not a required attribute — the redemption burn leg depends
  on it, and nothing here relaxes it.

- **Q5 — the closed `APP_ENV` set becomes `development | testnet |
  production`** — `staging` is **replaced**, not supplemented, because the
  program has no separate staging environment and an unused enum member
  invites a deployment into a state nothing is designed for. This is a
  third option; neither offered alternative matches it.

  **Verified touch points** (all in one change, per spec parity):
  `apps/web/app/config/client.ts:31` (type union),
  `apps/web/app/config/config.server.ts:41` and
  `services/api/src/config.ts:18` (zod enums),
  `services/api/.env.example` + `services/api/test/config.test.ts`,
  the badge catalog key `chrome.env-staging` → `chrome.env-testnet`
  (`apps/web/app/i18n/locales/en.ts:101`), and the `APP_ENV` row at
  `app-spec.md:289`.

  **Two corrections to this plan's own reading.** The rename is *safe*: every
  other `appEnv` consumer branches only on `development` (the session
  cookie's `Secure` flag at `session.server.ts:233`, and the dev guards in
  `alerts/push/incident-acks/session`), so none of them changes behavior.
  And the proposal's "all three config boundaries (web, api, notifier)" is
  wrong — the notifier runs inside `apps/web` and has no `APP_ENV` enum of
  its own, so there are **two** code boundaries plus the spec row. The
  standing `i18n-coverage.test.ts` gate fails on a missed catalog key, so
  the rename cannot half-land.

- **Q6 — registry, cluster and the three public hostnames are overlay
  parameters**, supplied at deploy rather than pinned in plan text. The

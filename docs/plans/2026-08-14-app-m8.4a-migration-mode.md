## 1. Origin & problem statement

Master plan §2 row 8.4a (added 2026-07-30, Ira's direction): *"the row after
which the program is no longer in complete reset-and-rebuild mode. Three parts
land together"* — **(i)** contract upgradability + the wasmd contract admin

reset-and-rebuild rule at its three documentation sites is replaced by the
migration rule in the same change. The row is a decision that **blocks 8.4**:
nothing non-devnet deploys until it is made, because the wasmd admin is fixed
at instantiate and a contract instantiated without one can never be given one.

The decisions are now made (overview §6, ratified 2026-08-14, Ira):

- **D21** — the migrate entry point is added; **the wasmd admin is the admin

## 2. Mechanism

### 2.1 The migrate entry point exists to be drilled, not to transform state

v1 `migrate` performs **no state transformation**. The entry point exists so
that the capability, its authorization, and its verification procedure are
established and drilled **before anything irreversible deploys** — the first
real migration should be a rehearsed operation, not a first flight. The body
is exactly the cw2 gate:

- Load the stored cw2 marker (`cw2::get_contract_version`). Reject when the
  stored `contract` name ≠ `CONTRACT_NAME` (a foreign contract's state must
  never be adopted). Reject when the stored version is **newer** than the
  code's `CONTRACT_VERSION` (downgrades reintroduce fixed flaws; the F1–F9
  hardenings are the standing example of what a downgrade would resurrect).
  Equal or older stored versions are accepted — equal makes re-migration
  idempotent, which is what lets the drill assert byte-for-byte state
  identity.
- `set_contract_version` to the current name/version.
- Return a response with `old_version` / `new_version` attributes and touch
  **nothing else**. No state walk: iterating validators or queues inside
  migrate is unbounded work (`SECURITY.md`), and a migration that needs a
  data transform writes it explicitly in that future version's migrate, gated
  by the version check this PR installs.

`MigrateMsg` is an empty `#[cw_serde]` struct, so a future version can add
fields without changing the wasmd-level call shape. Errors are typed
(`ContractError::InvalidMigration { reason }`, a new variant in
`contracts/src/error.rs`) — never panics.

Version comparison needs a semver ordering. `cw2` stores a plain string and
ships no comparator; the standard resolution is the `semver` crate (small,
no transitive dependencies, ubiquitous in cw contracts). Adding it is a
reviewed dependency decision under `SECURITY.md` — recorded in §7 Q4 with
the recommendation, and pinned in `Cargo.lock` like everything else.

### 2.2 Two authorization layers, and which one is load-bearing

wasmd routes `MsgMigrateContract` only from the contract's **wasmd admin**;
the in-contract cw2 gate then constrains *what* an authorized migration may
do. The wasmd layer is the security boundary — with the admin set to the
admin group policy (D21), a migration requires a group proposal, threshold
votes, and execution, the same ceremony as any admin action. The cw2 layer
is a correctness gate on the authorized path.

Both claims about the wasmd layer are **chain behavior**, and per the
chain-facts rule neither is established by reading wasmd source: that a
non-admin's `MsgMigrateContract` is rejected when the admin is a group
policy account (an address with **no private key by construction** —
`nvhash-group-bootstrap.sh:204`), and that a group proposal carrying
`MsgMigrateContract` with the policy as `sender` actually executes it, are
[VERIFY] items the new drill exists to settle (§2.3). Until the drill runs,
this plan treats them as hypotheses.

Deploy wiring: `nvhash-deploy-p2p.sh` gains a `WASM_ADMIN` hook defaulting
to `$CONTRACT_ADMIN`, replacing the hard-coded `--admin "$ADMIN_ADDR"`
(:240). Under the group bootstrap order that already exists
(`nvhash-group-bootstrap.sh:13–14` — policy created **before** instantiate,
its address consumed via `CONTRACT_ADMIN`), both authorities land on the
admin policy with no new ceremony. A plain bootstrap without the group keeps
today's behavior (`CONTRACT_ADMIN` defaults to the deployer address,
deploy-p2p.sh:141), so non-governance devnet flows are unchanged.

**Deliberately not offered:** an "instantiate with no admin" path. Overview
sequencing fact 2 records the irreversibility; the honest way to renounce
upgradability later is `MsgClearAdmin` via the same group ceremony, which is
reversible right up until it is executed. The drill asserts the bootstrap
set the admin it intended (§4 invariant 1's C7 leg).

### 2.3 The migrate drill (`contracts/drills/migrate-drill.sh`)

New drill, following `gov-drill.sh`'s proposal machinery (submit → vote ×
threshold → exec → assert against `EventExec` / `EventProposalPruned`,
because a successfully executed proposal is pruned in its own transaction —
the 2026-07-29 finding). Sequence, each step an assertion:

1. **Bootstrap with the governed topology**: `nvhash-group-bootstrap.sh`
   then `CONTRACT_ADMIN="$POLICY" WASM_ADMIN="$POLICY"
   nvhash-deploy-p2p.sh`. Assert `q wasm contract <addr>` reports
   `admin == $POLICY` — the drill's own precondition, checked, not assumed.
2. **Unauthorized migrate is REJECTED**: `tx wasm migrate <addr> <code_id>
   '{}'` signed by a non-member key AND by an individual group member's key
   (a member is not the policy; threshold means no single member holds the
   capability). Assert both fail with the wasmd unauthorized error, and that
   the contract's code id and cw2 marker are unchanged. [VERIFY — this is
   the assertion that establishes wasmd's admin check under a keyless policy
   admin; it has never been exercised in this repo.]
3. **Build the migration target**: copy the crate to a temp dir, bump
   `version` to `0.1.0+drill` (or `0.1.1`; §7 Q5), build via
   `scripts/build-artifact.sh` semantics (Docker, on demand — no binary is
   ever committed), `tx wasm store`. A version-distinct build sidesteps
   wasmd's store-time checksum dedupe (storing byte-identical wasm does not
   yield a distinct code id [VERIFY]) and makes the cw2 version-advance
   observable.
4. **Authorized migrate SUCCEEDS through the group**: submit a proposal
   whose single message is `/cosmwasm.wasm.v1.MsgMigrateContract` with
   `sender = $POLICY`, vote to threshold, exec. Assert
   `EventExec.result == PROPOSAL_EXECUTOR_RESULT_SUCCESS` and
   `EventProposalPruned.status == PROPOSAL_STATUS_ACCEPTED` (the only
   observable pair for a successful exec — gov-drill finding 1). [VERIFY —
   group-executed migration end to end.]
5. **Post-migrate state asserted byte-for-byte where applicable**: assert
   the contract's code id is the new one; the cw2 `contract_info` raw key
   carries the same name and the bumped version; and a full
   `q wasm contract-state all` dump taken before step 4 equals the dump
   after, **except** the `contract_info` key, whose delta is exactly the
   version string. `Config {}`, `EpochStatus {}`, `Validators {}` responses
   are additionally diffed as JSON (belt and braces at the interface level).
6. **Downgrade is rejected by the contract on a live chain**: propose a
   second migration back to the original (older-version) code id through
   the same group ceremony. Assert the proposal lands
   `ACCEPTED` + `executor_result FAILURE` (the wrapped contract error
   surfaces in `executor_result`, not in the proposal status — gov-drill's
   exec-failure finding), and that code id and cw2 marker still show the
   bumped version. This drills the in-contract gate itself, not just the
   wasmd layer. [VERIFY — that a failed migration inside group exec leaves
   the contract on the new code id with state untouched.]

The drill needs no epoch crank, so the E-CAL one-crank-per-month devnet cap
(`IMPLEMENTATION-STATUS.md` §4) does not constrain it — it can run on a
fresh chain any day of the month, alongside `gov-drill.sh`.

### 2.4 `redemption_margin_bps`: from constant to bounded config

The 2026-07-09 simulation finding (`IMPLEMENTATION-STATUS.md` §3): the fixed
50 bps margin under-covers NAV drift over a redemption's final unbonding
tail when realized yield is high (observed past ~8% annualized under
harsher-than-mainnet timing; benign at typical parameters). The sizing rule
the finding records: **margin ≥ expected epoch yield × the unbonding/delay
fraction**. At plausible extremes (20%/yr realized ≈ 167 bps/epoch, × a
21-day/30-day fraction ≈ 117 bps) the need stays an order of magnitude
under 10%; a margin much beyond that stops being a drift cover and becomes
a liquidity brake, silently over-reserving `redemption_need` and starving
the deploy budget (epoch.rs:586–601 subtracts `need` from the deployable
surplus). Bound: **`0..=1_000` bps, reject outside** (the
`Config::validate` idiom — state.rs:63–101 rejects, never clamps), default
50 preserving today's behavior. **DECIDED 2026-08-14 (§7 Q1)** — the same
number lands in the contract bound, the `update_config` template's pinned
bound, and the spec text in commit B.

Plumbing (all sites named so the executor changes callers, not planners):

- `Config` gains `redemption_margin_bps: u64` with
  `#[serde(default = "default_redemption_margin_bps")]` returning **50** —
  NOT the bare `#[serde(default)]` used by `commission_bps`
  (state.rs:48), because a zero default would silently remove the margin on
  any state stored before this field existed. This is the one place D29 is
  harder than it reads: the field addition is itself a state-shape change,
  absorbed by the serde default so the v1 migrate stays a true no-op.
- `InstantiateMsg` gains `redemption_margin_bps: Option<u64>` (None = 50,
  the concentration-mirror idiom, msg.rs:22–30); `UpdateConfig` gains the
  eleventh `Option<u64>` field; `ConfigResponse` reports it.
- `Config::validate` gains the bound; the existing bounds tests extend
  (`instantiate_bounds_every_config_input`,
  `update_config_rejects_out_of_range_values`, contract.rs:489, :576).
- The three engine call sites (epoch.rs:354, :586, :620) read
  `cfg.redemption_margin_bps`; the `pub const` moves to
  `DEFAULT_REDEMPTION_MARGIN_BPS` beside the other defaults
  (contract.rs:25–36).
- **App ride-along (forced by CI, §1):** the `update_config` template in
  `apps/web` gains the field with its `contractRule` string, and
  `governance-templates.test.ts`'s pinned-bounds block gains the new bound —
  the test copies each bound from `Config::validate` by design.

**Simulation domain extends in the same change** (`SECURITY.md`: a new
parameter extends the sim domain and its per-epoch invariant assertions in
the same change; failures stay seed-reproducible):

- `Scenario` (sim.rs:68) gains `redemption_margin_bps`, randomized across
  the full allowed range in `Scenario::from_seed` (the domain's randomized
  interior).
- The three sim call sites (:775, :837, :860) read the scenario knob; the
  file-local const is deleted.
- Two new **boundary scenarios** (the sim.rs:153 pattern — each pins an
  edge and the smoke test asserts the edge was actually exercised, so none
  can rot into a no-op): `margin-zero` (no drift cover: the refund counter
  is expected to move under high-yield timing — refunds are the modeled,
  safe outcome, invariant violations are not) and `margin-max` (the full
  bound: the reserve over-covers, deploys shrink, and every §4.2-family
  invariant — TVV identity, four-way receipt conservation, share
  conservation, `settle + write_down == matured` — must hold unchanged).
- The invariant battery itself (sim.rs:1035–1110) is parameter-independent
  and is not weakened or specialized; the margin knob changes which paths
  it exercises, not what it asserts. The `redemption_refunds` counter is
  the finding's quantification instrument and remains the evidence base
  for the launch-time margin sizing row (spec §14 checklist, CO-37).

### 2.5 `ReceiptAccounting {}`: the §5.1 invariant, queryable in one read

Spec §5.1's continuously-verified invariant: *receipt outstanding == receipt
held by the principal marker == receipt bank supply == nHASH out on chain
(delegated + unbonding + pending deployment)*. Today a verifier assembles
this from `EpochStatus.receipt_minted` plus separate bank/staking queries at
different heights. The new query returns the legs the contract itself can
read, in one consistent state read:

```
ReceiptAccountingResponse {
  receipt_minted,        // the §5.1 counter (state.rs RECEIPT_MINTED)
  receipt_bank_supply,   // bank supply of receipt_denom
  staked,                // sum of program delegations (paginated read)
  unbonding,             // in-flight unbonding (epoch.rs unbonding_state)
  pending_deployment,    // earmarked PENDING_DELEGATIONS total
  matured_unsettled,     // minted − staked − unbonding, saturating
}
```

Reuses the paginated readers the crank already trusts (`unbonding_state`,
epoch.rs:74 — pagination follows to exhaustion, a truncated read is the
exact bug that function's doc comment forbids). Read-only, permissionless,
bounded by the 100-validator ceiling like every other chain sweep. Spec
§11.3 gains the entry in the same change (commit D); the exact field set is
settled against what the whitelisted queries can serve at commit B and the
spec records what shipped.

`cargo schema` is regenerated and committed **in each contract commit** —
the CI gate (`git diff --exit-code -- schema`, `contracts/CLAUDE.md` §CI)
enforces per-commit currency, and the committed JSON is what the App's
template-totality test reads.

### 2.6 Schemas leave baseline mode: the flip is a mechanism, not a sentence

**Mechanics.** The two existing baseline migrations become **frozen
migration 0** — `20260715013707_init` and `20260723000000_init_sessions`
are never regenerated again; every future schema change is a new,
timestamped, append-only migration produced with `prisma migrate diff
--from-migrations --to-schema-datamodel` (from-migrations, no longer
from-empty), hand-written SQL included where the datamodel cannot express
the constraint. `./dev pg reset` remains a **dev-environment convenience**
(it replays the full migration chain), not the schema-change procedure.

**Enforcement, because a rule without a gate is a wish** (two new tests):

- **Freeze gate:** a test in each workspace pins the SHA-256 of its frozen
  migration 0 file(s) (`services/indexer/test/migration-freeze.test.ts`,
  `apps/web/test/migration-freeze.test.ts`). Editing history — including
  "regenerating the baseline" out of habit — fails CI with a message
  pointing at this plan's rule. The app-side test also asserts the two
  hand-written blocks (schema guard, partial unique index) are present in
  the frozen file; the indexer-side test asserts the `proposers` NOT NULL
  `ALTER TABLE` is.
- **Fold gate:** the existing model-vs-migration staleness checks flip
  direction: `prisma migrate diff --from-migrations
  --to-schema-datamodel prisma` must be **empty**, i.e. the migration chain
  folds to exactly the models. A model edit without an appended migration
  (or vice versa) fails CI. Migrations must still apply cleanly to an empty
  database (the standing `db-grants` CI path, unchanged).

**Why `indexed` flips at the same time as `app`.** The trigger is the first
environment whose contents cannot be recreated, and `app` crosses it first —
sessions, the notification log, and push subscriptions are not rebuildable
from chain (apps/web/CLAUDE.md:41–44), while `indexed` is rebuildable by
definition. The honest version of the argument for flipping both anyway:

1. **The stale-instruction hazard is the row's own part (iii).** Two schema
   lifecycles in one repo means every schema change starts with "which mode
   is this one in?", and the failure mode — someone regenerates the indexer
   baseline because that was the rule last month — is exactly the class of
   error this row exists to retire. One rule everywhere is cheaper than two
   rules plus a discriminator.
2. **"Rebuildable" stops being cheap at 8.4.** Against the public Provenance
   testnet (D27) a full re-index is hours-to-days of LCD sweeps against
   infrastructure we do not control, and T1's verification ledger
   (calendar-boundary observations, lag-under-backfill measurements) reads
   from that database — a casual wipe destroys measurement continuity even
   though the data is theoretically reproducible.
3. **The cost of flipping early is near zero.** `indexed` migrations stay
   append-only from a frozen baseline; the only thing lost is the
   convenience of regenerating one file, which the fold gate replaces with
   an appended diff — the same command with different flags.

The alternative (flip `app` now, `indexed` at first testnet backfill) saves
nothing measurable and spends a discriminator. Rejected.

**Ordering note.** 8.4a lands *before* 8.4, so at flip time no deployed
database exists anywhere — the flip is prophylactic, which is the correct
order: the rule changes before the first environment that depends on it, not
after (master plan §2 phase note: "after 8.4a should assume migrations, not
rebuilds").

### 2.7 The rule replacement preserves constraints, never deletes them

The comment standard: when a lore comment encodes a real constraint, rewrite
it as the constraint. The three sites are **replaced**, in the same commit
as the mechanism (commit C):

- `services/indexer/CLAUDE.md:27–36` — "ONE baseline migration" becomes the
  migration rule: frozen baseline, append-only diffs from `--from-migrations`,
  the freeze/fold gates named, and the constraint carried forward in
  migration form: *any migration touching `gov_proposals.proposers` must
  preserve NOT NULL — x/group requires at least one proposer and the
  generated client types the list as required; the constraint lives as
  hand-written SQL because a list column's nullability is not a Prisma
  datamodel property* (today at indexer-design-notes.md:241–244 and the
  baseline's own trailing comment).
- `apps/web/CLAUDE.md:35–44` — same replacement; the "first environment
  whose contents must survive" sentence becomes "that point is behind us as
  of PR 8.4a"; the two hand-written blocks are re-stated as frozen-baseline
  facts guarded by the freeze gate, not as re-application instructions
  (there is no longer a regeneration to survive).
- `indexer-design-notes.md` §Schema history (:235–244) — rewritten as the
  historical record it now is (baseline mode ran 2026-07-15 → 2026-08-…,
  frozen at migration 0) plus the standing proposers constraint in its
  migration-form phrasing.

No environment is left following stale instructions, and no constraint is
lost in the rewrite — the freeze-gate tests assert the constraint text's
SQL survives in the frozen files, mechanically.

## 4. Security & invariants (enforced mechanisms with gating tests)

Attacker-gain lines on every authorization/honesty invariant, per overview
§8 (D26).

1. **Only the admin group policy can migrate the contract.** The wasmd admin
   is set to the admin group policy address at instantiate; no deployer key,
   member key, or stranger can route `MsgMigrateContract`.
   *What an attacker gains if it does not hold:* **complete code control
   over a fund-custodying contract** — a migration installs arbitrary new
   code behind the existing contract address, inheriting asset-manager
   authority over the vault, receipt mint/burn, and NAV authority in one
   move; every other invariant in this repository is void from that moment.
   Said plainly: whoever can migrate owns the funds.
   *Gates (named):* `migrate-drill.sh` **step-2 rejection assertions**
   (non-member AND single-member both rejected) and **step-1 admin
   assertion** (`q wasm contract` admin == policy). New tests; drill
   assertions count as gates per the master plan §6 trust-surface row.
2. **A migration cannot downgrade or adopt a foreign contract's state.**
   In-contract cw2 gate: name must match, stored version must not exceed
   the code's.
   *What an attacker gains if it does not hold:* an authorized-but-mistaken
   (or socially-engineered) proposal migrates to an older code id,
   silently resurrecting fixed exploits (F1–F9 class) with the full
   ceremony of legitimacy — the group approves a hash it believes is
   forward.
   *Gates:* commit A unit tests (all four version/name quadrants);
   `migrate-drill.sh` **step-6 downgrade leg** (live-chain
   `ACCEPTED` + `executor_result FAILURE`, state untouched).
3. **v1 migrate transforms no state.** *Gate:* `migrate-drill.sh` **step-5
   byte-for-byte dump diff** (whole raw state equal except `contract_info`)
   plus the unit-level storage-snapshot assertion. This is an honesty
   invariant about the capability's blast radius, not just hygiene: it is
   what makes "the entry point exists but does nothing yet" a verified
   claim in the spec amendment rather than a promise.
4. **`redemption_margin_bps` is bounded at entry.** Reject outside the
   stated range at instantiate and after every UpdateConfig merge — no
   out-of-range value is ever stored (the `Config::validate` mechanism,
   state.rs:58–101).
   *What an attacker gains if it does not hold:* nothing directly (the
   field is admin-gated), but an unbounded value turns an admin mistake
   into a liquidity failure — a fat-fingered 50_000 bps margin reserves 5×
   the queue and halts deployment economics without tripping any alarm.
   Bounding converts that to a rejected proposal.
   *Gates:* extended `instantiate_bounds_every_config_input` and
   `update_config_rejects_out_of_range_values`; the App-side pinned bound
   in `governance-templates.test.ts` (which fails if the contract bound and
   template bound ever diverge — the cross-repo half of the mechanism).
5. **The margin parameter cannot break the §4.2 invariant family anywhere
   in its allowed domain.** Sim domain randomizes the knob and pins both
   edges; TVV identity, receipt conservation, share conservation, and
   undeferred loss recognition are asserted per epoch, seed-reproducibly.
   *Gates:* the CI fixed-seed smoke over the extended `Scenario`; the two
   new boundary scenarios with exercised-edge assertions (a no-op boundary
   scenario is itself a test failure, the sim.rs:151 discipline).
6. **`ReceiptAccounting` is read-only, bounded, and safe for any caller.**
   Paginated reads to exhaustion; no truncation; bounded by the
   100-validator ceiling. *Gates:* unit test on the response arithmetic;
   the query reuses `unbonding_state`, whose pagination contract is already
   pinned.
7. **The committed schema is the shipped interface, per commit.** *Gate:*
   the standing contracts-CI schema-diff gate — which is also what feeds
   invariant 4's App-side half.
8. **Migration history is append-only and the frozen baselines are
   immutable, hand-written constraints included.** *What is lost if it does
   not hold:* the `proposers` NOT NULL and the app schema's partial unique
   index silently vanish in a "regeneration", and the first environment
   with real data diverges from every other — the exact failure the
   reset-and-rebuild rule previously prevented by other means.
   *Gates:* the two new **freeze gates** (SHA-256 pins + constraint-text
   assertions) and the flipped **fold gates** (§2.6). New tests, named
   `migration-freeze.test.ts` in each workspace.
9. **Standing gates continue:** `cargo fmt`/`clippy -D warnings` on the
   pinned root toolchain (1.97.1, `rust-toolchain.toml` — which stays at
   the repo root; the optimizer-container constraint is load-bearing),
   `cargo test --locked` over a fresh artifact, the sim smoke, schema diff;
   `pnpm -r` typecheck/test/Biome via `./dev`; no binary artifact
   committed anywhere (the drill's version-bumped wasm lives in a temp
   dir).

**Nullable-gates-affordance review:** the contract gains no nullable that
gates an affordance. The one absence-gated capability is wasmd-level: an
**unset admin** means migration is permanently impossible — absence means
"no, forever", not "unknown", and it is treated conservatively by never
offering an unset-admin bootstrap path (§2.2) and asserting the set admin in
the drill's step 1. The `Option<u64>` message fields mean "leave unchanged /
use default", the established UpdateConfig semantics, and gate nothing.

## 7. Open questions (each with a recommendation)

- **Q1 — exact margin bounds.** Recommend **`0..=1_000` bps, reject
  outside** (never clamp — the `validate` idiom), default 50. Rationale in
  §2.4: the sizing rule at hostile extremes needs ~117 bps; 1_000 gives 8×
  headroom while capping the liquidity-brake failure mode. Zero is allowed:
  a zero margin's failure mode is a **refund**, which the vault handles and
  the sim's refund counter surfaces — an economic knob, not a safety hole;
  the `margin-zero` boundary scenario keeps it honest. Confirm before
  commit B (the bound lands in `validate`, the template, and the spec
  simultaneously).
- **Q2 — which policy holds the wasmd admin.** D21 says the **admin**
  policy, and this plan follows it. Recommend confirming the rationale into
  the spec text: code migration is fund administration at its most extreme,
  so it belongs with pause/halt under the admin policy's (eventually
  tighter, 8.5) threshold — never the ops policy, whose remit is parameter
  tuning.

  next. The byte-for-byte drill assertion is stronger evidence of intent

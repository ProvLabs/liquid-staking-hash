## 2. Mechanism

### 2.1 Entity anchors are URL fragments over the existing routes

The anchor contract (recorded in console-spec §14 as the console-side record
of app §14.13, §6):

| Anchor | Grammar | Landing view | Entity source |
| --- | --- | --- | --- |
| redemption request | `#req-{request_id}` | `/redemptions` queue table row | vault pending-swap-out queue |
| validator | `#val-{valoper}` | `/validators` table row (expanded) | `Validators {}` |
| epoch | `#epoch-{epoch_index}` | `/` epoch-history table row | the IndexedDB ledger (§9.3) |
| proposal | `#prop-{proposal_id}` | `/governance` proposal row (expanded) | x/group live state |

Fragments, not routes or query params, deliberately: a fragment never reaches
the static host, so the anchor mechanism adds **zero** new server-routing
surface — the SPA-fallback rewrite the existing page-level deep links already
require (BrowserRouter, `src/main.tsx`) is the only hosting requirement, and
it is 8.4's to enforce (§4 invariant 6 hands it off explicitly).

One module, `src/lib/anchors.ts`, owns the grammar (parse + format, a closed
discriminated union) and one hook applies it: on first arrival of the owning
query's data, find the row, scroll it into view, apply a transient highlight
(reduced-motion aware per §11.7), and expand it where the page has row
expansion. **The anchor-miss state is a first-class honesty surface**, not a
silent no-scroll: when the data has loaded and the entity is absent, the page
renders a labeled notice with the entity-specific reason —

- request: "the chain's queue no longer holds request #N (paid out, refunded,
  or never existed)";
- validator: "no enrolled validator {valoper} (unregistered or never
  enrolled)";
- epoch: "this browser's ledger has no epoch #N — history accrues per browser
  (§5.3)" — the §14 item 5 caveat, surfaced exactly where the history-poor
  consequence bites;
- proposal: "the chain retains only live proposals; executed and rejected
  proposals are pruned (chain-facts §x/group 1) — durable history is the
  App's record."

A stale or still-loading owning query renders no miss-notice (absence is not
yet a fact, chain-facts §x/group 3's "a partial sweep is no prune signal"
generalized); the notice appears only on a *successful* read that lacks the
entity.

### 2.2 The governance panel renders only what the LCD serves, and says so

New route `/governance`, Monitor nav group (read-only; no write surface —
proposal composition stays §17.3 deferred). The console has no backend, so the
panel is the **live plane only**, which is precisely its engineering value
next to the App's indexed mirror (m7.2): it answers "what does the chain hold
*right now*", raw JSON behind every derived figure (§9.6 idiom).

Data, all over the already-pinned LCD (same origin, no CSP change; routes as
exercised by `services/indexer/src/workers/governance/policies.ts:112-198`
and `state.ts:92-227`):

1. `group_policy_info(Config.admin)` → group id. A **404 is the plain-account
   fact** ("this deployment has no group behind it"); any other failure is
   "could not check" — two different answers, never conflated
   (chain-facts §x/group 8).
2. `group_policies_by_group`, `group_info`, `group_members` — the D25
   dual-policy topology rendered as found (set-valued; the console asserts no
   expected count), members with weights.
3. `proposals_by_group_policy` per policy, paginated **to exhaustion under an
   explicit page cap**; hitting the cap renders a "truncated at N" label,
   never a silent drop and never a prune inference (chain-facts §x/group 9).
4. Per SUBMITTED proposal: the live tally from the **Tally query**
   (`/cosmos/group/v1/proposals/{id}/tally`) — `final_tally_result` is zeros
   until the module tallies, and rendering those zeros would assert "nobody
   voted" (chain-facts §x/group 7); `votes_by_proposal` (recoverable only
   while SUBMITTED, §x/group 2); voting-period-end countdown.
5. The pruning caveat as standing panel copy: an executed/rejected proposal is
   pruned in its own transaction, so this panel *structurally cannot show
   outcome history* — the honest empty state names the App's governance
   center as the durable record. This is §17 honesty applied to absence.

Poll tier: medium (30 s) for proposals/tally, slow for policy/member topology.
Mock fixtures (`src/data/fixtures.ts`) gain the governance shapes so
`VITE_MOCK=true` renders the page, per the console's standing convention.

### 2.3 The App side: `governance` target + typed anchors, one pair with 2.2

`VerifyTarget` gains `"governance"` and `verifyHref` gains an optional typed
anchor argument — a discriminated union keyed by target (`redemptions` accepts
only a request-id anchor, `validators` only a valoper, `overview` only an
epoch index, `governance` only a proposal id), so an anchor cannot attach to a
target that has no row for it: the impossible link is unrepresentable, not
validated. The map stays CLOSED and total (`satisfies`), the origin lock is
unchanged, and fragments are appended after the path so the environment lock
(`{CONSOLE_URL}` prefix, boot-checked chain id) is untouched.

Call sites added: the governance routes (`app/routes/governance.tsx` list →
`/governance`; `governance.$proposalId.tsx` → `#prop-{id}` **on rows whose
live plane holds the proposal only** — a `pruned` row keeps no verify link,
because a link to a pruned proposal is a dead link with extra steps, the exact
D8 rule now applied per-row instead of per-surface);
`app/components/portfolio/active-redemptions.tsx` (`#req-{id}` per active
request); `app/components/validators/mine/standing-header.tsx` (existing
`validators` target gains the valoper anchor); `app/components/market/history.tsx`
epoch rows (`overview` + `#epoch-{index}`).

The anchor grammar exists in two codebases that cannot share code (the console
is outside the pnpm workspace, ADR-001 Decision 4). The authority is the
console-spec §14 record (§6), and **both** suites pin the same golden strings
against it (`apps/web/test/verify-link.test.ts`,
`apps/console/test/anchors.test.ts`) — drift fails whichever side moved.

### 2.4 The tx layer is first-party; the reviewed-dependency event resolves to the empty set

The recorded constraint (`apps/console/CLAUDE.md`: "re-add only the needed
cosmjs packages at a current, audited version") assumed the adapter would need
some. **Research says the needed set is empty.** `apps/web` ships the same
vendor (Figure extension, `window.figure.provenance` connect/signDirect,
`apps/web/app/wallet/figure-extension.ts:24-44`) with **zero** `@cosmjs/*`
dependencies: a ~177-line dependency-free protobuf writer
(`apps/web/app/tx/proto.ts`, whose header cites "the console precedent" and
SECURITY.md's dependency posture), first-party `MsgExecuteContract` encoding
(`build.ts:386`), and simulate-verbatim fees. This PR mirrors that stack into
the console rather than re-importing the `elliptic` advisory chain at any
version — §7 Q3 records this as the SECURITY.md reviewed-dependency decision,
with outcome "no dependency added", and amends the CLAUDE.md constraint to
match (§6).

New console modules (mirror-tracked the way `src/lib/types.ts` tracks
`msg.rs` — a header comment naming the `apps/web` source of truth and the
same-change update rule):

- `src/tx/proto.ts` — the wire primitives (ported, trimmed to what the
  console encodes).
- `src/tx/build.ts` — `MsgExecuteContract` (sender/contract/msg/funds),
  `TxBody`, `AuthInfo` (SIGN_MODE_DIRECT, secp256k1 pubkey Any), `SignDoc`,
  `TxRaw`. Account number/sequence from
  `GET /cosmos/auth/v1beta1/accounts/{addr}` (decoded defensively —
  **[VERIFY]** on devnet which account type wrappers Provenance returns).
- `src/tx/simulate.ts` — `POST /cosmos/tx/v1beta1/simulate` over the unsigned
  bytes; **the returned gas-wanted IS the fee, used verbatim**:
  `gas_limit == amount`, denom `nhash`, no price, no factor
  (chain-facts §flatfees; `GAS_PRICE_NHASH = 1n` mirrored from
  `simulate.server.ts`). Simulation failure surfaces the chain error verbatim
  before signing (§10.2 step 2).
- `src/tx/figure-extension.ts` — the vendor module, PROVISIONAL against the
  same injected surface `apps/web` certifies (a divergence found by W1's
  checklist run is fixed in the vendor module of *both* apps and recorded in
  app-spec §14.1). `signDirect` only; an extension without it gets a specific
  error, never a silent amino fallback signing different bytes.
- `src/tx/broadcast.ts` — `POST /cosmos/tx/v1beta1/txs` (BROADCAST_MODE_SYNC)
  + inclusion polling (`GET /cosmos/tx/v1beta1/txs/{hash}`) feeding the
  existing toast lifecycle in `execute.tsx`.

`wallet.tsx` keeps its adapter interface; the real `connect`/`signAndBroadcast`
path replaces the line-41 throw. The confirm sheet's fee line becomes the
simulate result with the flat-fee caption, replacing the §17-honest "not
estimated here" placeholder — the display claims exactly what was computed,
and only that.

**Write-surface scope check** (the brief's question answered from the specs):
console v1 owns the **entire §4 role table** as an engineering surface —
keeper cranks, operator enroll/unregister/pay/purge, admin
config/halt/pause/recovery. App-spec §14.6 moved these into the App as the
*consumer* path but explicitly retains the console as the engineering surface
("no longer the required path", not "removed"), and console-spec §15 steps
5–6 build them all. So the adapter serves every existing guard-preflighted
button; nothing is narrowed. The admin subset's *execution* path is §14
item 6, resolved in §2.6.

### 2.5 CSP `connect-src` is generated from the profile, never hand-edited

`index.html`'s CSP meta keeps its static directives but carries a
`__CSP_CONNECT_SRC__` token; a small Vite plugin (`transformIndexHtml`, in
`vite.config.ts`) replaces it at dev-serve and build time from a pure function
in `apps/console/build/csp.ts`:

- `connectSrcFor(mode, lcdUrl)` returns `'self'` + the **exact origin** parsed
  from `VITE_LCD_URL`, plus `http://localhost:*` **only** when
  `mode === "devnet"`.
- It **throws** on an unparseable URL, a bare wildcard, or any attempt to emit
  a blanket `https:` — the build fails closed rather than shipping a wide or
  wrong pin.
- The single source is the same `VITE_LCD_URL` the app itself queries
  (`src/data/lcd.ts:10`), so a wrong CSP pin and a wrong data plane are the
  same visible defect, not two drifting lists. A test-profile build no longer
  ships the mainnet LCD host and vice versa; an 8.4 program-operated LCD is a
  one-line profile change (D24's LCD-hosts row consumes this mechanism).

The meta-tag CSP remains the delivery vehicle (static host); tightening via
server headers is an 8.4 deployment option layered on top, not a replacement
(§7 Q5).

### 2.6 Console §14 items 5, 6, 7 and CO-24 — resolved here, recorded in §6

- **Item 5, epoch-ledger backfill: v1 ships WITHOUT backfill.** The
  history-poor consequence stays, labeled (the §11.5 empty-state copy plus the
  §2.1 epoch anchor-miss notice). Rationale: backfill means unbounded
  historical `tx_search` scans from the browser against the pinned LCD — a
  cost profile the App's indexer already paid properly, and §17.3 already
  names indexer-backed history as the durable fix. Building a second, worse
  indexer inside a no-backend SPA to dodge a labeled limitation would trade
  honesty machinery for scan load. The anchor contract is designed so the gap
  is *stated at the point of impact* rather than papered over.
- **Item 6, admin execution path: compose-message-JSON is the production
  path; direct execute survives only behind the literal address match.** The
  mechanism decides this, not preference: on every non-devnet deployment the
  admin is a group **policy address** created before instantiate (D25,
  CO-28), and a policy address is not a wallet — no connected extension can
  ever satisfy `address == Config.admin` (`src/lib/guards.ts` role
  detection). Admin program-ops reach the chain as governance proposals, and
  the App owns that flow (app-spec §8.7/§14.6 decided). So the Admin panel's
  terminal action is **"copy encoded message JSON for a group proposal"**
  (the §8.7 parenthetical made primary), with a link into the App's
  governance center as the acting surface — the console's link is *verify,
  not act*. The direct-execute button renders only when the connected address
  literally equals `Config.admin`, which on devnet plain-account bootstraps
  it can; nothing role-gates on topology assumptions.
- **Item 7, monikers/identicons/explorer:** fetch **real monikers** from
  `cosmos.staking.v1beta1/Validators` (spec §5.2 already lists the query; the
  fabricated `monikerOf` at `Validators.tsx:14-16` is deleted — a synthesized
  name on a verification tool is a small standing lie). Fallback is the
  truncated valoper in the existing address-chip form, **no identicons**
  (fabricated visual identity invites recognition of noise). External
  explorer: link the valoper via `explorerAccountBase` on row expansion, the
  address-chip pattern already shipped — policy: explorer links are
  supplements on expansion, never the primary verification path (the console
  *is* the verification path).
- **CO-24, IncidentKind → IncidentSeverity vs console §11.2 — CONFIRMED, with
  one recorded vocabulary note.** As built
  (`services/indexer/src/reconciler/incidents.ts:122-181`):
  `reconciler_divergence` critical, `contract_halted` critical, `indexer_lag`
  warning, `slash_write_down` warning, `redemption_refund` info. Against
  §11.2 semantics: contract halted → `--status-critical` ✓; divergence is the
  identity-check-fail class → critical ✓; lag is the stale-data class →
  warning ✓; a write-down is invariant-skew class → warning ✓; a refund is
  informational ✓. The note: the incident vocabulary is three-valued
  (`info | warning | critical`) while §11.2 is four-valued; the mapping rule
  recorded is **serious-class conditions carry `warning` severity** (the
  console's serious *rendering* stays a display concern). This binds D30's
  8.1 `vault_paused` decoder to `warning`, and it is recorded in the m2.5
  plan's open-question row and beside §11.2's status table (§6) so the copy
  consumers m2.5 §6 worried about inherit one rule.

### 2.7 The test harness the gates require

Vitest joins the console's devDependencies with a `test` script; the CI
console job (`app-ci.yaml:317-335`) gains `npm test` and a
`npm run build:test && node scripts/check-bundle.mjs` step. The bundle guard
mirrors `apps/web`'s `check:bundle` precedent: the built test/production
bundle must contain **no devnet-key/mock-identity material** (scan for the
`MOCK_IDENTITIES` literals and the direct-key marker), which converts §10.1's
"compile-time excluded" from prose to a gate — the mock/devnet path moves
behind a build-mode static condition so Vite's dead-code elimination actually
removes it, and the guard proves it stayed removed.

## 4. Security & invariants (enforced mechanisms with gating tests)

Attacker-gain lines per overview §8 (D26) on every authorization/honesty
invariant.

1. **`connect-src` pins exactly the profile's LCD origin; the build fails
   closed on anything wider.** *Attacker gain if broken:* any code-injection
   foothold (compromised dependency, future XSS) gains an exfiltration and
   command channel to arbitrary hosts from a **publicly reachable** (D22)
   page that users connect wallets to — addresses, role facts, and the
   pretext for a substitute-signing phish. A *wrong* (rather than wide) pin
   is self-announcing: the app reads through the same variable, so the
   console visibly cannot load data. *Gates:* `test/csp.test.ts` (throw
   cases + per-profile origin cases); the built-output case (§3.5).
2. **The console signs only what it rendered.** The bytes handed to
   `signDirect` are encoded from the exact message object the confirm sheet
   displayed; funds attach only to `PayCommission`/`PayTip` (§10.2 step 1).
   *Attacker gain if broken:* a signature over an action the engineer never
   reviewed — funds moved with a payment message, or a halt/config/purge
   executed under a benign-looking confirm. *Gates:*
   `test/sign-binding.test.ts` (decode-back deep-equality);
   `test/tx-build.test.ts` byte-goldens pinning the encoding itself.
3. **No key material, ever** (SECURITY.md apps rule). The extension owns
   signing; the console handles an address and signatures only. The devnet
   direct-key/mock path is **absent from test/production bundles**, now
   enforced rather than asserted. *Attacker gain if broken:* a key-entry
   surface on a public testnet build — the exact phishing target SECURITY.md
   exists to preclude; a public bundle containing a "connect as admin" mock
   path also fabricates authority theater. *Gates:* `scripts/check-bundle.mjs`
   in CI against the `build:test` output; the CI step fails on any
   mock-identity/direct-key marker.
4. **The fee is the chain's simulate result, verbatim — stated as computed.**
   No price knob, no factor, `gas_limit == amount`
   (chain-facts §flatfees; a `gas × price` tx is *rejected*, not overpriced).
   *Honesty stake:* a confirm sheet stating a fee it did not compute is a §17
   break on a fund-adjacent surface. *Gates:* `test/tx-fee.test.ts` (the
   `apps/web/test/tx-fee.test.ts` mirror); the confirm-sheet case asserting
   the displayed figure is the simulate return.
5. **Anchor honesty: a verify link never lies by silence.** Every anchor
   resolves to the row, or to a labeled anchor-miss notice with the
   entity-specific reason — never a silent no-op scroll (which reads as
   "nothing to verify" or "verified fine" depending on the visitor's prior).
   *Attacker gain if broken:* dead or mute verify links train the public
   pilot's users (D22) that the program's own verification path is
   unreliable, which is the soil for "use this other explorer instead"
   substitution phishing; the anchor contract is what makes the App's
   honesty claims *checkable*. *Gates:* the commit-A miss-state cases per
   entity; the cross-pinned grammar goldens in both suites (§2.3);
   `test/verify-link.test.ts` origin lock over anchored hrefs.
6. **The environment lock survives the anchor extension.** Fragments append
   after the path; every href stays strictly under the booted `CONSOLE_URL`
   whose chain id the App's boot check proved. *Attacker gain if broken:* a
   verify link that escapes the console origin is an arbitrary-redirect
   primitive on money-adjacent figures. *Gate:* the extended
   `verify-link.test.ts` origin/traversal cases run over anchored forms.
   *Handoff, stated:* fragments cannot 404 at the host, but the **page paths
   still can** — the SPA-fallback rewrite is a hosting requirement 8.4's
   deploy profiles must encode and its pilot click-through must exercise
   (§4b C7 drill).
7. **The governance panel never invents state.** No-group (404) vs
   could-not-check (everything else) are distinct renders
   (chain-facts §x/group 8); open-proposal tallies come only from the Tally
   query (§x/group 7); a capped sweep labels itself truncated and infers no
   prune (§x/group 3, 9). *Attacker gain / honesty stake:* a panel that
   renders zeros as "nobody voted" or an outage as "no governance" hands a
   public viewer a false fact about who controls a fund-moving contract.
   *Gate:* `test/governance-state.test.ts` matrix (each cell named in §3.2).
8. **Role gating stays UX, never security** (§12). The compose-JSON admin
   path (§2.6) builds messages; the group policy on chain is the authority;
   hiding/showing buttons grants nothing. *Attacker gain if this were
   inverted:* none on chain — which is the point; the invariant is that no
   reviewer can find a console code path whose *safety* depends on role
   detection. *Gate:* review assertion + the §10.3 preflight tests continuing
   to pass with role forced to `admin` in mock mode against a non-admin
   chain state (the contract error surfaces verbatim).
9. **Dependency surface unchanged: zero packages added to `dependencies`.**
   The reviewed-dependency event (SECURITY.md supply chain) resolves to the

   of `package.json`/`package-lock.json`; `npm audit` in the 8.0b CI gate

10. **Standing gates continue:** Biome from the root, `tsc -b` in the console
    CI job, palette validator untouched (no new chart colors — the governance

## 4b. Completeness obligations (overview §8, v2 per D26)

### C1 — Natural keys & cardinality

| Key / collection | Uniqueness | Max multiplicity | Handling |
| --- | --- | --- | --- |
| `request_id` in the queue | unique (vault-assigned) | one row | anchor lands or misses; no dedupe needed |
| `valoper` in `Validators {}` | unique per contract | one row | same |
| `epoch_index` in the ledger | unique per `(chain_id, contract)` DB (§9.3) | one row | ledger DB partitioning already prevents cross-deployment collisions |
| `proposal_id` | chain-global | one row across policies | listed under its policy; anchor searches all discovered policies' lists |
| policies per group | set-valued | ≥ 2 under D25, 1 on legacy devnet | rendered as found; no expected-count assertion |
| proposals per policy | unbounded | page cap | paginate to exhaustion under cap; `truncated` label (C2) |
| anchors per URL | one fragment | 1 | last-wins is the browser's rule; the parser takes the whole fragment or nothing |

### C2 — Wire bounds

The console has no `bounds.ts` registry; bounds are per-read constants in
`src/data/lcd.ts`, each with the cap and the truncation behavior in the
return type (`{ items, truncated }`), because a hidden cap is a silent prune
(chain-facts §x/group 9). Bounded reads this PR adds: proposals per policy
(cap, truncated-labeled), votes per proposal (same), group members (same),
staking validators for monikers (page limit 200, the `stakingTotals`
precedent at `lcd.ts:109`). Existing pending-swap-out pagination (spec §13)
is unchanged and the anchor search runs over the exhaustively-paged list.
*Gate (C7):* the truncated cells in `governance-state.test.ts`; breaking a
cap's label makes the cap-hit case render an unlabeled full list and the test
fails on the missing label.

### C3 — Concurrency

| Read-then-write / race | Remedy |
| --- | --- |
| Anchor scroll vs polling refresh | scroll/expand fires **once**, on first successful data arrival for the owning query; later polls never re-scroll (a 10–30 s yank loop otherwise). The hook keys on "applied" state, not on data identity |
| Account sequence vs a concurrent tx from the same key | sequence fetched at sign time, once per submission; a stale sequence fails broadcast and the chain error surfaces verbatim in the toast — **no auto-retry, no sequence bumping** (a retry loop against a guard-rejected tx is a griefing pattern on the user's own funds) |
| Two rapid submissions from the confirm sheet | the confirm button disables on submit; the toast lifecycle is per-submission (existing `execute.tsx` shape) |
| Poll tiers racing the panel's first render | the store's existing `{data, fetchedAt, error}` per-query independence; the governance page renders per-section like every §9.6 consumer |

### C4 — State × affordance (generated from loader inputs)

Enumerated over `entity/panel state × {each owning read: ok, unavailable}`,
carried in types (discriminated unions — `GovHeader = governed | no-group |
unknown`, anchor result = `found | missing | pending`), so consumers are
compiler-forced. The cells:

| State × input | Render |
| --- | --- |
| anchor + owning read ok + row present | scroll, highlight, expand |
| anchor + owning read ok + row absent | entity-specific miss notice (§2.1); page otherwise normal |
| anchor + owning read failed/stale | no notice, section error/stale state as today; notice may appear on a later successful read |
| governance: policy 404 | "no group behind this deployment" (a valid state, not an error card) |
| governance: policy read failed | "could not check" (never no-group) |
| governance: proposals ok, tally read failed for one row | that row's tally cell degrades with reason; list survives (§9.6 per-section failure) |
| governance: page cap hit | list + "truncated at N" label; no prune inference |
| open proposal, zero votes yet | Tally-query result (possibly genuinely zero) labeled as live tally — never `final_tally_result` |
| wallet: no extension found | connect button → specific "extension not found" error |
| wallet: extension without `signDirect` | specific unsupported error; no fallback |
| tx: simulate failed | chain error verbatim, **before** signing; confirm proceeds nowhere |
| bundle: mode = test/production | no devnet/mock affordance exists in the artifact (gate 3) |

### C5 — Plane precedence

The console is **single-plane by design** (live LCD; §12 trust root), so no
live/indexed contest exists to resolve. The obligation C5 leaves is the
inverse of the App's: honesty about what the live plane **cannot hold** —
pruned proposals (panel caveat, §2.2.5), deleted votes (§x/group 2), the
single-snapshot epoch retention (ledger + item-5 caveat). Every such absence
is rendered as a stated retention fact with a pointer to the durable record
(the App), never as an empty list that implies "nothing ever happened". The
one two-source read that exists — NAV from the vault query with the contract
snapshot as fallback (`src/data/lcd.ts:33-36` note) — is unchanged.

### C6 — Temporal spans

Voting-period-end and (where a policy sets one) min-execution-period windows
render as countdowns on the proposal rows, the §11.5 countdown component;
spans tolerate ±1 block of skew (§13). The anchor highlight is a transient
span (~2 s, motion-reduced to a static outline). The ledger's `observed_at`
vs chain window times are already distinguished (§9.3); the epoch anchor
notice quotes ledger coverage ("epochs #7–#14 in this browser") so the span
of *recorded* history is explicit. **[VERIFY]** during the devnet drill: a
non-zero `min_execution_period` policy's window fields as served by this
build's LCD (CO-33's drill extension produces the fixture).

### C7 — Gate property

Every mechanism above names its test and what breaking it fails:

| Mechanism | Gate | Breaking it fails |
| --- | --- | --- |
| CSP generator throw-on-wide | `test/csp.test.ts` | widening to `https:` or dropping the origin turns a named case red; hand-editing `index.html` fails the token-replacement case |
| fee-verbatim | `test/tx-fee.test.ts` | reintroducing a price/factor fails the equality cases (the exact regression the App's twin test pins) |

None of these run against an in-memory stand-in of the thing they gate: the

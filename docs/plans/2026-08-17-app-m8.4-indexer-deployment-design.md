## 1. Origin & problem statement

The indexer runs today only under `infra/dev/compose.yaml`, against a devnet
node and a throwaway Postgres. Row 8.4 needs it running in `provlabs-test`
(and, later, `provlabs-prod`) on the team's standard pipeline: an image in
Artifact Registry, a Helm chart under ArgoCD, and a GitHub Actions caller that
builds, pushes and opens the image-bump PR.

Three properties of this particular service shape the whole design, and each
one removes work rather than adding it:

1. **It serves no HTTP, holds no keys, signs nothing** (`src/index.ts` boundary
   comment). No `Service`, no ingress, no Kong annotations, no port. Liveness
   is a heartbeat file written after each successful database ping and read by
   `scripts/healthcheck.mjs` — an `exec` probe, not an HTTP probe.
2. **It has a zero cross-package dependency surface** (`services/indexer/CLAUDE.md`):
   one runtime dependency, `@prisma/client`. The build context can be narrow.
3. **It is the sole writer of the `indexed` schema** as `indexer_writer`
   (ADR-001 Decision 1). The deployment must preserve that ownership, and
   migrations belong to this component and no other.

Against those, one property adds work: **it must be a single writer**, and the
reason is stronger than efficiency. `src/workers/chain-events/store.ts`
persists the running marker NAV in the reserved `meta:chain-events:nav`
checkpoint row via an **unconditional** last-write-wins upsert — unlike the
other idempotency arms, it carries no `observedHeight` guard — and reads it
back inside the window transaction. Two supervisors on different windows let
the later committer stamp its NAV over the other's. Overlap is a correctness
fault, not wasted work.

## 2. Mechanism

### 2.1 The container reproduces the dev execution path exactly

The service runs TypeScript sources directly on Node's type stripping; there is
deliberately no build step (ADR-002; `infra/dev/compose.yaml`). The image keeps
that: same `node:22-bookworm-slim` base as the tools plane and the `app-ci`
job containers, same `NODE_OPTIONS=--experimental-transform-types` (required —
`runtime/streams.ts` uses TS parameter properties, which strip-only mode
rejects), same sources. "Works in `./dev`" and "works in the cluster" stay one
claim.

Two alternatives were considered and rejected. An **esbuild bundle** would be
smaller and distroless-friendly, but introduces a build step for a service the
repo deliberately builds no step for, and diverges the deployed artifact from
the tested one. **`pnpm deploy --prod` into distroless Node** hardens the
runtime further but drops the `prisma` CLI that §2.3 needs in this image, and
Prisma's engine/libssl expectations on distroless are unverified. Distroless is
recorded as a hardening follow-up (§9), not a v1 requirement.

### 2.2 The chart holds no secret material

`cloud-sql-proxy` with `--auto-iam-authn` (the vault-manager pattern) means
`DATABASE_URL` carries a principal and no password. There is therefore **no
`SealedSecret` in this chart at all** — the strongest available reading of
SECURITY.md's secrets-via-environment rule and the overview §6 D24 posture
question.

This has one non-obvious consequence that must be handled in the role
bootstrap, not the chart. Prisma connects **as the IAM user**, so
`prisma migrate deploy` would create tables owned by
`nvhash-indexer@provlabs-test.iam` rather than by `indexer_writer` — which is
what `infra/dev/postgres/roles.sql` and the grant-boundary gate assert, and
what `api_reader`'s default privileges hang off. The fix is two statements per
environment:

```sql
GRANT indexer_writer TO "nvhash-indexer@provlabs-test.iam";
ALTER ROLE "nvhash-indexer@provlabs-test.iam" SET role = indexer_writer;
```

Without the second statement the deployment presents as healthy while silently
violating the ADR-001 boundary, and the first symptom is `api_reader` unable to
read a table added months later. It is a required part of §5, and §4b is what
keeps it from being a topology assumption.

The three domain roles are created **`NOLOGIN`** in the deployed bootstrap.
Only IAM principals authenticate; the roles exist purely to own objects and
carry grants. That is what lets the bootstrap file live in the repository
containing **no credential at all** — unlike `infra/dev/postgres/roles.sql`,
whose throwaway dev passwords are permitted by the devnet rule but would not be
permitted here (SECURITY.md, "secrets via environment only").

### 2.3 Migrations ride the same digest as the code

A run-to-completion **initContainer** in the same Pod, from the same image and
digest as the app container, runs `prisma migrate deploy` as `indexer_writer`
before the supervisor starts. Schema and code cannot be different commits.
`migrate deploy` is a no-op when up to date, so re-running on every Pod start
costs nothing.

Ordering is load-bearing and works without extra plumbing: `cloud-sql-proxy`
is a **native sidecar** (an initContainer with `restartPolicy: Always`), so it
starts and stays running before later initContainers execute — the proxy is
listening when the migration runs.

This is why the image does **not** prune dev dependencies: the `prisma` CLI and
`prisma/migrations` are what the initContainer runs. Roughly 40 MB, and the
direct cost of the guarantee.

### 2.4 A start height is required, and the seam is only half-wired

`Worker.startHeight` is declared at `src/runtime/worker.ts:34` and every worker
accepts it, but `src/index.ts` passes it **only** to the governance worker
(`BigInt(config.govStartHeight)`). chain-events, epoch-history and
validator-sampler fall through to `?? 0n`, floored to `1n` at
`src/runtime/worker.ts:108`.

On a real testnet (pio-testnet-1, ~33 M blocks) those three would page from
height 1 in 500-height windows — on the order of 66,000 windows, each doing a
`tx_search` plus a `block_results` per height. That does not index slowly; it
does not arrive.

The correct value is the **contract instantiate height**, not the deployment
date: blocks before instantiate hold no program events by definition, and
epoch-history and validator-sampler anchor to `run_epoch` crank heights that
cannot precede it. Deployment date would silently discard real history, and
8.4a's bootstrap ordering (group and policy created *before* instantiate, since
there is no admin-rotation message) makes a gap between the two likely.

`GOV_START_HEIGHT` stays an independent knob and is set explicitly in the same
values file. Its default of 1 is spec-recorded (overview §6 D13); coupling it to
the new variable to save one line would amend a spec for tidiness.

**Note on section references:** `§n` alone means a section of *this* document;
decision-register items are always written "overview §6 Dnn" to point at
[the milestone overview](2026-08-05-app-m8-hardening-and-pilot.md), whose §6 is
the register and whose §7 is the conformance map.

## 3. Design

### 3.1 `services/indexer/Dockerfile`

Build context is the repo root (the shared workflow's default `.`). Four stages
on a digest-pinned `node:22-bookworm-slim`, carrying the "keep in lockstep with
`infra/dev/compose.yaml`" note that `app-ci.yaml` already carries:

| Stage | Contents |
| --- | --- |
| `base` | image pin, `WORKDIR /app`, `COREPACK_ENABLE_DOWNLOAD_PROMPT=0` |
| `deps` | `pnpm-lock.yaml` + `pnpm-workspace.yaml` + **all 8 workspace manifests**, then `corepack pnpm install --frozen-lockfile --filter @nvhash/indexer` |
| `build` | `services/indexer/`, then `prisma generate --generator=client` |
| `final` | `COPY --from=build --chown=node:node /app /app`, `USER node`, `CMD ["node","services/indexer/src/index.ts"]` |

`pnpm-workspace.yaml` is not optional in `deps` — without it pnpm does not know
it is in a workspace and `--filter` resolves nothing. The `final` stage sets
three environment variables: `NODE_OPTIONS=--experimental-transform-types`,
`NODE_ENV=production`, and
`INDEXER_HEARTBEAT_FILE=/heartbeat/indexer.heartbeat`.

Three details that are not free choices:

- **`--generator=client`.** `prisma/schema.prisma` declares a *second*
  generator, `dbIndexed`, whose output is
  `../../../packages/db-indexed/generated/client`. A plain `prisma generate`
  fails in a context without `packages/db-indexed/`. Selecting the generator
  keeps `packages/` out of the image entirely.
- **All workspace manifests are copied explicitly** (root, `apps/web`,
  `services/api`, `services/indexer`, `packages/{api-types,chain-client,db-indexed,fixtures}`).
  `--frozen-lockfile` validates the lockfile's importers against the manifests
  present, so a filtered install with manifests missing reports the lockfile as
  out of sync. Listing them means **adding a workspace package fails this build
  loudly** instead of drifting. (`pnpm fetch` is the alternative and was
  rejected: it pulls the whole monorepo's dev tree, Playwright included, to
  build one service.)
- **`CMD` does not go through `pnpm run start`.** That script is
  `prisma generate && node src/index.ts`; generating at container start needs a
  writable tree and defeats `readOnlyRootFilesystem`. The Dockerfile says so in
  a comment, because the divergence from compose is otherwise the kind of thing
  a reader "fixes" back.

### 3.2 `services/indexer/Dockerfile.dockerignore`

Per-Dockerfile ignore file rather than a shared repo-root `.dockerignore`, so
each future component scopes its own context — the indexer's context has no
business containing `apps/`, `contracts/`, or `services/api/src`, and a shared
root file could never say that. BuildKit honours
`<dockerfile-name>.dockerignore` in preference to the context's
`.dockerignore`, and the shared workflow drives buildx on
`moby/buildkit:v0.32.2` with an explicit `file:` input, so the path is used.

Written as an **allowlist** (`**` then `!` re-inclusions), not a denylist: a
denylist fails *silently* when someone adds a top-level directory — it lands in
the context, credentials and large fixtures included. An allowlist fails
*loudly*, at the `deps` stage `COPY`. Fail-loud over fail-silent is how the
rest of this service is built (bounded config, allowlisted log fields,
allowlisted schema columns).

Two comments belong in the file: the manifest list is duplicated here and in
the `deps` stage (different jobs — context filter vs. copy — and a mismatch
surfaces as a failed build, not a bad image), and the file is **BuildKit-only**
(the legacy builder ignores it, so local reproduction needs
`docker buildx build`).

### 3.3 `services/indexer/argocd/` — the Helm chart

Chart name **`nvhash-indexer`**, equal to the `argo-app` input: the shared
workflow derives the image path
`us-central1-docker.pkg.dev/provlabs-test/docker/<argo-app>` from it, and
templates name resources off `{{ .Chart.Name }}`. A bare `indexer` is too
generic for a registry that already holds `vault-manager` and `nuva-app`.

**Two of vault-manager's five templates are deliberately absent**, and the
chart says why so neither is copied back in for symmetry:

- **no `service.yaml`** — the indexer serves no HTTP; nothing should be able to
  reach it;
- **no `sealed-secret.yaml`** — §2.2; the chart holds no secret material.

**`config-map.yaml`** — the indexer's configuration interface is environment
variables (`src/config.ts` reads `process.env`), not vault-manager's TOML file.
A ConfigMap consumed by `envFrom.configMapRef` carries `DATABASE_URL`,
`LCD_URL`, `RPC_URL`, `CHAIN_ID`, `CONTRACT_ADDRESS`, `VAULT_ADDRESS`,
`RECEIPT_DENOM`, `INDEX_START_HEIGHT`, `GOV_START_HEIGHT` and the tuning knobs.
A **`checksum/config` annotation on the pod template** is required: without it,
editing values restarts nothing and the indexer runs stale configuration
indefinitely.

**`deployment.yaml`**

- `replicas: 1` and `strategy: {type: Recreate}`, with a comment citing
  `store.ts` and §1: RollingUpdate would briefly run two supervisors, which is
  the exact overlap that corrupts the NAV carry.
- initContainers, in order: `cloud-sql-proxy` as a native sidecar
  (`--private-ip --auto-iam-authn --structured-logs --port=5432`), then
  `migrate` (§2.3) with `workingDir: /app/services/indexer` and
  `command: ["node_modules/.bin/prisma","migrate","deploy"]`.
- `startupProbe` and `livenessProbe`, both
  `exec: node /app/services/indexer/scripts/healthcheck.mjs`. Liveness at
  `periodSeconds: 15`, `failureThreshold: 3`, deliberately matched to the
  heartbeat contract (15 s ping interval, 45 s `MAX_AGE_MS` in
  `scripts/healthcheck.mjs`). **No `readinessProbe`** — nothing routes traffic
  here, so readiness would gate nothing.
- `securityContext`: `readOnlyRootFilesystem: true`, `runAsNonRoot`,
  `allowPrivilegeEscalation: false`, all capabilities dropped. Two `emptyDir`
  mounts make that possible: `/heartbeat` (the code already honours
  `INDEXER_HEARTBEAT_FILE`) and `/tmp`.
- Datadog labels and `DD_ENV`/`DD_SERVICE`/`DD_VERSION` `fieldRef` env as
  vault-manager. `datadog.version` **must** exist in values — the shared
  workflow writes it unconditionally. **No `dd-trace`**: a new runtime
  dependency against SECURITY.md's dependency discipline, recorded as a
  follow-up (§9) rather than smuggled in with a deployment change.
- Resources: `requests: 500m / 1Gi`, `limits: 2Gi`. First cut, and the comment
  says so — **PR 8.2** (load test) is where these get measured.

**`service-account.yaml`** — `iam.gke.io/gcp-service-account: nvhash-indexer@{{ .Values.projectId }}.iam.gserviceaccount.com`,
Workload Identity, vault-manager's shape.

**Values files.** `values.yaml` holds the environment-*invariant* defaults
(resources, probe timings, `INDEX_WINDOW_SPAN`, `POLL_INTERVAL_MS`,
`RECONCILE_INTERVAL_MS`) rather than vault-manager's `empty: placeholder` —
those values are not per-environment and duplicating them twice invites drift.
`values-test.yaml` carries `projectId`, image name, `datadog.env`, the
`pio-testnet-archive-rpc.provenance` host on `:26657`/`:1317`,
`chainId: pio-testnet-1`, the Cloud SQL instance name, the contract/vault/denom
identity, and `chain.startHeight` (the vault-manager `epochHeight` idiom).
`values-prod.yaml` mirrors it with mainnet-archive hosts and **contract/vault
left unset**: `config.ts`'s `required()` throws on a blank value, so an
accidental prod sync fails closed rather than indexing an unknown chain. Both
`values-gha-*.yaml` are CI-managed stubs with vault-manager's warning header.

### 3.4 `src/config.ts` + `src/index.ts` — `INDEX_START_HEIGHT`

Add `INDEX_START_HEIGHT` via `boundedInt(env, "INDEX_START_HEIGHT", 1, 1)`,
following the `GOV_START_HEIGHT` precedent exactly, and pass
`startHeight: BigInt(config.indexStartHeight)` to the chain-events,
epoch-history and validator-sampler workers in the composition root. Default 1
leaves devnet behaviour unchanged. Rationale in §2.4.

### 3.5 `.github/workflows/indexer-deploy-test.yaml`

A thin caller of the shared workflow:

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'services/indexer/**'
      - '!services/indexer/argocd/**'
      - 'pnpm-lock.yaml'
      - 'pnpm-workspace.yaml'
      - 'package.json'
      - '.github/workflows/indexer-deploy-test.yaml'
  workflow_dispatch:
permissions:
  id-token: write
  contents: write
  pull-requests: write
jobs:
  indexer:
    uses: ProvLabs/gha-workflows/.github/workflows/docker_build_and_argo_deploy_test.yaml@main
    secrets: inherit
    with:
      docker-file: services/indexer/Dockerfile
      argo-app: nvhash-indexer
      auto-merge: false
      build-cache: true
      reproducible: false
```

Four decisions in it:

- **The negation excludes the whole chart, not just `values-gha-*`.**
  crates-rs excludes only the gha files — the minimum that stops the deploy
  commit re-triggering the workflow. But a chart or values change needs no new
  image: ArgoCD reads the chart from git. Excluding the directory prevents the
  loop *and* the pointless rebuild. Negation rather than `paths-ignore` because
  GitHub rejects both filters on one event (crates-rs documents this; the
  reasoning carries over).
- **`reproducible: false`** — not merely deferral. `reproducible: true`
  disables provenance and SBOM attestations, and a Node dependency tree
  benefits far more from an SBOM than from digest stability. crates-rs earned
  reproducibility with hand-pinned digests and a verification script; the
  trade is worse here.
- **An explicit `permissions` block.** crates-rs omits it and inherits an org
  default; this repo's `app-ci.yaml` deliberately narrows to
  `contents: read`, and a reusable workflow's declared permissions are capped
  by the caller's token. Granting explicitly avoids a confusing failure in the
  `update-image` job.
- **`build-cache: true`** — registry-backed BuildKit cache, keyed on
  `argo-app`; the `deps` stage is the expensive one and is keyed on manifests.

### 3.6 `.github/workflows/indexer-deploy-prod.yaml`

`workflow_dispatch` only, required `docker-tag` input, calling
`docker_tag_and_argo_deploy_prod.yaml` with the same `argo-app`. It re-tags the
existing test image into the prod registry, so **the promoted artifact is the
digest that ran on testnet** — no rebuild. Its `update-image` job is gated
`if: github.ref == 'refs/heads/main'`, so the dispatch must come from `main`.

## 4. Security & invariants

The milestone's bar (overview §7): **"enforced" means a mechanism plus a gating
check, never a caller or topology assumption.** A Helm chart is exactly the kind
of artifact where security properties degrade into topology assumptions, so each
row below names its gate, and §4b is the work that makes three of them real.

| Property | Mechanism | Gating check |
| --- | --- | --- |
| No user-identifiable data in logs or schema | `logger.ts` `SAFE_FIELDS` allowlist; schema-field allowlist | existing `app-ci` gates, unchanged |
| Fails closed on misconfiguration | `config.ts` `required()` / `boundedInt`; `assertChainIsolation` boot check | existing unit suites; in-cluster symptom is CrashLoopBackOff, the correct outcome |
| Schema and code are the same commit | migrate initContainer runs the app container's own digest | none needed — impossible by construction (§2.3) |
| No key material, no signing | unchanged: no signer exists in this service, and this change adds no dependency that could introduce one | nothing new required — the property is structural, not configured |
| No secret material in repo, chart, or image | IAM auth; no `SealedSecret` template; `NOLOGIN` roles in the bootstrap | **§4b G1** (repo-scan) |
| Single writer | `replicas: 1` + `strategy: Recreate` | **§4b G2** (rendered-chart assertion) |
| ADR-001 ownership: `indexer_writer` owns every `indexed` table | `ALTER ROLE … SET role = indexer_writer` (§2.2) | **§4b G3** — otherwise a pure topology assumption |
| No HTTP surface | no `Service`, no `containerPort`, no ingress | **§4b G2** (same rendered-chart assertion) |

The container hardening (`readOnlyRootFilesystem`, non-root, dropped
capabilities) is defence in depth on a process that already holds no keys and
opens no listener.

## 4b. Enforced mechanisms this PR must add

Three gates, because without them the rows above are assertions about how the
cluster happens to be configured — which is what overview §7 forbids.

**G1 — secret repo-scan in `app-ci`.** Overview §7 already assigns this to
8.4 verbatim: "a repo-scan check in `app-ci` (no non-placeholder secrets outside
`.env.example` patterns) plus review of the 8.4 profiles." It is the gate that
keeps the secret-free-chart claim true as `values-*.yaml` files accumulate
across components, and it is the one gate here that is a milestone obligation
rather than this design's proposal.

**G2 — rendered-chart invariant assertion.** `helm template` the chart against
each values file and assert: `replicas: 1`; `strategy.type: Recreate`; no
`kind: Service`; no `containerPort`; `readOnlyRootFilesystem: true`; the migrate
initContainer's image equals the app container's image. This converts §1's
correctness requirement and the no-HTTP boundary from "someone reviewed the
YAML" into a check that fails when a future edit reintroduces RollingUpdate —
the single most likely regression in this design, because RollingUpdate is the
Kubernetes default and reads as an improvement.

**G3 — ownership assertion against the deployed schema.** The `ALTER ROLE`
in §2.2 is invisible when omitted. Minimum viable gate: extend the existing
grant-boundary integration suite to assert that every table in `indexed` is
owned by `indexer_writer` (true in dev today, and the property that actually
matters), so a bootstrap that fails to set the default role produces a failing
check somewhere rather than nowhere. See §8 Q2 for the residual gap — the dev
suite cannot observe the deployed instance, so this narrows the hole without
closing it.

**Tension to resolve, not to decide silently:** G1 and G2 are `app-ci.yaml`
changes, and the session direction for this design was to leave `app-ci.yaml`
alone. That direction was given about a *Docker build-only job* (dropped, and
still dropped — see §9). G1 is a milestone obligation and G2 is what keeps §1
from being a comment; both are named here so the call is explicit at plan
approval rather than absorbed as scope.

## 5. Out-of-repo prerequisites

None of these can be delivered by this change, and the deploy does not work
without them.

1. **GCP service account** `nvhash-indexer@provlabs-test.iam.gserviceaccount.com`
   with `roles/cloudsql.client` and `roles/cloudsql.instanceUser`,
   Workload-Identity-bound to the `nvhash-indexer` KSA in the target namespace.
2. **Cloud SQL**: an `nvhash` database (on the shared instance or its own) and
   the IAM database user `nvhash-indexer@provlabs-test.iam`.
3. **ArgoCD Application** `nvhash-indexer` per cluster, with
   `spec.source.path: services/indexer/argocd` and
   `valueFiles: [values-test.yaml, values-gha-test.yaml]`. The filename must
   contain `gha` — the shared workflow locates it with
   `select(contains("gha"))` and fails otherwise.
4. **Cloud SQL role bootstrap** — the deployed analogue of
   `infra/dev/postgres/roles.sql`: create `indexer_writer` / `api_reader` /
   `app_writer` as `NOLOGIN`, then the two statements in §2.2. New in-repo
   artifact, and credential-free by construction (§2.2); see §8 Q2 for the
   drift problem it creates.
5. **Org secrets visible to this repo**: `ARGOCD_API_KEY`,
   `ARGOCD_API_KEY_PROD`, `ARGOCD_IMAGE_UPDATER_APP_ID`,
   `ARGOCD_IMAGE_UPDATER_PRIVATE_KEY`. `secrets: inherit` passes only what the
   repository can already see.
6. **The ARGOCD image-updater GitHub App installed on this repository** — it
   opens the values-bump PR and needs contents + pull-request write here.
7. **Archive node reachability** from the namespace, and it must genuinely be an
   archive: the height-pinned `x-cosmos-block-height` reads in epoch-history,
   validator-sampler and governance fail against a pruning node.
8. **Whether ArgoCD auto-syncs**, which decides whether chart-only changes
   deploy on their own.

## 7. Sequencing

**8.4a's Prisma half is a hard blocker, and the migrate initContainer makes it
mechanical rather than advisory.** `prisma migrate deploy` of a *regenerated
baseline* against a populated database fails. 8.4a's contract half has landed
(`f27943f`, the wasmd `migrate` entry point, overview §6 D21); the
baseline-mode exit has not. Either it lands first, or the first testnet deploy
is treated as a one-time empty-database bootstrap with 8.4a required before the
next schema change.

Softer dependencies: `INDEX_START_HEIGHT` needs the real instantiate height, so
it needs the testnet bootstrap to have run (overview §6 D25 policy topology, D27
chain choice); and Q1 below should be settled before the chart's `DATABASE_URL`
is treated as final.

## 8. Open questions

**Q1 — Prisma over Cloud SQL IAM auth is the highest-risk unverified
assumption here.** vault-manager proves the pattern for `sqlx`. Prisma passing
an empty password to a proxy doing `--auto-iam-authn` *should* behave
identically, but it is unverified. Cheap probe: `prisma migrate status` against
the test instance through the proxy, before the chart's `DATABASE_URL` is
final. If it fails, the fallback is the password-in-`SealedSecret` path, which
re-adds the template §2.2 removes.

**Q2 — two role files, one gate.** `infra/dev/postgres/roles.sql` is pinned by
the grant-boundary test; the Cloud SQL bootstrap (§5 item 4) is not. They will
drift, and the drift is invisible until `api_reader` cannot read a table added
months later. §4b G3 narrows this by asserting the ownership *property* in the
dev suite, but no CI job can observe the deployed instance, so a bootstrap
applied incorrectly to Cloud SQL still passes everything. The honest options are
to parameterize one file for both environments, add a post-sync verification
step that runs against the real instance, or accept and document the gap with an
owner. **Under overview §7's definition this is the one row of §4 that cannot be
fully enforced by CI**, and it should be dispositioned explicitly rather than
inherited.

**Q3 — the `indexed_from_height` honesty gap.** That field rides the
**governance list payload only** (`services/api/src/routes.ts:825`). With a
non-1 `INDEX_START_HEIGHT`, the transactions / epochs / validators endpoints
present a truncated window as complete history — the same defect the governance
payload exists to prevent. Extend the mechanism, or record the gap as accepted.

**Q4 — deploy-PR CI cost (informational).** The generated values-bump PR
touches `services/indexer/argocd/values-gha-test.yaml`, which sits outside
`contracts/`, so `app-ci.yaml`'s `changes` filter marks it `app=true` and runs
the full suite — Playwright, `db-grants`, console typecheck — on a one-line
YAML edit, on every deploy. Deliberately not changed in this design; flagged
because it is immediately visible.

## 9. Out of scope

- `services/api`, `apps/web` and console charts — same pattern, own changes.
- `dd-trace` (new runtime dependency; labels only here).
- Distroless runtime (§2.1) — hardening follow-up.
- Reproducible builds (§3.5) — separate work, worse trade for a Node tree.
- Load-tested resource values — **PR 8.2** owns them.
- A PR-time Docker **build-only** job in `app-ci`. Considered and dropped by
  session direction. Consequence, recorded so it is a known trade: a broken
  `Dockerfile` or a stale `Dockerfile.dockerignore` allowlist is first observed
  on merge to `main`, when the deploy workflow runs. Distinct from §4b G1/G2,
  which are security gates rather than build convenience.
